# PRE-PROV 規格審閱（白話版）

> 這份給你看「這張票要做什麼、為什麼、怎麼驗」。你 10/19 晚上離線前交代「有問題你跟委員共識決」，所以規格定案由我和兩家委員（codex、composer）共識決定，這份是事後讓你核對用的。
> 正式規格：`docs/FFDSTAR_SPEC.md`（第 3 版）；施工清單：`docs/manifests/FFDSTAR.json`。

## 一句話

每次產生特徵時，多存一份「每一欄實際做了哪些處理」的紀錄；同時修好 IC 分析可能讀到舊資料的錯。

## 要解決的三件事

1. **處理紀錄沒存下來**：每一欄有沒有做平穩化、用了多少的分數差分階數（d*）、縮尾（去掉極端值）有沒有做，程式其實都算好了，但存說明檔的時機比收集紀錄早，所以一直沒存到。現在的說明檔只寫「設定上開了什麼」，不是「實際做了什麼」。
2. **IC 會讀到舊資料（資料正確性的錯）**：IC 分析為了快，會把特徵存一份快取重用；但它只認「設定編號」。同一組設定重新產生特徵（例如 K 線資料被更正）之後，IC 仍拿舊快取來算。
3. **失敗時可能留下「舊特徵＋新時間軸」**：委員審查時找到——重新產生特徵中途失敗時，時間軸檔已被換成新的，特徵檔卻退回舊的，兩者對不上。

## 怎麼做

- **紀錄存法（你 10/19 核可）**：每欄一列，存成壓縮表格檔，放在該次產出資料夾裡一個獨立的小資料夾；說明檔只記摘要和這個檔的指紋。最大的真實產出（20.4 萬欄）估計每次多約 1.3MB（約 +0.2%）。做完會用真實產出重量一次，超過估算兩倍會再問你。
- **成功也記**：每一步不只記失敗，成功、關閉、不適用都要記，而且必須來自程式實際走到的地方，不能拿設定充數。
- **資料內容指紋**：每次產出算一個「內容指紋」，內容一變指紋就變。IC 的快取改成比對這個指紋，不一樣就重讀。IC 報告和存活特徵清單也會寫明「用的是哪一次產出」。
- **失敗一律整次失敗**：存紀錄、算指紋、寫說明檔，任何一步失敗，整次產出就算失敗，不會留下一半新一半舊的狀態。
- **特徵數值完全不變**：這張票只「記錄」，不改任何特徵的值、欄數或格式。驗收會用真實 K 線比對改前改後，每一欄逐位元相同。

## 怎麼驗

- 158 項自動測試，全部用真實 K 線短區間資料，涵蓋：單週期、多週期、多幣種、平穩化開關、縮尾開關、預處理總開關關閉、特殊比率欄、死欄剔除、IC-first 流程。
- 每項重要檢查都另外寫一個「故意改壞」的版本，確認測試真的抓得到錯，而不是怎樣都會過。
- 檢查紀錄對不對時，不拿紀錄自己來證明自己，而是用獨立的計算重算一次比對。例如：拿紀錄裡的 d* 重算分數差分，看結果是否和實際存下的值一樣。

## 現在不做、留著的事（每條都有理由）

1. **R1 舊的共用 d* 快取檔查不出是哪次產出的**：你 8/5 定過「修正只考慮以後」，舊資料不回頭補。
2. **R2 產生特徵 API 回的任務編號查不到**：屬於 API 任務登記的範圍，和本票的紀錄、IC 身分沒有資料上的關聯，需另外查是不是原本就這樣設計。
3. **R3 ADF 平穩性檢定出錯時，程式當作「不平穩」繼續做**：要改成直接失敗就會改到特徵值，違反本票「不改數值」的前提；本票先讓它在紀錄裡看得到，等真實資料量出發生頻率再決定。兩家委員都同意不在本票改。
4. **R4 兩種計算路徑在少見設定下行為不一致**：屬於全票排序第 8 步（NUMVIEW）要統一的範圍。
