# 一、🔴 唯一的缺陷 — 這條你要知道

## `G3-D1` 匯出前篩選只有一組條件，正反例被同時截斷

**是什麼**：`/search` 匯出之前那個「篩選」，**只有一組條件**，而且**同時套用在正例和反例上**。

**為什麼是錯的**：如果你的條件引用了 `future_*`（未來幾根的報酬）欄，
那麼**正例和反例會同時被結果截斷**。後果是：

- 反例**不再是對照組**（它們也是被結果挑過的）
- 三組報酬表會**三組皆正**，看起來「怎麼選都贏」
- 條件 IC 建立在**照結果挑過**的樣本上（統計上叫 range restriction ＋ collider bias，
  偏誤方向**不可預測**——不是「偏高」或「偏低」，是不知道往哪偏）
- **畫面上完全沒有提示**

**為什麼現在不做**：**你已經裁定了修法**（2026-08-31），但那個修法**不小**——

1. 正例、反例各自獨立條件，**絕不共用**
2. 篩選**不再兼差推導答案窗深度**，改成直接問你「哪個 timeframe 的第幾根 bar 用來區分正反例」
3. purge（切分時要隔開的距離）＝ 正反例深度**取大者**

第 2 點是關鍵：現在的深度是**從條件反推**出來的，而我自己記錄過**四種反推不出來**的情形。
這等於要重做匯出流程的一段規格，不是補一個 if。

**接下來怎麼處理**：這是**下一張票**，不是這張票的殘留。要做的時候：
先重開 `/search` 匯出段的規格（正反例雙條件 ＋ 深度改為明問），再走完整流程。
**在那之前，如果你的篩選條件引用了 `future_*` 欄，那批事件的 IC 不要當真。**

# 二、你**看得到**的四條殘留

這四條不影響正確性，但你在畫面上會遇到，先講清楚免得你以為是壞掉。

## 1. `B5-SINGLECLASS-1` 隨機對照批「全是 0」會被擋下來

**是什麼**：產隨機對照批時，如果抽出來那批的答案**全部都是 0**（或全部是 1），
匯入會被拒絕，理由是 `missing_control_group`。

**為什麼會遇到**：你的事件**越罕見**，隨機抽一批的正例率就越低——低到 0 是很正常的。
而那正是最需要看 lift 的時候（「隨便挑 0%、我挑的 25%」才是強訊號）。

**為什麼現在不做**：`missing_control_group` 這條規則的原意是「**使用者標註**的一批要有正反例」。
隨機對照批算不算例外，**沒有人裁定過**。我可以直接放寬它，但那是**弱化一個既有的檢查**
——這種事我不自己決定。

**接下來怎麼處理**：**要你或委員會裁一句**：「無條件抽樣批是否豁免 `missing_control_group`」。
裁完我改一行。在那之前，如果你撞到，把想抽的筆數調大或把門檻調低就會過。

## 2. `B4-TIMEOUT-1` 掃描網格的兩個逾時秒數**是我判斷的，不是量出來的**

**是什麼**：k/h 掃描網格有兩道保護——單格 60 秒、整體 900 秒逾時。

**為什麼要講**：benchmark 我只量到**五階段**（單格 6.9 毫秒），
**沒有量到每格的條件 IC**（真正貴的那段）。所以我**不能**說「60 秒足以吸收合理的單格 IC」
——那句話沒有數據支撐。現在那兩個數字是**保守的上限**，作用是讓卡死的格子一分鐘內被切掉。

**為什麼現在不做**：要量它得先有一個**已物化的 feature run**，在上面跑含 `analyzer.analyze`
的單格 p50/p95/p99。那是一次獨立的量測工作。

**接下來怎麼處理**：等你實際跑一次大網格。如果你發現正常的格子被逾時切掉，
那就是這個數字太小，告訴我，我拿你那次的實測值去凍結它。

## 3. `B4-ORPHAN-WORKER-1` 逾時的格子**不會真的停下來**

**是什麼**：單格逾時後，畫面會標它 unavailable、其餘格子照常，
但**那個工作其實還在背景跑**，會佔 CPU 到它自然結束。

**為什麼現在不做**：Python **沒辦法從外面殺掉一個執行緒**（`asyncio.wait_for` 只取消等待，
不取消工作本身）。真正的修法是把單格改成**子行程**——那是另一個設計題，會動到整個掃描的架構。

**接下來怎麼處理**：短期沒有動作。如果你掃大網格時感覺機器變慢，這就是原因。
真要修得排一張「掃描改子行程」的票。

## 3b. `B4-FACTORY-COST-1` 掃描網格有一段**固定開銷**（110 格約 2.8 秒）

**是什麼**：掃描網格的每一格都會**自己建一個分析器**。codex 實測：建 110 次共 **2.835 秒**
（每次 25.8 毫秒），其中 **2.216 秒**花在重讀 YAML 設定檔上（每格都重讀一次）。

**為什麼不直接快取分析器**：因為那會**讓第一輪那個嚴重問題復活**——
分析器帶著可變狀態，格與格之間共用就會互相污染（逾時的格子會改到別格正在用的東西，
而算出來的數字仍然合法、不會報錯）。

**為什麼現在不做**：兩個原因。①**沒有已批准的時間門檻**可以據以判斷「2.8 秒算不算高」
——那要先量到含條件 IC 的整格成本，也就是上面那條 `B4-TIMEOUT-1`。
②可行的方向是只快取「**已驗證過的設定**」（用檔案路徑／修改時間／契約版本當 key），
分析器本身每格照樣新建——那是一個獨立的設計題，不是順手改。

**接下來怎麼處理**：跟 `B4-TIMEOUT-1` **綁在一起**評估。等你實際跑一次大網格，
如果覺得慢，兩條一起量、一起修。

## 4. `G3-R9` 事件模式的「辨別表」顯示「沒有模型分數」

**是什麼**：`/ic-analysis` 事件模式的辨別表會顯示
`not_computed：no_model_scores_in_event_pipeline`，而不是數字。

**為什麼現在不做**：那張表要的是**模型對每個事件打的分數**，
而分數來自 ML 層／pattern 橋——**那一層在你的成熟度地圖裡標的是「不完整」**。
匯入管線本身不產生分數，沒有東西可餵。

**接下來怎麼處理**：等 ML 層那條線做起來。**畫面已經誠實寫出原因**，不是靜默空白。
`/pending-features` 頁面有它的占位卡。

**接下來怎麼處理**：**下次因為別的原因重開那份規格時，順手把這三條寫回去。**
這不是拖延——它們的行為已經對了、已經有測試守著、理由已經寫在契約檔的註解裡。
