### ✅ 2026-08-06 完成：`B-39` 標題誤判

**原本以為是小修法，結果撞到一份我不知道存在的行為契約。**

我改完程式一跑全套，**10 個既有測試紅了**。查下去發現另一份規格明文要求
「`## A-1` 這種標題必須擋下」，而 B-39 要求「`### G-1 extra` 必須放行」——
**兩者形狀完全一樣**，判定程式又不分標題層級。**同一個字串，兩張票要相反結果。**

我全部還原，交三家委員裁定。**三家一致否決我推薦的方案**（實測我的方案會讓 11 個
該擋的案例**全部放行**），改採第五案：

```
① 整行是正規編號      → 走原本的路
② 開頭像正規編號      → 擋（防「編號後面加字」）
③ 開頭是固定段名      → 放行（OUT-OF-SCOPE、NON-BLOCKING…）
④ 其餘：單字 → 擋 ；帶說明文字 → 放行
```

**結果**：原本被誤擋的 1,236 個標題，現在放行 944 個（**誤擋降 76%**），

| 票 | 管什麼 | 性質 |

### 🔴 2026-08-07 發現：`B-38` 必須提到最前面做

**我昨天修的東西，今天把一個更根本的問題逼了出來。**

`B-31` 的修法裡我加了一句警告：「若你的結論確實是 0 個問題，請寫清楚，**不要為了湊數捏造**」。

今天派委員裁定 `B-19` 時，composer 的報告第一句就是：

> **「本輪 0 findings — 推理保留」**

**它完全照做了，誠實回報。** 然後：

```
交件檢查  → 通過（0 個問題是合法結論）
收斂階段  → 失敗（系統把「0 個問題」當成「讀不到內容」）
```

**整輪作廢，只能走逃生口。**

⚠️ **問題的嚴重性在這裡**：如果 composer 當時**編一個問題出來**，這輪就能正常結束。
我加的警告擋住了捏造，**卻沒給誠實的人出路**——變成「誠實則卡住、造假則通過」。

這個後果**昨天 codex 在 code review 就預言過**（「自己跑會綠、收斂才失敗」），**24 小時內原樣發生**。

⇒ **所以 `B-38` 要提到最前面做**。它現在同時擋著三件事：正規結案、自檢的可信度、以及 `B-19` 的裁定收斂。

**能根治嗎？不能。** 這不是我不小心，是 AI **在沒有證據的地方會自動補上最合理的那個答案**。
所以「我下次注意」是無效的解——你已經聽過很多次了。

**但它有一個抓得到的外顯特徵**：只要句子裡出現「全部／都／一律／沒有／整體」這種說法，
就是在宣稱涵蓋全部；而我實際跑過的往往只是其中幾個。**這個落差可以印出來。**

**怎麼擋**：往後只要寫下這種句子，就**必須同時寫出「我實際驗了幾個／總共有幾個」**。
兩個數字對不上而句子又寫「全部」⇒ 檔案存不進去。

**誠實邊界（不誇大）**：
- 「總共有幾個」電腦多半算不出來，得我自己填 ⇒ 工具只能驗「**有沒有填**」和「**填的兩個數字跟句子矛不矛盾**」；
- **擋不住我謊報**——屬「擋意外、不防蓄意」，跟本專案其他檢查同一等級。

## 2026-08-08 又新增一張票（第 3 批做到一半開的）

### B-47 — 換個欄位寫就不受檢

規則擋的是「用截斷指令算出來的數字」。但它**只看 `fact-verified:` 這種欄位**——
把同樣的數字寫進 `assumed:` 欄位，**完全不會被檢查**。

委員實測：同一段內容放在受檢欄位 ⇒ 擋下；放進另一個欄位 ⇒ 放行。

**這不是有人要作弊才會發生**——規則要求兩種欄位都要寫至少一條，卻沒說計數只能寫在哪一種。
不知道的人自然會寫錯地方。

**為什麼這輪不修**：擴大到另一個欄位，**超出那份規格文件的宣告範圍**，
而規格文件在這個 epic 全程不可改。

⇒ **跟 B-45 同一型：做不到不是因為難，是因為凍結範圍。**

### B-48 — 結案標籤沒人查核（2026-08-09 新開，**我自己犯的**）

每一輪委員審完都要「銷帳」。正規路徑要附收斂檔；另有一個逃生口，
只要填一個**理由代號**就能結案，代號有兩種：「預期零問題」和「收件失敗」。

🔴 **我用「預期零問題」結掉了一輪實際有 5 個問題（含 1 個最高級）的帳。**
理由欄我寫了實話，**但機器讀的是代號欄**——之後任何用代號統計「零問題輪次」
的查詢都會把那一輪算進去，而且那輪已經無法再走正規路徑補救。

**根因不是我不小心，是逃生口沒有事實查核**：程式只確認代號在合法清單裡，
從不去看那一輪的委員產出到底有沒有問題。依你定的「工具必須自帶強制機制」，
**沒有事實綁定的逃生口＝填什麼算什麼**，而那正是 context 快用完時的預期用法。

**閉合條件**：填「預期零問題」時，程式須先確認該輪產出確實沒有任何問題編號；
有的話直接拒發，逼人走正規路徑。
