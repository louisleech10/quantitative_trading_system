## 一、一句話

**你設一個條件，系統在 K 線上找出所有符合的時點，算「從那時買入、持有 N 根之後賺多少」，再跟「隨機挑同樣多的時點、持有同樣久」比。**

---

## 二、名詞對照（後面會一直用）

| 白話 | 系統裡的說法 | 意思 |
|---|---|---|
| 根 | bar | 一根 K 線。1h run 一根＝1 小時，12h run 一根＝12 小時 |
| 觸發點 | 事件 / event，時間點叫 `t0` | 條件成立的那一根 |
| 觸發批 | 事件批 / event batch | 一次掃描找出的所有觸發點，打包成一批 |
| 對照批 | 隨機對照批 / random control batch | 隨機挑的時點，用來當「不挑時機」的基準 |
| 持有期 | horizon（`h`） | 買入後持有幾根。可以一次看好幾個（你要的複選） |
| 答案欄 | `label`（0 或 1） | 這次「算不算成功」。**你不用填，系統自己算** |
| 算好的特徵 | FF run / Feature Factory run | 事先算好的所有指標（EMA、RSI、MACD…），存在檔案裡 |

### 第 6 步：兩批各自算報酬，並排給你看

報酬公式（實查 `momentum/Analysis/event_samples/tables.py`）：

```
報酬 = (出場那根的收盤價 − 進場價) / 進場價
```

做空會反號。資料不夠長的事件（例如最後 55 根之內的觸發點算不出 55 根報酬）**直接排除，不會灌 0 拉低平均**。

🔴 **進場價用哪一根、哪個價——這一條交委員會，還沒定案。**

**你的想法**（2026-09-20）：用條件成立那根的**下一根開盤價**（系統裡叫 `next_open`）。
你同時聲明：這只是想法，沒深入評估是否有風險、統計數據或量化金融計算上的誤區。

**我查到的現況**：`next_open` 系統已經支援——實查 `momentum/Analysis/event_samples/alignment.py:102-106`，
取 `t0_idx + 1` 那根的 `open`，資料不夠（t0 是最後一根）就標 `missing_bar` 排除。
五個可選值為 `trigger_open`／`trigger_close`／`next_open`／`decision_bar_open`／`decision_bar_close`。

**我為什麼覺得你的直覺有道理**：條件要用到 t0 那根的收盤價才算得出來（EMA 是收盤價算的）。
如果進場價用 t0 的收盤價，等於假設「收盤瞬間同時算完指標並成交」。
用下一根的開盤價比較接近真的買得到的價格。

**但這正是要交委員會的原因**——我不是量化金融專家，下面幾件事我沒有能力自己判斷：
跳空風險怎麼處理、不同選擇會不會讓報酬統計產生系統性偏誤、
隨機對照批是否必須用完全相同的進場語意、事件研究的標準做法是什麼。
**這一條在委員會給出結論前不算定案。**

## 四、現在有什麼、缺什麼

### 已經有的（不用重做）

| 零件 | 狀態 |
|---|---|
| 條件掃描產事件批的函式 | ✅ `generate_events` 已存在，能跑，過同一個驗證器 |
| label 自動算 | ✅ 已在上述函式內 |
| 算持有 N 根報酬 | ✅ `event_forward_return_table`，N 可指定任意一組，**不寫死** |
| 不開 IC 也能算報酬 | ✅ 報酬表跟 IC 的答案窗**沒綁在一起**（實查） |
| 產生隨機對照批 | ✅ 已有端點，會避開觸發點，種子可重現 |
| 讀取算好的特徵 | ✅ `FeatureLibrary.load` 能依「標的／週期／識別碼」讀出整張特徵表 |
| 對一張表求條件 | ✅ `parse_condition` ＋ `evaluate_condition` |

### 缺的四塊

| # | 缺口 | 白話 |
|---|---|---|
| 1 | **掃描函式沒有 API 接口** | 函式在，但 `api/` 裡**零個呼叫者**——前端根本碰不到它 |
| 2 | **條件讀不到 FF 欄位** | 「讀特徵表」和「求條件」兩端都有，**中間沒接**：沒有任何程式把 FF 的欄位名註冊給條件引擎。🔴 **而且現在寫錯欄名不會報錯**——找不到該欄時條件直接判「不成立」，你會得到「零筆命中」而不是錯誤訊息（codex 查出）。這條必須在規格裡改成**報錯**，否則你永遠分不清「條件真的沒成立」和「欄名打錯」 |
| 3 | **比較比的是達標率，不是報酬** | 現有比較端點回「觸發批裡 label=1 佔幾成 vs 隨機批佔幾成」，不是平均報酬。而且它**常常是灰的**——它要求觸發批帶「標籤規則收據」（`label_rule`），一般匯入沒有，就回「無從確認兩批用同一條規則」而不並排 |
| 4 | **隨機抽樣現在不公平** | 見下表 |
| 5 | **統計欄位差兩個** | 現成的有筆數／平均／中位數／勝率／信賴區間；**標準差**與**最好／最差**沒有，要加（實查 `tables.py:118-131`） |
| 6 | **沒有欄位選擇器** | 這個 run 有 18 萬個以上欄名，後端能回清單但前端只能拿到一整包平鋪的。**沒有逐層下拉＋搜尋，你寫不出條件** |

#### 缺口 4 細項（四項都要修）

| 項 | 現況（實查） | 應該是 |
|---|---|---|
| 抽幾筆 | 前端預設 100 筆，**不跟著觸發批** | 跟觸發批同筆數 |
| 候選資格 | 只看**單一**答案窗長度 | 看你選的**最長**持有期 |
| 樣本之間 | 只禁抽到同一根，**不禁答案窗互相重疊** | 應互斥 |
| 期間池 | 取自觸發批最早～最晚的 `t0` | 應為整個 run 的期間 |

## 五、做法：七步

1. **條件引擎吃 FF 欄位**——把讀到的特徵表欄位名註冊給條件引擎，讓你能寫 `close_1h_trend_EMA_5 > close_1h_trend_EMA_10`。**並且欄名打錯要報錯，不能靜默回零命中**
2. **欄位選擇器**——逐層下拉（來源欄→週期→類別→指標→參數）＋打字搜尋。**沒有這個你根本沒辦法從 18 萬個欄名裡挑出要的**
3. **掃描函式接上 API**——條件 → 事件批 → 匯入（`label` 用漲跌正負號填，進場價用 `next_open`）
4. **報酬表補兩個統計量**——加上**標準差**與**最好／最差**
5. **產隨機對照批**——走既有端點，**修掉缺口 4 的四項**
6. **比較端點改成比報酬**——現在只讀 label 算達標率，要改成讀報酬表並排全部統計量
7. **前端**——掃描設定畫面（持有期**直接輸入**、即時顯示約幾天）＋ 兩組統計並排的表（現在沒有並排元件）
