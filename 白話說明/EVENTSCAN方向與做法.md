## 一、一句話

**你設一個條件，系統在 K 線上找出所有符合的時點，算「從那時買入、持有 N 根之後賺多少」，再跟「隨機挑同樣多的時點、持有同樣久」比。**

---

## 二、名詞對照（後面會一直用）

| 白話 | 系統裡的說法 | 意思 |
|---|---|---|
| 根 | bar | 一根 K 線。1h run 一根＝1 小時，12h run 一根＝12 小時 |
| 觸發點 | 事件 / event，時間點叫 `t0` | 條件成立的那一根 |
| 觸發批 | 事件批 / event batch | 一次掃描找出的所有觸發點，打包成一批 |
| 對照批 | 隨機對照批 / random control batch | 隨機挑的時點，用來當「不挑時機」的基準 |
| 持有期 | horizon（`h`） | 買入後持有幾根。可以一次看好幾個（你要的複選） |
| 答案欄 | `label`（0 或 1） | 這次「算不算成功」。**你不用填，系統自己算** |
| 算好的特徵 | FF run / Feature Factory run | 事先算好的所有指標（EMA、RSI、MACD…），存在檔案裡 |

**所以畫面要這樣做**（這是本票要新做的東西）：

1. **逐層下拉**：選來源欄 → 選週期 → 選類別 → 選指標 → 選參數。每一層只有幾個到幾十個選項，

2. **打字搜尋**：想直接打 `EMA` 就跳出所有含 EMA 的欄位，選一個貼進去。
3. **打錯要報錯**：現在系統找不到欄位時**直接判「條件不成立」**，你會看到「零筆命中」而不是錯誤訊息
   （缺口 2）。本票會改成明確報錯並告訴你最接近的欄名。

**現況**：後端已經有 `GET /api/v1/ic/features/list`（給 標的＋週期＋run識別碼，回該 run 的全部欄名），
前端也有呼叫它的程式（`fetchAvailableFeatures`）。**缺的是上面這三件事**——現在只能拿到一整包平鋪清單。

### 第 2 步：你輸入持有期

你 2026-09-20 裁定：**用「根」計算，但畫面要顯示大約幾天；而且要支援複選**。

所以畫面會長這樣（示意）：

```
持有期（直接輸入，逗號分隔，要幾個都行）
  ┌─────────────────────────────┐
  │ 5, 10, 30, 55               │
  └─────────────────────────────┘
  → 5 根 ≈ 5 小時 ｜ 10 根 ≈ 10 小時 ｜ 30 根 ≈ 1.3 天 ｜ 55 根 ≈ 2.3 天
```

**不是勾選清單**（你 2026-09-20 裁定）：直接打字輸入，想看幾個就打幾個，不受預設選項限制。
你一邊打，底下就即時顯示每個數字大約是多久。

換算由系統算：`根數 × 週期長度`。同樣打 55，在 12h run 上會顯示「≈ 27.5 天」。

### 第 3 步：系統掃描

在 20,352 根裡逐根求值你的條件，找出所有成立的根。

🔴 **但不是每根都算一筆**（委員會 2026-09-20 裁定，見 7-4）。

多頭排列一旦成立，通常會**連續維持好幾十根**。如果每根都算一筆「買入持有 N 根」，
**340 筆可能其實只是 10 段趨勢**，你會以為有 340 次獨立買賣。

所以：**每一段連續成立只算一次進場**（進場點＝那段的第一根）。

假設壓縮後得到 **340 筆**（示意）。「每根都算」的版本保留為參考表，但不當主數字。

### 第 4 步：系統填 `label`（你不用做任何事，也不會被問任何門檻）

🔴 **你 2026-09-20 裁定：完全不要門檻，也不會給。** 這一步照你的裁定設計。

匯入契約**強制**每筆要有 `label`（0 或 1），而且一批裡必須兩類都有——這是硬的，
實查 `momentum/Analysis/contracts/event_import_contract.json` 的 `required_fields`，繞不過去。

所以 `label` 用**漲跌的正負號**填，**綁你輸入的最長持有期**（見 7-11）：

- 持有最長那個期間後，報酬 > 0 → `label = 1`
- 報酬 ≤ 0 → `label = 0`

**這不是門檻，是漲跌的定義。** 沒有任何數字要你設定，畫面上也不會出現門檻欄位。

**為什麼綁最長的**：`label` 會決定「隔離區寬度」和「隨機對照的候選資格」，
這兩者必須夠寬到涵蓋你要看的最長持有期。綁 5 而你在看 55，那 55 那一列的防護只有 5 根寬。

🔴 **誠實講**：這個 `label` 對你要的統計數據**一點貢獻都沒有**（勝率是另外從報酬直接算的，見第 6 步），
而且**你輸入的每一個持有期都會有完整的一列統計，不是只算綁 `label` 的那個**（見 7-11）。
它純粹是匯入契約的形式要求，你在畫面上完全不會看到它。

> **如果你連這個內部欄位都不想要**，另一條路是完全不走事件匯入、另建一條掃描→報酬統計的路徑。
> 你看到的數字會一模一樣，但**既有的未來資料防護、時點對齊檢查全部用不到**，等於一條沒護網的平行路。
> 我不建議，但這是你的選擇。

### 第 5 步：系統產一批隨機對照

隨機挑 **340 根**（跟觸發批**同樣多**），規則：

- 避開觸發點附近（前後各留緩衝，免得對照組其實也在條件成立的區間裡）
- 同一個標的、同一個週期
- **只從有觸發點的那些月份裡挑**，而且**名額按每月觸發筆數分配**（委員會 2026-09-20 裁定，見 7-6）
- **進場語意、出場錨、持有期集合由觸發批帶入**——不能各自取預設值（見 7-2 之阻斷性缺陷）
- 樣本彼此的持有期**不重疊**；排不下就**回報「無法比較」**，不偷偷把數量縮小（見 7-7）
- 亂數種子固定 → 同樣的設定重跑會得到**一模一樣**的結果

### 第 6 步：兩批各自算報酬，並排給你看

報酬公式（實查 `momentum/Analysis/event_samples/tables.py`）：

```
報酬 = (出場那根的收盤價 − 進場價) / 進場價
```

做空會反號。資料不夠長的事件（例如最後 55 根之內的觸發點算不出 55 根報酬）**直接排除，不會灌 0 拉低平均**。

✅ **進場價＝條件成立那根的「下一根開盤價」**（`next_open`）——你的提議，**委員會兩家已確認正確**。

**現況**：系統已支援——實查 `momentum/Analysis/event_samples/alignment.py:102-106`，
取 `t0_idx + 1` 那根的 `open`，資料不夠（t0 是最後一根）就標 `missing_bar` 排除。
五個可選值為 `trigger_open`／`trigger_close`／`next_open`／`decision_bar_open`／`decision_bar_close`。

**為什麼是對的**：條件要用到 t0 那根的收盤價才算得出來（EMA 是收盤價算的）。
如果進場價用 t0 的收盤價，等於假設「收盤瞬間同時算完指標並成交」——做不到。

🔴 **但我原本的理由講反了**（委員會更正，見 7-1）：我寫「跳空成本由 `next_open` 自然承擔」是錯的。
`next_open` 的損益**不包含** t0 收盤→次根開盤那一段；是 `trigger_close` 把它算進去了。
⇒ **有樂觀偏誤的是 `trigger_close`**，不是 `next_open` 多付成本。

系統另有並列口徑 `ret_label_anchor`（一律以 t0 收盤價為基準）。
**主欄用 `ret_entry`**（可成交的那個），`ret_label_anchor` 當診斷、**不拿來跟隨機批相減**。
**兩批一律用同一個口徑且畫面標明**，否則各用一個去比會失真。

你要的是「**統計數據**」，不只是一個平均值。所以每個持有期都給這幾個（示意數字，非實測）。

🔴 **你輸入的每一個持有期都是完整的一列**——不是只算綁 `label` 的那一個（見 7-11）。
🔴 **只有「全體」一組**——委員會 2026-09-20 裁定：不得顯示「正例組／反例組」，那在本票的 `label` 定義下是套套邏輯（見 7-2）。
🔴 **筆數是「每段連續成立算一次」**，不是每根都算（見 7-4）。

🔴 **上一版我寫「勝率是 `label` 加總得來的」——那是錯的，我查了程式才發現。**
勝率是直接從報酬的正負算的，跟 `label` 無關。

**這件事讓 `label` 的定位更清楚了**：它對你要的統計數據**一點貢獻都沒有**，純粹是匯入契約的形式要求。
你看到的每一個數字都是從報酬直接算出來的。

- **筆數會隨持有期變少**（340→335），因為資料尾端算不出長持有期的報酬，那些事件**直接排除不灌 0**
- **為什麼要中位數和標準差**：平均值會被少數極端值拉走。中位數告訴你「典型情況」，標準差告訴你「有多不穩」——只看平均會誤判

### 7-2 🔴 `label` 的問題比我以為的嚴重——它會出現在主表

**我原本判斷「`label` 不會進到你看得到的數字」，兩家都說錯了。**

**處置**：**主表只顯示全體一組**，正例／反例分組在本票不顯示。`label` 只活在匯入契約裡。

### 7-3 🔴「持有 N 根」現在有兩套時鐘（我完全沒想到）

|---|---|

| 全 K 線表 | t0 + 5 |

更糟的是：同一個事件可能在報酬表顯示**正報酬**、卻被標成 `label=0`。

### 7-4 🔴 均線條件會連續好幾根都成立（我完全沒想到）

**處置**：主要數字用「**每一段連續成立只進場一次**」（first-of-run）。每根都算的版本保留為參考，但不當主數字。

### 7-5 「差 +0.72%」是真的還是運氣？現在答不出來（推翻我）

**問題長這樣**：表上寫「觸發批平均 +1.05%、隨機批 +0.33%、**差 +0.72%**」。

那 **+0.72% 到底是這條規則真的有效，還是剛好抽到好樣本？** 這是你看完表最該問的問題。

一般統計用**信賴區間**回答：「差是 +0.72%，區間 [+0.31%, +1.13%]，不含 0 ⇒ 大概不是運氣」。
但**這條路現在算不出這個區間**，兩個原因：

**原因一（技術性的）**：系統算區間需要先做「切分」這個前置步驟，而事件掃描這條路**沒有做切分** ⇒ 系統直接標「無法提供」。

**原因二（比較根本的）**：你的 340 筆**不是 340 個獨立樣本**。

> 多頭排列連續成立時，第 100 根和第 101 根的「持有 30 根報酬」
> 有 29 根是**重疊的同一段價格**。它們幾乎是同一筆交易，不是兩次獨立的下注。

如果拿「340 個獨立樣本」的公式去算區間，**算出來會太窄**——讓你以為「很確定有效」，其實資訊量遠沒有 340 筆那麼多。

**還有一個常見的誤用**：有人會分別畫觸發批和隨機批各自的區間，看它們重不重疊。**這不能回答「差是不是 0」**——兩個區間重疊，差仍可能顯著；不重疊，也不保證顯著。要看的是**「差」本身的區間**。

**處置**：用 bootstrap（把資料重複重抽幾百次、每次重算一遍差、看這些差分布在哪）算出「差」的區間，而且**重抽的單位要是「一整段連續成立」而不是「一根」**，這樣才不會把重疊當成獨立。

**在做出來之前**，表上方會有一條硬性橫幅：

> 「**無信賴區間；平均差為正不得讀成這條規則會賺。**」

### 7-6 隨機對照要從「哪段時間」裡挑？（我自我推翻是對的，但還不夠）

**問題長這樣**：要挑 340 根隨機的 K 線當對照，從哪段時間裡挑？

**如果從整個 run 挑**（2024-01 到 2026-04，兩年多）：

> 假設你的條件剛好都在 2024 年那波多頭成立。那你比的是
> 「**2024 多頭的報酬** vs **兩年平均的報酬**」——
> 差異來自**行情**，不是來自你的條件。條件根本沒被驗證到。

所以要**從有觸發點的那些月份裡挑**，這樣兩邊在同一種行情下比。我先前寫「該用整個 run」是錯的，自己推翻掉。

**但還不夠**，委員又抓到一層：

> 現在系統分配名額是按「**每個月有多少根可以挑**」，不是按「**每個月有幾個觸發點**」。
>
> 假設觸發點 80% 集中在 1 月，但 1、2、3 月的 K 線數量差不多 ⇒
> 隨機批還是會**平均分到三個月**。結果又變成「以 1 月為主 vs 三個月平均」，
> 同一個毛病換個形式又出現。

**三條機械規則**：

1. 期間池＝**有觸發點的那些月份**（UTC）的聯集
2. 名額按**觸發筆數**分：1 月有 80% 觸發，1 月就抽 80% 的對照。某月候選不夠就**直接回報失敗**，不把缺額倒到別的月充數
3. 「整個 run」那版只能當**另一張參考表**，標題要寫清楚它回答的是不同的問題（「這個條件是不是只是選到了好行情」）

### 7-7 抽樣不足時不准偷偷縮水（推翻我的措辭）

現行最危險的是：候選不夠時會**靜默把 n 縮小**（`n_target = min(n_requested, candidate_count)`）——**估計量被換掉了，畫面看起來卻像成功**。

**處置**（採較嚴的版本）：不縮 n、不放寬互斥、不抽相鄰根充數。互斥排下來不夠就**回報「無法比較」**並列出四個計數，讓你知道為什麼。

### 7-9 手續費與滑點要不要算？（你 2026-09-20 提問）

**業界做法分三層，答案不一樣**：

| 算什麼 | 扣不扣成本 | 為什麼 |
|---|---|---|
| **IC 本身** | **不扣**（業界標準） | IC 是「因子值 vs 未來報酬」的相關係數，衡量**排序能力**。成本發生在**換倉**，不發生在「某個時點的相關性」上——扣了沒有明確定義 |
| **淨 IC（net IC）** | 扣 | 進階診斷：扣掉換手成本後因子還有沒有效。**不是 IC 的標準定義**，是額外一層 |
| **事件研究的報酬** | 學術通常不扣 | 它要衡量的是「資訊效應」，所以報未扣成本的異常報酬。但實務要判斷「能不能真的賺」就得扣 |
| **回測** | **一定扣** | 它宣稱的就是「這樣做會賺多少」，不扣就是假的 |

**本專案現況**（實查 `momentum/Analysis/net_ic_analyzer.py`）：

- 已有淨 IC，公式＝`淨值 = 毛值 − (成本bps ÷ 10000) × 換手率`
- **預設關閉**（`cost_enabled = False`）
- 🔴 裡面有一個設計比「扣成本」更有用：**`breakeven_cost_bps`**

**`breakeven_cost_bps` 是什麼**：它不要你猜費率，而是**反過來告訴你「成本要高到多少，這個獲利才會被吃光」**。

> 例：它回 `3.2`，而幣安吃單費約 5 bps ⇒ 你當場就知道
> **這條規則扣完手續費就沒了**，完全不必去設定任何費率。

**我對 EVENTSCAN 的建議**：

1. **主數字報未扣成本**（跟事件研究慣例一致，也跟委員建議一致）
2. **但加一欄 breakeven**：這批事件的平均報酬，在多少 bps 成本下會歸零
3. **不在本票發明費率**——我不知道你用哪家交易所、什麼手續費等級、吃單還是掛單

理由：讓你猜一個費率再扣，猜錯了整張表就是錯的；breakeven 反過來給你一個**不需要假設**的判準。

**委員另外提醒的三項成本**（算不進報酬公式，只能揭露）：
開盤第一筆成交價 ≠ 你真的買得到的均價、永續合約的資金費、滑價。

**這些我會在寫規格時逐條處理**，不需要你現在決定——但其中兩條我要先講，因為它們影響你怎麼讀數字：

- **換 EMA 組合試到有效果 = 沒有意義**。畫面會寫「這是同一段樣本上的描述，不是驗證過的策略」。

### 7-11 🔴「輸入多個持有期但 `label` 只綁一個，其他不就白輸入了？」（你 2026-09-20 提問）

**不是白輸入。這是我上一版沒講清楚，現在補上。**

**報酬表對你輸入的每一個持有期，都算一整列完整統計**——平均／中位數／勝率／標準差／最好／最差／成本歸零點。
輸入 `5, 10, 30, 55` 就是**四列，每列都完整**。

🔴 **`label` 綁哪個持有期，不影響這四列的任何數字**——實查 `momentum/Analysis/event_samples/tables.py:118-131`，
算這些統計的函式（`_weighted_stats`）**根本不讀 `label`**。

**那 `label` 到底影響什麼？三件你看不到的事**：

| # | 影響 | 說明 |
|---|---|---|
| 1 | 通過匯入契約 | 純形式要求，契約規定每筆必須有 0 或 1 |
| 2 | **隔離區寬度** | 防止未來資料洩漏的緩衝帶，寬度由它決定（實查 `ic_filter_orchestrator.py:1211`：`label_window_rows` 抬 purge） |
| 3 | **隨機對照的候選資格** | 哪些 K 線有足夠的後續資料可以當對照 |

**所以這題有唯一正確答案，不需要你選：綁「最長的那個」。**

理由是第 2、3 點——**隔離區和候選資格必須夠寬到涵蓋你要看的最長持有期**。
若綁 5 而你在看 55，那 55 那一列的防護只有 5 根寬，**不夠**；綁 55 則四列都安全。
這也正是委員說的「候選資格應該用 `max(持有期)`」。

### 7-12 breakeven 現在在哪？三條路都能用嗎？（你 2026-09-20 提問）

| 路徑 | 現況（實查） |
|---|---|
| **全域序列型 IC** | ✅ **有，且前端已在顯示**。`frontend/src/components/ic-analysis/NetICChart.tsx` 掛在 `/ic-analysis`，三個鍵 `breakeven_cost_bps`／`profitable_after_cost`／`net_factor_return`。但**預設關閉**（`cost_enabled = False`） |

#### 事件型「沒有 breakeven」是不能做，還是沒做？（你 2026-09-20 追問）

**是「沒做」，不是「不能做」。** 卡住的原因很具體：

現行公式需要**兩樣**東西：

```
淨值 = 毛值 − (成本bps ÷ 10000) × 換手率
                                    ↑
                     turnover = position.diff().abs()
```

`換手率` 是從 **`position` 這條連續序列**算出來的——「這期持有多少、下期持有多少、差多少就是換手」。
這條序列由 `FactorTimingReturnSeries` 提供（實查 `momentum/Analysis/factor_return_analyzer.py:20`，
註解逐字「單標的因子擇時多空序列」）。

🔴 **而事件型沒有這條連續序列**。事件型只在**事件發生的那些時點**有因子值，
中間是空的、不連續、間隔不規則——`position.diff()` 在稀疏不規則的點上**沒有定義**。

所以現況是：`_run_net_ic` 去 `self._factor_return_series` 拿資料，事件路徑那裡是空的 ⇒ 回 `unavailable`。

**但概念上完全成立，而且比序列型更簡單**：

| | 全域序列型 | 事件型 |
|---|---|---|
| 交易長怎樣 | 每期調倉，換手率是連續變動的量 | **一次進場、一次出場，一趟來回** |
| 成本怎麼算 | `成本 × 換手率`（要先算換手率） | `成本 × 2 腿`（固定） |
| 成本歸零點 | `毛報酬 ÷ 換手率` | **`平均報酬 × 10000 ÷ 2`** |

事件型**不需要「換手率」這個中間量**——每筆交易的換手是確定的，所以公式反而更直接。

⇒ **不是做不到，是現有公式的前提（連續持倉序列）在事件型上不存在**，需要一條專屬事件的公式。
本票會做出來（做法第 10 步）。**做出來之後，事件型 IC 也能直接用同一條**——
它跟本票一樣是「一個事件一趟來回」的結構。
