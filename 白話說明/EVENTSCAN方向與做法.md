> **這份是給你看的方向說明，不是規格。** 你看過同意，我才去寫規格。

## 一、一句話

**你設一個條件，系統在 K 線上找出所有符合的時點，算「從那時買入、持有 N 根之後賺多少」，再跟「隨機挑同樣多的時點、持有同樣久」比。**

---

## 二、名詞對照（後面會一直用）

| 白話 | 系統裡的說法 | 意思 |
|---|---|---|
| 根 | bar | 一根 K 線。1h run 一根＝1 小時，12h run 一根＝12 小時 |
| 觸發點 | 事件 / event，時間點叫 `t0` | 條件成立的那一根 |
| 觸發批 | 事件批 / event batch | 一次掃描找出的所有觸發點，打包成一批 |
| 對照批 | 隨機對照批 / random control batch | 隨機挑的時點，用來當「不挑時機」的基準 |
| 持有期 | horizon（`h`） | 買入後持有幾根。可以一次看好幾個（你要的複選） |
| 答案欄 | `label`（0 或 1） | 這次「算不算成功」。**你不用填，系統自己算** |
| 算好的特徵 | FF run / Feature Factory run | 事先算好的所有指標（EMA、RSI、MACD…），存在檔案裡 |

## 三、從頭到尾走一遍（完整舉例）

### 第 0 步：你選一個算好的資料

系統裡**現有 14 個可用的 FF run**（實查 `data_cache/features/registry.json`）。舉其中一個：

| 項目 | 值（實查） |
|---|---|
| 標的 | `ETHUSDT` |
| 週期 | `1h`（一根＝1 小時） |
| 識別碼 | `4a8a0b3726cc906ab3534994605e77f5` |
| 期間 | 2024-01-01 00:00 ～ 2026-04-27 23:00（UTC） |
| 有幾根 | 20,352 根 |
| 算好幾個特徵 | 437,066 個 |

🔴 **資料源就是 FF，FF 有什麼就用什麼**（你 2026-09-20 裁定）。系統不會自己再算任何指標。

### 第 1 步：你寫一個條件

**你原本舉的 `EMA5 > EMA10 > EMA30` 不能直接用——因為這個 run 裡沒有 EMA_30。**

實查這個 run 的 EMA 週期，有這 14 個：

```
5, 8, 10, 13, 20, 21, 34, 50, 55, 89, 100, 144, 200, 233
```

所以你可以寫（例如）：

```
close_1h_trend_EMA_5 > close_1h_trend_EMA_10
  AND close_1h_trend_EMA_10 > close_1h_trend_EMA_34
```

這是「短期均線在中期之上、中期在長期之上」——多頭排列，跟你原本的意思一樣，只是用 34 代替 30。

**其他能用的指標家族**（實查同一份 manifest）：

| 類別 | 有哪些 |
|---|---|
| 均線 | `EMA`、`SMA`、`WMA`、`DEMA`、`TEMA`、`TRIMA`、`KAMA`、`MAMA`、`MAVP`、`MA`、`MIDPOINT`、`BBANDS`（布林帶） |
| 動能 | `RSI`、`MACDFIX`、`MOM`、`ROC`、`ROCP`、`ROCR`、`CMO`、`TRIX`、`PPO`、`APO` |
| 統計 | `LINEARREG`、`STDDEV`、`TSF`、`VAR` |

### 第 2 步：你選持有期（可以複選）

你 2026-09-20 裁定：**用「根」計算，但畫面要顯示大約幾天；而且要支援複選**。

所以畫面會長這樣（示意）：

```
持有期（可複選）
  ☑  5 根   ≈ 5 小時
  ☑ 10 根   ≈ 10 小時
  ☑ 30 根   ≈ 1.3 天
  ☑ 55 根   ≈ 2.3 天
  ☐ 120 根  ≈ 5 天
  [＋自訂]  ___ 根  ≈ __ 天
```

換算由系統算：`根數 × 週期長度`。同樣選 55，在 12h run 上會顯示「≈ 27.5 天」。

### 第 3 步：系統掃描

在 20,352 根裡逐根求值你的條件，找出所有成立的根。

假設找到 **340 根**（示意）。

### 第 4 步：系統自己算 `label`（你不用做任何事）

每個觸發點，系統看「持有之後報酬有沒有過門檻」：

- 過了 → `label = 1`
- 沒過 → `label = 0`

🔴 **這一步是你「不想給反例」能成立的關鍵。**匯入契約規定每批必須同時有 0 和 1（實查 `momentum/Analysis/contracts/event_import_contract.json` 的 `required_fields`），但**那個 0 不需要你提供**——系統從「後來漲沒漲」自動算出來。

### 第 5 步：系統產一批隨機對照

從同一個 run 隨機挑 **340 根**（跟觸發批同樣多），規則：

- 避開觸發點附近（前後各留緩衝，免得對照組其實也在條件成立的區間裡）
- 同一個標的、同一個週期、同一段期間
- 亂數種子固定 → 同樣的設定重跑會得到**一模一樣**的結果

### 第 6 步：兩批各自算報酬，並排給你看

報酬公式（實查 `momentum/Analysis/event_samples/tables.py`）：

```
報酬 = (出場那根的收盤價 − 進場價) / 進場價
```

做空會反號。資料不夠長的事件（例如最後 55 根之內的觸發點算不出 55 根報酬）**直接排除，不會灌 0 拉低平均**。

🔴 **「進場價」有兩種算法，這件事要先講定**（codex 2026-09-20 查出）：

| 口徑 | 進場價是什麼 | 白話 |
|---|---|---|
| `ret_entry` | 依設定的「進場語意」取價（預設＝觸發那根的**收盤價**） | 「條件成立那根收盤時買進」 |
| `ret_label_anchor` | 一律用觸發那根的收盤價當基準 | 固定基準，不隨設定變 |

兩個算出來的平均**都合法，但不是同一件事**。如果不講清楚用哪個，觸發批跟隨機批可能各用一個口徑去比，數字會失真。

**我的建議**：兩批一律用同一個口徑，並在畫面上標出來是哪個。這條要寫進規格鎖死。

畫面（示意數字，非實測）：

| 持有 | 觸發批平均報酬 | 隨機批平均報酬 | 差 | 觸發批筆數 |
|---|---|---|---|---|
| 5 根 ≈ 5 小時 | +0.42% | +0.05% | **+0.37%** | 340 |
| 10 根 ≈ 10 小時 | +0.68% | +0.11% | **+0.57%** | 340 |
| 30 根 ≈ 1.3 天 | +1.05% | +0.33% | **+0.72%** | 338 |
| 55 根 ≈ 2.3 天 | +0.91% | +0.60% | +0.31% | 335 |

（筆數會隨持有期變少，因為資料尾端算不出長持有期的報酬——見上面「直接排除」。）

**這張表就是你要的東西。**

## 四、現在有什麼、缺什麼

### 已經有的（不用重做）

| 零件 | 狀態 |
|---|---|
| 條件掃描產事件批的函式 | ✅ `generate_events` 已存在，能跑，過同一個驗證器 |
| label 自動算 | ✅ 已在上述函式內 |
| 算持有 N 根報酬 | ✅ `event_forward_return_table`，N 可指定任意一組，**不寫死** |
| 不開 IC 也能算報酬 | ✅ 報酬表跟 IC 的答案窗**沒綁在一起**（實查） |
| 產生隨機對照批 | ✅ 已有端點，會避開觸發點，種子可重現 |
| 讀取算好的特徵 | ✅ `FeatureLibrary.load` 能依「標的／週期／識別碼」讀出整張特徵表 |
| 對一張表求條件 | ✅ `parse_condition` ＋ `evaluate_condition` |

### 缺的四塊

| # | 缺口 | 白話 |
|---|---|---|
| 1 | **掃描函式沒有 API 接口** | 函式在，但 `api/` 裡**零個呼叫者**——前端根本碰不到它 |
| 2 | **條件讀不到 FF 欄位** | 「讀特徵表」和「求條件」兩端都有，**中間沒接**：沒有任何程式把 FF 的欄位名註冊給條件引擎。🔴 **而且現在寫錯欄名不會報錯**——找不到該欄時條件直接判「不成立」，你會得到「零筆命中」而不是錯誤訊息（codex 查出）。這條必須在規格裡改成**報錯**，否則你永遠分不清「條件真的沒成立」和「欄名打錯」 |
| 3 | **比較比的是達標率，不是報酬** | 現有比較端點回「觸發批裡 label=1 佔幾成 vs 隨機批佔幾成」，不是平均報酬。而且它**常常是灰的**（要求觸發批帶「標籤規則收據」，一般匯入沒有） |
| 4 | **隨機抽樣現在不公平** | 見下表 |

#### 缺口 4 細項（四項都要修）

| 項 | 現況（實查） | 應該是 |
|---|---|---|
| 抽幾筆 | 前端預設 100 筆，**不跟著觸發批** | 跟觸發批同筆數 |
| 候選資格 | 只看**單一**答案窗長度 | 看你選的**最長**持有期 |
| 樣本之間 | 只禁抽到同一根，**不禁答案窗互相重疊** | 應互斥 |
| 期間池 | 取自觸發批最早～最晚的 `t0` | 應為整個 run 的期間 |

## 五、做法：五步

1. **條件引擎吃 FF 欄位**——把讀到的特徵表欄位名註冊給條件引擎，讓你能寫 `close_1h_trend_EMA_5 > close_1h_trend_EMA_10`
2. **掃描函式接上 API**——條件 → 事件批 → 匯入
3. **產隨機對照批**——走既有端點，**修掉缺口 4 的四項**
4. **比較端點加「平均報酬」**——現在只讀 label，要改成也讀報酬表
5. **前端**——掃描設定畫面（含持有期複選＋天數換算）＋ 兩組報酬並排的表（現在沒有並排元件）

### 兩條我查過、確定不走的路

| 曾考慮 | 為什麼不走 |
|---|---|
| 改匯入契約，允許「只有觸發點、沒有反例」的批 | **不需要**。label 系統自己算，契約天生就滿足 |
| 掃描時把隨機列混進同一批 | **被程式碼明文擋死**。理由寫在註解裡：對照組混進條件樣本，分母不再是無條件基準——「**那正是 estimand 的死法**」 |
