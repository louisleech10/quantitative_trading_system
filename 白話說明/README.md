### 為什麼「清單」花掉一整天

清單（技術版叫 TODO）是**寫給實作端照著做的施工說明書**，裡面每一條驗收都會變成閘門。
**閘門寫錯的代價不是慢，是它會亮綠燈但什麼都沒擋**——那比沒有閘門更糟，因為後面的人會信它。

委員擋了我 **12 輪**，抓到的東西一次比一次深。兩個最致命的：

| 委員抓到 | 白話 |
|---|---|
| 某個檢查**由構造上永遠通過** | 我寫「把宣告過的檔複製到乾淨資料夾，再比對差異」——複製進去的只有宣告過的東西，**差異永遠是空的**。那個檢查存在，但什麼都不會擋 |
| 新加的閘門**永遠不會被執行** | 我加了參數卻沒接線，**既有的呼叫從來不會帶那個參數** ⇒ 斷言全綠、生產零保護 |

### 🔴 我今天犯了 15 次同一種錯


## 🔴 維護規則（使用者 2026-08-05 定）

🔴 **這幾條不靠我記得——`scripts/plain_docs_sync_check.sh` 會擋，而且分兩層。**

| 層 | 時機 | 行為 |
|---|---|---|
| **提醒層** | `git commit` 當下 | 若這次改了實作卻沒帶說明檔，**印出提醒但放行** |
| **強制層** | `git push` 之前 | 判準＝**說明檔的最後更新不得早於其監看路徑的最後改動**；不合就**拒絕 push** |

**提醒層為什麼刻意不擋**：如果說明檔這次確實不需要改，硬擋會逼我養成用逃生口的習慣——
**那機制就等於失效了**。所以提醒放前面、硬擋放後面，而硬擋用的是時序判準，**繞不過去**。

### 📌 這機制已經擋過我兩次（都是同一種錯）

兩次都是**改完施工清單就以為做完了，忘記這份 README**。

| 次 | 情況 |
|---|---|
| 1 | `e243776` 修完驗收 oracle，push 被拒 |
| 2 | `18cfdd2` B3 完成，push 又被拒 |

**同一種錯連犯兩次，正好證明它不是多餘的**——
如果只靠我記得，這兩次的進度你都會看到舊的。

| 說明檔 | 它監看什麼 |
|---|---|
| `README.md`／`第0批-施工清單.md` | `scripts/`、`docs/GOVB0_`、`tests/governance/` |
| `治理待辦總覽.md` | `handoffs/20260801-GOV-AMEND-BACKLOG.md` |
| `第0批-在做什麼.md` | `docs/GOVB0_FRICTION_SPEC.md` |
| `治理進度日誌.md` | 不受管（使用者明示不看） |

**這個設計被使用者連續打回三次才對**：
①一開始沒有任何檢查 → ②只驗 `README.md`（其他檔忘了也沒事）→
③腳本要「記得跑」才有用（等於把紀律換個地方）→
④判準只驗「有沒有動過」，**實測證偽**：文件先更新、實作後改也算過，**順序完全沒驗**。
現行版本改為**比新舊**，副作用是**連人工標記都不需要了**——少一個要記得維護的東西。

**誠實邊界**：只驗**時序**，**不驗內容是否真的反映現況**——可只改一字換綠燈。
`git push --no-verify` 亦可繞過。屬「擋意外不防蓄意」，內容正確性仍靠審查。

### 三條規則本體

1. **時時更新**——每完成一個批次，立刻更新本檔的進度區塊與施工清單的進度表。
   不是等整批做完才更新。
2. **一份做完就封存**——某個任務（如第 0 批）整批完工後，
   把它的說明檔移到 `白話說明/Archived/`，本檔只留**當前正在做的那一個**。
   ⇒ **你打開這個資料夾，看到的永遠是「現在在幹嘛」，不是一堆歷史。**
3. **日誌是我自己的紀錄**——使用者不看流水帳，有問題直接問我。
   我依需要決定是否續寫與分檔，不佔用本檔版面。
