# B4 adversarial review — Codex — 2026-06-22

## Verdict
需修補後派工。方向可行,但 SPEC/TODO 目前把「交易式/RunBusyError/下游失效」寫得過滿,會讓實作者漏掉狀態一致性與並發邊界。

## Findings
1. [BLOCKING][High] 未驗證假設:「delete_run 已有 in-flight tombstone」不成立。SPEC §A 稱 registry get(:139) 刪除中拋 RunBusyError(:157/190),但實碼 `FeatureRegistry.get` 只回 dict/None,不檢查 deleting；`RunLifecycleManager.delete_run` 只 acquire lease 後 `_delete_run_locked`,不 mark_deleting。會失敗: bulk 取得 lease 刪檔期間,其他 reader/list/ensure 仍可看見 registry entry,直到 remove；若刪檔部分失敗則 registry 仍留但 artifacts 可半缺。修法: SPEC 明確要求 delete path 先在 registry transaction 內 mark_deleting/失敗 clear,或明確以 lease-only 定義且補所有 reader busy/hidden 行為與測試。
2. [BLOCKING][High] 「交易式」定義仍不夠可執行。SPEC §C 說逐 run 原子+report,但現有單 run delete 可先刪 features,再因 cgsa manifest/read/rmtree error 而保留 registry；這不是 per-run artifact+registry 原子。會失敗: bulk report failed,但 features 已消失、registry 仍列出 run,FeatureExplorer 看到 browse_ready false/404。修法: 定義 partial delete 狀態的修復策略: registry deleting/error tombstone、second-chance cleanup、或 report 中標 partial_artifacts_deleted 並從 list_runs 隱藏/標不可用。
3. [BLOCKING][High] 下游失效漏了實際參照。SPEC/TODO 只列 browse `_tasks`、checkpoint completed_items、quality cache；實碼還有 `FeatureFactoryService` per-task `_df_cache/_stats_cache/_adf_cache/_feature_metadata_cache/_cgsa_*`, `_browse_inflight`, disk `data_quality.json`/`feature_stats_cache.parquet`, frontend `selectedRunKey`, `explorerSummaryByTask`, `explorerFeatureNamesByTask`, `explorerRecentTasks`, `validationSummaryByTask`, `batchTask.browse_task_ids/results`, `FeatureExplorer` auto default selection。會失敗: 刪後 UI/cache 仍能顯示已刪 run 或對舊 task 發 browse request。修法: SPEC 列「後端 task/cache/inflight + 前端 selection/cache/recent + batch live/checkpoint」完整 invalidation matrix 與測試。
4. [MAJOR][High] checkpoint invalidation 語義空泛。SPEC §C/Task1.2 說「completed_items 參照標失效」,但現有 resume 會從 `completed_items` 重建 skipped/retained_completed、`list_recoverable_batches` 只看 completed_items 非空、quality 從 results_from_completed 計算。會失敗: 標個 invalid flag 若現有 builders 不過濾,刪除 run 仍被視為 completed/recoverable/quality target。修法: 指定 checkpoint schema (`deleted_at/delete_status/delete_reason`) 與所有 readers 過濾/顯示規則,包含 live `_tasks` 同步。
5. [MAJOR][High] 並發矩陣不足: bulk vs single delete/retention discard/batch generation 只說 RunBusyError。現有 retention discard 有自己的 per-item asyncio lock,但 bulk 不會共用；single delete/bulk 只靠 file lease,registry 不 tombstone；batch generation 在子 process 持 lease,但 parent checkpoint/register 也有窗口。會失敗: duplicate deletes 結果不冪等、retention item terminal 與 bulk report 衝突、完成後 register/checkpoint 指向已刪 artifact。修法: SPEC 要求同一 run 的 delete orchestration 共用 helper/lock+idempotent outcome,並測 bulk+single、bulk+retention discard、bulk+running batch same run。
6. [MAJOR][Medium] 防誤刪不足。SPEC 只有確認對話+空選,但 RunManagerPanel 有 batch grouping/全選,且 bulk target 以 symbol/timeframe/config_hash 表示；沒有要求二次呈現 aliases/batch aliases/full hash、active 禁選、批次群組選取範圍、重複去重後數量。會失敗: 使用者在分組/過濾下誤以為只刪可見子集或刪錯同 alias run。修法: 確認 dialog 顯示每筆 symbol/tf/alias/full hash/bytes/batch,active rows disabled,提交 payload 是去重後明細。
7. [MAJOR][High] HTTP 207 語意未定。SPEC Task1.1 說部分失敗回 207,但未定全成功/全失敗/validation/busy/not_found/schema；前端 TODO 也只說顯錯。會失敗: store 把非-2xx 當整批失敗,或 207 不被測試環境/clients 正確處理。修法: 定義 response body + status matrix: 200 all deleted/no-op, 207 mixed, 409 all busy?, 404 only invalid endpoint? 或一律 200 with per-run status;前後端型別與測試一致。
8. [MINOR][Medium] d_star cache 不應列為必刪下游。它按 symbol/timeframe/fracdiff/time_range fingerprint,不是 run artifact；刪 run 不應清 shared d_star,否則可能破壞跨 run reuse。SPEC 沒提 d_star 是合理,但 adversarial focus 有此題,建議在 §N 明確登記「不清 d_star cache」及原因。

## 被當成事實的未驗證假設

- 「reuse delete_run 即 per-run 原子」: 對 partial filesystem failure 不成立。
- 「下游只有 browse/checkpoint/quality」: 實碼存在更多 server/client references。
- 「207 + 前端顯錯足夠」: HTTP/client contract 未定義。
