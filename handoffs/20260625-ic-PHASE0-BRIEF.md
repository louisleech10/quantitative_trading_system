# IC 修法 Phase 0 — 白話決策版

> 2026-06-25 ｜ 給使用者看的版本，用日常語言寫。技術證據（檔名/行號/型別）在 SPEC §A，這裡不放。

---

## 現在發生什麼事

你在「IC 分析」頁面選一個 run、按下分析 → 畫面**卡很久 → 整個崩潰 → 跳出「WebSocket 連線失敗」**。

我把背後挖開，發現**六個獨立的毛病**疊在一起。Phase 0 就是**先把這六個止血、堵漏**，讓這個功能「跑得完、不會偷偷算錯」。**這一輪不重蓋任何大架構**，只修壞掉的地方。

---

## 六個毛病，用白話講

**① 程式直接當掉**
分析跑到一半，內部兩個模組對「資料要長怎樣」講好的格式對不上，程式一碰就崩。
→ **修法**：把資料轉成對方要的格式再交過去。只有一個地方在呼叫，改起來乾淨、不會波及別處。

**② 時間軸算錯年份（會算出假結果）**
系統要按「年份／季度」分組看因子表現。但它把時間戳的單位搞錯（把「秒」當成「毫秒」），結果 2024 年的資料被算成 **1970 年**。分組結果整個是錯的。
→ **修法**：讓它自己看資料判斷正確單位；如果算出來是 1970 或未來年份這種明顯不合理的，**直接報錯停下**，絕不偷偷給你一份錯的結果。

**③ 有個分析選項是「擺設」**
設定裡有「按波動度分組」這個開關，預設是開的，但底層程式根本沒寫這段 → 開了也沒用，靜悄悄被忽略。
→ **修法**：要嘛把它做出來，要嘛就讓它老實報錯說「不支援」。**這點交給委員會（技術顧問）討論定案，我照結論做**（見下方）。

**④ 「只看前 30 個特徵」的篩選是假的**
你在前端勾「只分析前 30 個特徵」，這個指令送到後端後**被丟掉了**，後端其實把**全部四萬多個特徵**都拿去算 → 這就是它跑超久、卡死的最大元兇。
→ **修法**：讓這個篩選**真的生效**。而且篩了多少、原本多少、用什麼條件篩的，全部**記在報告裡可查**，絕不偷偷砍掉特徵不告訴你。遇到超大的 run（像四萬多個）會**跳警示**。

**⑤ 跑的時候洗版一萬多條警告**
分析每個特徵都印一條警告，一次跑印了一萬四千多條 → 拖慢速度、洗爆畫面。
→ **修法**：跑完**收尾印一行總結**（例如「有 N 個特徵品質偏低」），不再逐條洗版。

**⑥ 卡住時前端只會說「連線失敗」**
分析很重時會把整條連線佔住，導致前端誤以為斷線，只丟一句沒用的「連線失敗」，還會無限重連。
→ **修法**：讓重運算不再佔住連線；真的出錯時**顯示真正的錯誤原因**；停掉無限重連；連不上時改用備援方式拿結果。

## 我絕對不會做的事（守住範圍與正確性）

- 不會**偷偷砍特徵**、不會放寬資料品質檢查、不會亂改 IC 的計算邏輯（只修②③這兩個本來就算錯的）。
- 不重蓋大架構（串流、訓練/測試切分、事件對照分析都留到後面的 Phase）。
- 不順手亂改 API 大格式。

## 需要你知道的一個取捨

只有 **毛病③（擺設的分組選項）** 有兩種做法：

- **A. 先讓它老實報錯**（我傾向）：Phase 0 的定位是「止血」不是「加新功能」，所以先讓它誠實說不支援，真正做出來留到下一階段。
- **B. 現在就把功能補上**。

**你說「照委員會討論的結果執行就好」 → 我會把這題丟給技術委員會（Codex + Composer 兩個 AI）討論收斂，定案後直接照做，不再回來問你。**
