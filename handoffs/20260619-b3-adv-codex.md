# B3 SPEC/TODO Adversarial Review — Codex

## Verdict
需修補後派工。SPEC/TODO 方向正確,但目前把多個關鍵語義留給實作者推斷；照此派工會高機率破 browse/quality/RunManager 一致性或在背壓/decide/resume 產生死鎖與重複 register。

## Findings
1. [BLOCKING][High] completed/generated 語義未拆清。證據:SPEC §A/Task1.1「completed_items/queued_items/status」「成功 item 預設進 generated」；真實碼 `_build_task_state`/`get_status`/`get_batch_quality_summary`/`list_recoverable_batches` 都從 `completed_items` 推導 results、browse_task_ids、quality、completed_count。失敗:staging item 若放 completed_items,會被 quality/list/status 當已可消費；若不放,progress/resume 又不守恆。修法:明定 checkpoint schema: generated_pending/retained/discarded 分欄或 filtered completed semantics,所有下游只看 retained,並列測試覆蓋 list/status/quality/RunManager。
2. [BLOCKING][High] 背壓「decide 釋放」與「B3 不刪檔」互斥。證據:SPEC §C/§V「磁碟背壓…decide 釋放」「discard 不 register、不在 B3 刪檔」；TODO §0「B3 不刪檔」。失敗:若 discard 不刪實體檔,磁碟空間未釋放,恢復派工可能 disk full；若背壓計數包含 discarded,discard 永不釋放導致死鎖。修法:分清 logical pending bytes vs real free bytes；背壓恢復前必做 `shutil.disk_usage`/T-C 風格 hard free-space gate；discard 的 B3 行為需明確「停止 pending 計數但仍受實際 free-space gate 約束」。
3. [BLOCKING][High] crash-resume 守恆未列出可驗證 crash points。證據:SPEC §V「resume:retention_pending item 重啟後狀態還原、不重算成功層、register 不重不漏」；真實碼 `_safe_persist_checkpoint` 寫失敗只 log 不 abort,`resume_batch` 會依 `completed_items`/manifest 缺失 requeue。失敗:hdf5 生成後 checkpoint 寫失敗會重算；register 成功後 checkpoint 寫失敗會重複 register 或漏狀態。修法:要求 crash matrix: after hdf5 before checkpoint、after checkpoint before notify、after register before checkpoint、during decide；定義 checkpoint 寫入失敗是否 fail-closed,register idempotency key,以及 injected-crash tests。
4. [BLOCKING][High] 並發 decide/冪等只有口號,無原子性設計。證據:Task1.2「重複 decide 冪等;並發 decide 安全」；真實 service 現有 checkpoint/task mutation 多處無單一交易鎖,`_record_item_result` 是 sync mutation。失敗:retain+discard race 可一邊 register 一邊標 discarded,或雙 retain 重複 quality/register。修法:指定 per-batch/per-item async lock 或 checkpoint CAS,合法 terminal 狀態先占用 `deciding`,再 register/mark；測試同 item 並發 retain/retain、retain/discard、discard/discard。
5. [MAJOR][High] 前端/API contract 缺 batch retention 欄位。證據:BatchTaskStatusResponse 只有 results/browse_task_ids/errors；前端 BatchTaskStatus 無 retention queue；現有 `GenerationProgress` 只處理單 symbol `retention_prompt/run_identity`。失敗:後端無法把 staging per-item 傳給 batch UI,或前端沿用單筆完成 prompt。修法:明定 REST/WS payload: pending item identity、state、hdf5_path/config_hash、decision_status/error；TS/Pydantic 同步。
6. [MAJOR][High] discard 與既有 `deleteRun` 邊界易被打穿。證據:RunRetentionDialog `remove()` 呼叫 `deleteRun`;SPEC/TODO 同時寫「discard 不刪檔(B4)」。失敗:batch 面板若重用現元件/動作,會刪 registry/artifact,提前做 B4。修法:batch discard 必走新 decision endpoint,不得呼叫 `/runs DELETE`;加前端測試 assert discard URL 不是 deleteRun URL。
7. [MAJOR][Medium] flag 關「完全舊行為」驗收不足。證據:SPEC §G/§V 只列 golden byte + register 時機同舊；golden baseline不能證明 register timing。失敗:flag off 仍可能多寫 checkpoint 欄位、延後 register、改 response 欄位但 byte 綠。修法:加 spy registrar/quality tests: flag off `_record_item_result` 同步立即 register、checkpoint schema/visible status 與舊兼容、batch status browse_task_ids 舊時機出現。
8. [MAJOR][Medium] retention 5 不變量可證偽性不足。證據:§V 只有自然語言與 `pytest -k ...` 名稱。失敗:實作者可用 smoke 測試假綠,未碰真實下游。修法:逐條指定 fixtures/commands/assertions: generated 不出 runs/quality, retain 後等於舊 register, A pending 時 B completes, restart reload pending, no duplicate register call count。

## 被當成事實的未驗證假設
- 「staging 只改 register 時機,不影響多下游」是 assumption；真實碼顯示 completed_items 同時服務 status/results/quality/list。
- 「decide 釋放背壓」是 assumption；discard 不刪檔時不釋放實體磁碟。
- 「resume 可不重算成功層」是 assumption；checkpoint 寫失敗目前 fail-open log-only。
