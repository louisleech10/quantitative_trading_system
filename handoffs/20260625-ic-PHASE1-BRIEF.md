# IC Phase 1 — 給使用者的白話 brief（決策文件）

> 目的：用白話講清楚 Phase 1 要修什麼、為何先做「契約」、第一刀做什麼。
> 技術細節（檔案、函式、行號）留在 SPEC，這裡不放。
> 級別：**大**（命中 ML 正確性 / 防洩漏 / 跨模組 / 多階段難回退）→ 走完整管線 + 雙家族 adversarial + 三方數據正確性簽核。

---

## 一句話

Phase 0 讓 IC 分析「能跑」；Phase 1 要讓它「**算得對、能信**」——目前的 IC 輸出有幾個地方會騙人（看似篩出好因子，其實混進了未來資訊、或統計顯著性灌水），Phase 1 把這些洞補起來。

## 你已經拍板的三件事

1. **這次只全力做 Phase 1 正確性**，事件研究主戰場（Phase 2A）之後再開。
2. **API 現在就改版**：大型分析不再把整包巨大的結果塞回前端，而是回「前 N 名 + 一個結果檔的位置（URI）」。一次改到位，前端只接一次，避免之後串流時又要重接。
3. **不另寫一套切資料的邏輯**：直接複用系統裡既有的 ML 驗證工具（walk-forward / purged CV）來做訓練/測試切分。

## 為什麼先做「契約」，不直接修公式

把正確性公式硬接在「現在這條舊的、會把整張大表攤平在記憶體裡」的路徑上，等於白做——因為之後（Phase 3）資料會改成「串流分塊」流動，舊路徑會被繞過，修在上面的東西全要重接。

所以四家委員會一致結論：**先定「契約」**——也就是先講好幾件事的「規格」，讓後面所有正確性修法都長在這個契約上，不管底下資料是小表還是串流，都不用返工。契約要定的東西（白話）：

- **怎麼切訓練/測試**（哪些列算 in-sample、哪些算 out-of-sample，中間要留多少「淨化間隔」避免前後黏到一起）。
- **哪些列要算、哪些不算**（Phase 1 小/中尺度**所有因子都評估、不丟任何一個**；`not_evaluated` 語義是給未來 430K 全量串流的**防漏安全機制**——萬一某因子沒跑到，**老實標記「沒評估」**而不是假裝得 0 分混進結果。是讓「漏」不可能靜默發生，不是允許漏）。
- **結果長什麼樣**（回傳 = 前 N 名摘要 **+ artifact 檔 URI**；**artifact 必須裝「全部因子的完整指標表」，前端讀它來瀏覽/篩選/排序，就像 FF explorer 讀完整特徵表**。不是丟掉只留前 N，是「快速摘要 + 全表可篩」。呼應決策 2，且使用者明確要求要能篩）。
- **篩選範圍**（統計校正 FDR 是在「哪個池子、哪個切分、哪些被評估的因子」上算的——算錯範圍，顯著性就是假的）。

## 一個已驗證的紅線（實測，不是猜）

你選了「複用既有 ML 工具」。我去讀了那兩個工具的程式，發現它們是用「**位置編號**」切資料、用「**連續一段**」做淨化間隔——這背後**假設資料是照時間連續排好的單一序列**。

但 IC 常常是**多個幣種堆在一起**的資料。如果直接餵進去，淨化間隔會「跨幣種」誤切——把 BTC 的尾巴當成 ETH 的開頭去淨化，等於**洩漏**。

→ 所以契約必須白紙黑字寫死：**切分要嘛分幣種各切、要嘛餵進去前先照時間+分幣種排好**。這條不鎖死，複用就會變成製造洩漏。

**（已查證）切分工具不是空殼**：walk_forward / purged CV 共 624 行、30 個既有測試全 PASS（含「切分不重疊 / purge / embargo 正確」）。Phase 1 只複用它的「切索引」邏輯，**不碰模型訓練**。使用者另提醒 XGBoost/LightGBM 模型引擎可能未測試——那是 **Phase 4（IC→ML 橋）** 的事，屆時先驗證，不混入 Phase 1。

## Phase 1 的施工順序（契約優先）

1. **1-contract（第一刀，本次先做）**：定上面那些規格 + 鎖死多幣種洩漏紅線。產出是幾個新的「資料結構定義 + 規格文件」，還不大改計算邏輯。
2. 1a 訓練/測試切分（落在契約上）
3. 1-align 前瞻偏誤硬閘（檢查「用今天的因子 vs 預測明天的報酬」有沒有對齊；差一格 IC 就爆）
4. 1b FDR 接線（統計多重檢定校正，接在正確的篩選範圍上）
5. 1c Net IC 量綱修正（把交易成本/換手折價算對）
6. 1d 因子歸因（真接實作，或老實改名叫「近似」）
7. 1e 顯著性 HAC / block bootstrap（滾動 IC 不是獨立的，現在當獨立算→顯著性灌水）
8. 1f 靜默空圖修
- 並行軌：薄串流脊骨（讓 4.5 萬列的大 run 可互動）

## 本次這一刀（1-contract）的交付與驗收

- **交付**：契約的資料結構（切分計畫 / 列遮罩計畫 / 篩選範圍 / 已評估範圍 / artifact 輸出 schema / `not_evaluated` 語義）+ API 版本化的新 response 形狀（top-N + artifact URI）。
- **三方數據正確性簽核**（鐵律）：切分 / 洩漏 / 合併的正確性，要 Claude + Codex + Composer **三方獨立簽核**，用真實 kline，不靠你驗收。
- **驗收**：契約有對應的可證偽單元測試（多幣種洩漏的反例會被擋下）、既有測試不退化、API 改版前端只接一次。
