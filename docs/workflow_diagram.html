Multi-Agent 協作協議 · 白話流程圖

一個需求進來，怎麼走到 commit？

從「判斷任務大小」開始，中／大任務走完整管線：主委起草 → 委員獵漏 → 化解 → 閘門放行 → 實作 → 簽核 → 進版。每一個「通過」都要有證據，不靠嘴說。

📥 收到需求

?這是小任務嗎？

判準：只改 1 個函式／局部 bug、能本地 pytest 驗、不碰資料正確性或共用路徑。

是 · 小 Claude 自己做 + 自跑測試，不派委員（省 token）→ 直接 commit。
否 · 中／大 進入下方完整管線。碰資料品質／跨模組／難回退／ML 正確性 = 大。

🔍 先手：web / X 搜尋已知問題

燒委員會前先花一次搜尋——工具 bug、錯誤訊息、已知限制、前例，世界上多半有人踩過，能省好幾輪。但搜尋是偵察不是判決，找到的解法仍要在我方環境實測，絕不凌駕資料正確性驗證。

1主委起草 SPEC／TODO

規格一律由主委起草，而且照範本寫（templates/SPEC_TEMPLATE.md）：每份 SPEC 要有風險分級、每個 Task 的驗證方式／邊界／「不可做」欄，並附一份測試章程（要測什麼、怎麼證明測得對）。

Claude 起草
🔒 GATE · 機器強制

template_check（格式 + 實際內容）

不只看「有沒有那個標題」，還看內容是否真的填了：風險分級那行不能空、每個 Task 要有驗證／邊界欄、涉及數值的地方要有 sha256／容差 token。範本沒跟好、內容缺 → 拒發派工 token。

2雙／三家 adversarial 審查

每個委員各自獨立去挑毛病，而且必須給「可證偽的反例」——不是說「看起來 OK」，是真的跑一個例子證明會壞。測試本身也受審：一個號稱「驗正確性」的測試，要能證明「把碼改壞它會變紅」，廉價綠燈不算。

沒有委員戳記 → 拒發實作 token。防止「主委自己寫個 reconcile、沒人複核就開工」。

4實作

實作者寫碼、需要時也自己跑指令。誰實作是動態的——Codex 與 Grok 依當下額度／指示切換，兩者都可能實作、也都可能當代跑或審查。主委只讀 receipt（收據），自己不下場跑，避免變成自己審自己。

?同一個問題卡超過 2 輪？

是 · 卡住 斷路器：立刻換手／開委員會診斷，禁止 solo 硬磨。
否 · 順利 繼續驗收。

5雙家實作審 + 主委獨立驗收

另一方 code review（實作者不自審）；主委親自重跑驗證，不憑執行端自報「我過了」。

Yes／No 讀法

綠 = 往下走 / 通過
紅 = 回頭修 / 換手 / 停
琥珀 = 判斷點 / 閘門

🔒 五道 Fail-Closed 閘門

  • 派工 token — gate.sh dispatch：派委員前要先開閘留痕。
  • template_check：SPEC/TODO 範本格式 + 實際內容都要對，才發派工。
  • reconcile stamps：沒委員戳記 → 拒發實作 token。
  • claim checker：commit 的「通過」宣稱要附 VERIFY receipt。
  • register-output：委員產出要登記（比對真跑輸出，防偽造）。

幾條不變的鐵律

  • 小任務不派工，Claude 自己做（省 token）。
  • web recon 先手，但 recon ≠ 判決，要自驗。
  • 主委只讀 receipt，自己不下場跑。
  • 同問題卡 2 輪 → 斷路器換手／委員會。
  • 三方簽核：任一方有疑就不過。
  • 審查勝簽核：至少一腿要真跑反例，不是確認式點頭。

運作細節 · 白話怎麼跑的

① 蓋章 + 機器強制

委員怎麼「蓋章」，機器怎麼「逼你」有蓋章

蓋章：委員審完，在定稿檔末尾附一行——
RECONCILE-STAMP: grok APPROVED 2026-07-12 sha256:5a8f… task:t6-recon-grok

那串 sha256 是「定稿內容的指紋」。只要有人偷改一個字，指紋就對不上、戳記自動作廢——所以不能先蓋章再改內容。

機器強制：一個腳本（reconcile_stamps_check）在你要開工／commit 前自動跑，它會 ①重算內容指紋比對戳記 ②去 audit log 查這個委員是不是真的被派工跑過 ③對照委員自己的輸出檔。三者全對才放行，否則拒發 token。人說「我蓋了」不算，機器去驗指紋+派工紀錄才算。

② receipt 收據

receipt 從哪來、裡面有什麼

跑驗收指令時不直接跑，是用一個外殼（run_with_receipt.py）包著跑。它自動把整場記成一個 json 檔：

claim_id（唯一 id）· command（跑了什麼）· exit_code（0=成功）· started/ended_at（時間）· 輸出 log。

之後任何「31 passed / 全綠」的宣稱，都要引用這個 receipt id；機器會回去查它真的存在、真的 exit 0、跑的檔案對得上。「通過」不是嘴說，是指得出一張真跑過的收據。主委也只信 receipt，不信執行端自己回報「我過了」。

③ 範本 + 測試章程

寫作有範本、測試有規範，都機器＋人審

範本：SPEC/TODO 照 templates/ 寫。template_check 不只查「標題有沒有」，更查內容有沒有真填——風險分級不能空、每個 Task 要有驗證／邊界／不可做欄、數值處要有 sha256／容差 token。缺一項就拒發派工。

測試章程（docs/TEST_DESIGN_CHARTER.md）：每份 SPEC 要附。核心一句——號稱「驗正確性」的測試，必須能證明「把碼改壞它會 FAIL」（可證偽／mutation）。廉價綠燈不算保證。測試設計本身也由委員會專審，量化統計嚴謹另有清單。

④ FAIL-CLOSED

什麼是 fail-closed（預設關門）

一道門有兩種預設：

fail-open（預設開）：出錯／沒驗到就放行——方便，但可能把壞東西放進去。

fail-closed（預設關）：只要驗證沒通過、或根本沒驗，就擋下。門天生鎖著，要拿出正確證據（token／指紋戳記／receipt）才開。

這整套閘門全是 fail-closed——寧可誤擋（麻煩但安全），也不誤放（把假綠放進版）。所以你會看到 commit 被擋好幾次：那不是壞掉，是門在盡責，逼你補上證據。
