# 驗收防偽閘 — 給老闆看的白話版

> 對應技術規格：`docs/VERIFY_GATE_SPEC.md`（檔案標題仍為 v2，依 HANDOFF 與確認戳記視為 **v2.1 定稿版**）  
> 讀者：非技術決策者。目標是說清楚「防什麼、怎麼防、哪裡擋不住、為什麼這樣設計」。

---

## ① 一句話總結

**以後交接文件或 commit 裡若寫「已驗、真紅、測試通過」這類話，必須附上機器可核對的「跑測收據」；沒收據就寫不進去、也 commit 不出去——但這套機制防的是「疏忽亂講」和「快測冒充慢測」，不是防有人刻意造假。**

---

## ② 要防什麼（這次事故為什麼會重演）

### 事故長什麼樣

2026-07-01 的 P0-FF-3 事件：交接文件寫了「對齊測試已驗證通過、真紅」，但**那個要跑約 25 分鐘的慢測從來沒真的跑過**。實際只跑了 0.38 秒的快速靜態檢查，卻被寫成「完整驗證通過」。第一次有人真的去跑慢測，立刻發現是紅的。

### 治理系統哪裡破了

委員會、派工門、審查流程都正常——委員也老實說「我沒跑慢測」。**唯一破口是：寫交接的人沒跑就宣稱跑了，而且當時沒有任何機器會擋這種話。**

### 這個閘要防的同型事故（不只這一次）

| 類型 | 白話說明 | 例子 |
|------|----------|------|
| **沒跑就宣稱** | 測試根本沒執行，卻寫「已驗」「通過」 | 只跑了語法檢查，卻寫「mutation 真紅」 |
| **快測冒充慢測** | 用幾秒鐘的快速檢查收據，撐幾十分鐘慢測的結論 | 0.38 秒靜態檢查 → 宣稱「慢測通過」 |
| **收據範圍對不上** | 有跑測試，但跑的範圍跟宣稱的不一致 | 收據只涵蓋 A 測試，卻宣稱 B 也過了 |
| **結論與結果相反** | 收據顯示失敗，卻寫「通過」 | 測試紅了，交接仍寫「全綠」 |
| **假收據** | 手寫一張看起來對的收據，沒有對應的執行紀錄 | 自己編 JSON，沒有系統留下的審計痕跡 |
| **舊綠蓋新紅** | 後來發現是紅的，舊文件裡「已驗」沒標作廢 | 事故後 HANDOFF 仍留著過期的綠燈宣稱 |
| **派工/審查假留痕** | 寫了「已做 adversarial review」，但沒有真派工的紀錄 | 自寫審查檔、自貼核准戳記，無對應任務事件 |

### 這個閘**不**要防什麼（誠實邊界，不可誇大）

- **不保證「人對結果的解讀正確」**：收據證明「有真跑、指令和範圍對得上」，不保證「紅被看成綠」。解讀品質仍靠 adversarial 審查 + 委員複核。
- **不保證「惡意造假」**：收據和審計紀錄由同一台可寫入的機器產生；有心造假的人理論上可同時偽造兩邊。設計目標是 **careless-proof（防粗心）+ tamper-evident（事後可發現被改過）**，**不是**密碼學級別的「不可偽造」。
- **不碰數值/ML/回測正確性**：這是流程誠實基建，不驗證特徵算對沒、模型有沒有洩漏。

## ③ 怎麼防（五個階段，白話版）

整體思路用一個類比：**收據 = 收銀機小票，檢查器 = 會計對帳，三層防線 = 寫的當下擋、存檔前擋、上雲後還擋。**

核心分工也要記住：

> **文字偵測只負責「這句話算不算驗收宣稱」——像路由器，不是法官。  
> 法官是：收據、任務紀錄、戳記、審計流水帳能不能對得上。**

在「commit / 交接邊界」：**對得起就過，對不起就擋（fail-closed）**。  
在「討論、引用舊資料、標記作廢」：**寬鬆放行（fail-open）**，避免正常檢討被誤殺。

**與既有派工門的關係**：本閘是既有 `gate_check.sh` 旁邊的**新增驗收通道**，不取代、不放寬、不繞過原本派工門。

---

### Phase 1 — 跑測試就自動開收據 + 審計流水帳

**做什麼**

以後驗證測試不直接裸跑，改走一個包裝工具（`run_with_receipt.py`）。它會：

1. 執行原本的測試指令（輸出照常顯示）。
2. 自動產一張**收據**（JSON + 完整 log），記下：
   - 跑了什麼指令、在哪個版本、工作區是否乾淨
   - 開始/結束時間、耗時、退出碼（過或沒過）
   - 跑了哪些測試項目、有什麼標記（例如「需要真實 K 線資料」）
   - log 的指紋（hash），方便事後核對有沒被改
3. 同時往**審計流水帳**（只能追加、不能改舊行）寫一筆事件，把收據指紋綁在一起。

**為什麼要兩份（收據 + 審計）**

單獨一張手寫收據不夠——檢查器要求「收據上的關鍵欄位必須能從指令和 log 重算，且跟審計流水帳對得上」。跑完後若有人改收據擴大範圍（例如多塞幾個測試項目），審計那邊的指紋對不上，會被擋。

**測試類型怎麼分（防快測冒充慢測的基礎）**

系統會依「實際跑了什麼」自動分類，例如：

- 靜態檢查 / 輔助冒煙測試（幾秒級）
- 需要真實 K 線資料的慢測
- mutation 探針（專門測「探針有沒有牙齒」）

人傳入的「我以為這是什麼測試」只供稽核參考；**以系統從指令和結果推導的為準**。

**檔案必須能進版本歷史**

收據和審計檔不能被「忽略 log 檔」的規則誤傷，否則本地有、雲端沒有，信任鏈斷裂。

### Phase 2 — 宣稱檢查器（核心大腦）

**做什麼**

一個檢查程式掃描：根目錄 `HANDOFF.md`、所有 `handoffs/` 交接檔、commit 訊息（含 `docs:` 類型）。它不做「這句話語意上對不對」，只做：

> **「這段文字是不是在宣稱驗收結果？若是，有沒有合格的背書？」**

**怎麼判斷「這是驗收宣稱」**

不是死背幾個關鍵字，而是把每段文字拆成一個個 **claim-object（宣稱物件）**，看：

- **極性**：成功 / 失敗 / 作廢 / 待驗 / 純討論
- **範圍**：哪個測試、哪個任務、哪個區域
- **預期測試深度**：沒要求 / 靜態 / 冒煙 / 要真 K 線 / mutation / 唯讀簽核
- **出現在哪**：正式狀態段、commit、還是引用/討論區
- **背書**：收據編號、任務編號、戳記、或標了作廢哪個舊宣稱

觸發詞分強弱：「已驗」「真紅」「全綠」「無 look-ahead」「signoff」等是強宣稱；單獨「passed」「通過」只在正式語境才算。引用區塊裡的 pytest 輸出（如 `` `42 passed` ``）、「passed through」「通過層 6.5」等**不算**宣稱。

**三種處理模式（優先順序）**

1. **有引用標記**（`VERIFY:<收據編號>` / `REF:<編號>`）：去查審計流水帳，核對極性、範圍、收據類型是否匹配 → 對就過，不對就擋。
2. **有作廢標記**（`SUPERSEDED:<編號>`）：表示舊宣稱作廢 → 放行。
3. **在討論/引用區**（引用塊、或標了「這是討論」的註解）：不當新宣稱 → 放行。
4. **其餘含宣稱語氣的正式文字**：**必須有 VERIFY 背書，否則擋**——這正是本次事故的核心規則（代號 W4，P0 優先）。

**快測不能撐慢測（再次強調）**

靜態檢查或幾秒冒煙測試的收據，**不能**用來背書「mutation 真紅」「慢測通過」「真跑過」這類話。

**背書必須「跟著 commit 走」**

引用收據時，收據、log、審計事件必須是**同一個 commit 裡已納入版本庫的檔案**。只在本地、還沒 commit 的收據，不能拿來支撐已 commit 的宣稱——防「本地編一張、遠端對不上」。

**唯讀簽核（讀碼結論用）**

讀程式碼得出的結論，可用特殊格式 `SIGNOFF:<家族>:<任務>:<範圍>` 背書，不要求跑測收據——但**不能**用來說「慢測跑過了」。也不能裸寫「已驗」。

**極窄豁免（不是逃生口）**

只有六類可申請豁免（錯字、文件範例、遷移說明、範本漂移、工具被擋、規格模糊），格式固定。  
**HANDOFF 正式狀態段、commit 訊息、RESULT 段：零豁免。** 每檔每議題最多豁免一次；雲端會統計豁免率，太高會警告。

**待驗清單（pending ledger）**

執行端說「這項留你驗」時登記；在關閉前，同一任務不准寫「DONE」「已驗」「ready」。關閉必須對到正確的待驗單號 + 匹配的收據。

**誤報門檻（實作硬性前提，見下文⑥）**

檢查器必須先通過「誤報 = 0」測試：本規格、事故檢討、議事紀錄裡**合法引用**的「已驗」「真紅」原文不能被誤擋。未達標前，不啟用最強的第一道防線。

### Phase 3 — 三層防線（實際擋人寫進去）

| 層 | 什麼時候擋 | 白話 |
|----|------------|------|
| **第一層：寫入當下** | AI 編輯 HANDOFF / handoffs 時 | 只檢查**這次新增或修改**的正式狀態文字（正在做、待辦、已完成、STATUS、RESULT 等段），不掃整份歷史；擋住「邊寫邊謊」——本次事故主路徑 |
| **第二層：本機存檔前** | git commit 前 + commit 訊息 | 掃已暫存的所有 HANDOFF、handoffs、相關 docs；commit 標題和內文也過檢查 |
| **第三層：雲端正式關卡** | PR / push 到 GitHub | 對變更範圍再跑一遍；**即使用 `--no-verify` 跳過本機關卡，雲端仍會擋**；工具缺失時必須失敗，不能「缺了就當沒事」 |

另有一支健康檢查：確認本機關卡裝對了、必要工具都在，納入派工前後檢查與雲端流程。

**降級路徑（硬性順序，不可跳過）**

若 claim-object 測試**誤報 ≠ 0**（會誤殺正常文字）→ **不上第一層**，只保留第二層 + 第三層 + 收據機制。寧可少擋一層，也不允許「亂擋導致大家找豁免逃生」。

### Phase 4 — 把現有驗證流程接上收據 + 補派工留痕漏洞

**mutation 探針檢查改走收據**

最常用的 `mutation_probe_check.sh` 規則 3 改經收據工具跑；**通過/失敗判定和對外訊息不變**——只是多了一張可核對的小票。

**派工門補 W2 / W3（P0，與本次事故同型）**

| 代號 | 原本漏洞 | 補法 |
|------|----------|------|
| **W3** | adversarial 審查只查「檔案在不在」 | 檔名須符合命名規則 + 對應任務在審計流水帳有真派工事件 |
| **W2** | reconcile 核准戳記可自己貼一行 | 戳記須綁任務事件 + 輸出檔 hash 機械對照，不能只看有一行字 |

**W7 輔助**

提供低成本抽查審計鏈的小工具，給人為抽查用——**刻意保留人工關卡，不改成全自動 fail-closed**。

---

### Phase 5 — 結構化結果欄位 + 衝突檢查

**RESULT 檔硬欄位（不用自然語言猜）**

執行端收尾的 `*-RESULT.md` 須用固定枚舉欄位，例如：

- `STATIC_CHECK` / `RUNTIME_CHECK` / `MUTATION_CHECK` = `NOT_RUN` | `PASS` | `FAIL` | `N/A:原因`
- `RECEIPTS=[...]`
- `OPEN_PENDING=[...]`

檢查器讀欄位，不靠猜段落意思。

**#6 衝突檢查（v1 只做這個，不做全自動索引）**

同一個「宣稱指紋」若已出現 FAIL/紅燈紀錄，舊的「已驗 VERIFY:…」若沒標 `SUPERSEDED` → 擋。  
**完整自動把整份 HANDOFF 重排索引 = 延後到 phase 2**（避免改變全員寫法、產生大量無謂修改）。

**W1（P1）**

規格裡寫「已確認」且涉及資料結構、型別、命令輸出的事實，必須附實測紀錄編號；純設計假設不准寫「已確認」。

## ④ 三層防線為何要三層

用「機場安檢」類比：

| 層 | 類比 | 防誰繞過 |
|----|------|----------|
| **第一層（寫入當下）** | 安檢在登機口前 | AI 邊寫交接就謊報——**本次事故主路徑**；不經 git 也擋 |
| **第二層（本機 commit）** | 行李必過 X 光才能托運 | 本機改完想存檔；養成「沒收據別 commit」習慣 |
| **第三層（雲端 CI）** | 抵達後邊境再查一次 | 有人習慣跳過本機關卡（`--no-verify`）；**正式執法在這層** |

**為什麼不能只做一層**

- 只做本機：可被 `--no-verify` 跳過，事故檔案仍可能進 repo。
- 只做雲端：寫入當下不擋，謊話先寫進檔案，靠事後 CI 才發現，成本高、且可能已誤導下一個接手的 AI/人。
- 第一層依賴「誤報 = 0」才上：否則正常引用、事故檢討文字會被誤殺，大家會濫用豁免或停用，反而繞過整個系統。

**三層可獨立關閉（緊急回退）**

第一層、本機關卡、雲端 workflow 都可單獨停用；建議停用時仍留一筆審計說明。收據和檢查器是新腳本，不動既有派工門邏輯，可整包 revert。

## ⑤ 已知會失效的地方 + 怎麼補（誠實列）

### A. 設計邊界內「本來就擋不住」的（不是 bug，是取捨）

| 風險 | 說明 | 補償 |
|------|------|------|
| **惡意偽造** | 收據與審計由同一可寫主體產生；刻意造假可兩邊一起編 | 威脅模型假設是**編排者疏忽**，不是內鬼；靠 tamper-evident 事後對帳 + 人工抽查（W7） |
| **解讀錯誤** | 收據顯示失敗，人仍堅持「其實算過」 | adversarial + 委員複核；閘不判「詮釋對不對」 |
| **未知同義詞** | 新寫法暫時抓不到（如新的「搞定」「穩了」） | v1 先 **WARN 收集**，週期性升級為必擋；**不是 v1 就封死所有說法**（防撞牆） |
| **過期宣稱殘留** | 舊 HANDOFF 裡過期綠燈沒清 | v1 只做 #6 衝突檢查 + 人工標 `SUPERSEDED`；**完整自動索引延後** |
| **人為稽核環節** | 模板空殼、審計鏈抽查 | 刻意保留給人（W6、W7）；不過度機器化以免逼出繞路 |

### B. 已知技術殘餘（v1 接受，phase 2 再補）

| 殘餘 | 風險程度 | 計畫 |
|------|----------|------|
| **待驗清單無檔案鎖** | 單機低風險；極端情況下併發寫入可能競態 | phase 2 加鎖 |
| **收據目錄無完整自動索引** | 難一眼看出「還有哪些宣稱沒收據」 | phase 2 做索引與自動 render |
| **完整 HANDOFF 自動重排** | 過期 claim 靠衝突檢查漸進清，不能一鍵全域正確 | phase 2；v1 避免 churn |

### C. 撞牆風險與對策（四方議事共識）

| 若發生什麼 | 後果 | 對策 |
|------------|------|------|
| 誤擋太多 | 大家濫用豁免或停用關卡 | 誤報 = 0 才上第一層；未知詞先 WARN |
| `--no-verify` 常態化 | 本機關卡形同虛設 | 雲端第三層不可 fail-open |
| 豁免洗版 | 假裝都是「錯字」 | HANDOFF/commit/RESULT 零豁免；統計豁免率 WARN |
| 同義詞軍備競賽 | 用新詞繞過 | 週期升級詞表；事故原文 fixture 回歸測試 |
| 收據疲勞 | 什麼都開收據，重要反而淹沒 | 只對正式狀態/待辦/結果段落中的 operational 新宣稱強制；純待辦、阻塞、決策且不含已驗/DONE/ready/真跑等驗收宣稱時不觸發 |
| 寫到未掃描檔 | 漏網 | 掃 HANDOFF + handoffs + commit；RESULT 用硬欄位 |

### D. 延伸背景（非本 SPEC v2.1 驗收範圍）

> 以下 W5/W8/W9/W10/W11 來自更大 workflow 掃描，**不在** `VERIFY_GATE_SPEC.md` v2.1 的 Phase / 驗收範圍內；僅供背景參考，TODO 生成與驗收勿當 v2.1 scope。

- **W10**：舊派工門在工具缺失時會「缺了就放行」；新驗收門在雲端**必須**缺失即失敗。
- **W11**：某些派工指令形式可能漏過舊 matcher；靠 Task 路徑 + 本 epic 的 handoff 檢查補。
- **W8 / W9**：記憶體簽核、RESULT 欄位與收據交叉驗證——P1，防持久污染。
- **W5**：派工 token 與前後快照配對——P2，靠人/review。
