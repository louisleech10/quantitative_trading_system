2026-08-04 深夜｜偵察輪做了什麼、發現什麼

一句話總結

原本以為 B-15 只是「唯讀指令被誤擋，煩人而已」。實際查出來，同一段程式碼裡藏著四個問題，其中兩個是「該擋的沒擋」。

查到的東西（都有實跑證據，不是推測）

1. 票上寫的原因是錯的。 票上說「只要指令裡出現委員的名字就會被擋」。我去讀程式碼，發現它其實已經避開這種情況了（註解裡還特別說明過）。真正的原因有兩個，而且互相獨立：

  • 原因 A：它看不懂引號。指令裡引號內的分號會被當成「這裡是新的一條指令」。 例：git commit -m "…修好了; codex 那邊已複查…" → 被擋。
  • 原因 B（更嚴重，今晚現場抓到）：只要指令裡出現 claude 這個字，而且後面任何地方出現 -p 這兩個字元，就會被擋。 問題是——治理檔案的資料夾就叫 .claude/，暫存資料夾叫 claude-501，而 -p 出現在 rev-parse、--porcelain 這種常見指令裡。 **所以「碰治理檔案的唯讀指令」等於在擲骰子。**而且中間加一根管線符號就會過，所以它看起來時靈時不靈——我過去一直以為是環境不穩。

2. 有兩個洞是「該擋的沒擋」（比誤擋嚴重得多）。

  • 用完整路徑呼叫委員工具（例：/opt/homebrew/bin/codex …）完全不會被擋。 而系統自己內部用的就是完整路徑——也就是說真正的派工形態不在守備範圍內。
  • 直接執行派工腳本 bash scripts/cx_run.sh … 也不需要任何許可證。 我查了，那支腳本和它的角色檢查裡，「token」這個字出現 0 次。

3. 一個更根本的問題：被擋下來的指令，系統完全沒有留下紀錄。 擋下來的原因只記「許可證過期」或「有欠帳」兩種，指令本身一個字都沒存。 另一份會記指令的日誌，因為執行順序排在檢查之後，被擋時根本不會執行。

這代表：誤擋率是憑印象講的，而且改完之後無法驗證有沒有改對。 所以 B-15 要拆成兩段——先讓系統記下被擋的指令，才有辦法談改判準。
