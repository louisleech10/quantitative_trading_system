第 2 批 b 第一輪審碼抓到三個真洞（都是我的）——共同形態是：我把「擋下」寫在數量上， 沒寫在身份上： ①餵另一批事件清單進來，程式照樣算出一份看起來正常的切分（沒有對帳）； ②單一 ETH 事件配單一 BTC 的邊界，也照樣通過（只檢查「有幾個標的」，沒檢查「是哪一個」）； ③時間單位混著給（一部分秒、一部分毫秒）或列號給負數，都不會報錯——負數在 numpy 會 回捲成尾端的列，靜靜給出錯的歸屬。三條都由 codex 實際餵壞資料跑出來證明， 讀碼是看不出來的（規格本身就沒寫「要檢查身份」）。三條全部補成明確報錯。

還有一條更難堪的：我的重構把一條真測試變成了同義反覆。我把「分簇」抽成共用函式之後， 原本「新做法 vs 舊做法逐值比對」那條測試，比的變成「共用函式 vs 呼叫共用函式的東西」—— 它永遠會綠，而且我當時只看到「567 條全過」就過去了。測試變綠不等於測試還在測東西。 已改成拿「依公式手推並凍結的答案」當對照，與程式無因果關係。

第 2 批 b 第二輪：又六條，全都是同一個毛病——我把「擋下」寫在「有沒有給」上 （缺欄位、缺計畫、缺標的），沒寫在「給的東西合不合理」上。六條分別是： 時間索引沒排序或有重複、數值裡混了 NaN（會被靜默變成 0）、事件編號重複（用「集合相等」 比對時會被吃掉）、列號給小數（0.5 會被截成 0，等於靜靜換了一列）、答案窗頭尾顛倒、 分簇桶寬給 0 或負數（其中 0 原本「有擋」純粹是巧合——靠 pandas 自己拋例外， 哪天它換行為就靜默失效）。全部補成明確報錯，並各配一條破壞性驗證。

其中一條是我推翻自己：列號給小數那條我原本判「型別錯誤不算資料問題，不改」， 三家有兩家判該擋，理由更好（0.5→0 是靜靜換了答案，不是型別噪音），依較嚴版採納。

還有一件方法論上的驗證：第一輪我記下「派工單要明確要求主動餵壞資料， 不能只讀碼對照」，第二輪照做之後，第一輪零意見的那一家這次也找到兩條。當輪就見效。

第 2 批 b 第三輪：三條，又是同一類的變體——這次是「守衛存在，但有一條路徑繞過它」： ①我第二輪補的「時間必須遞增」檢查，只補在數字那條分支上，日期型的索引直接繞過去 （等於只修了一半）；②列號我驗了範圍和不重複，沒驗順序——反過來排時「第一列」就不是 最早那一列；③標的代號如果是空的，我原本的寫法會先把空值濾掉，結果整組守衛一條都沒跑到， 還會輸出一筆沒有標的的結果。三條全部當輪修完並各配一條破壞性驗證。

教訓寫成一句：加守衛時要問「有沒有哪條路走不到這裡」，而不只是「這個檢查對不對」。

三輪合計：嚴重問題數 3 → 5 → 3，群集數 8 → 7 → 3，沒有一輪出現最嚴重等級。

🔴 2026-09-11 使用者糾正，我這裡犯了規：我原本寫「依『95% 就收』原則，第 2 批 b 到此收工」。 那條是治理票的收斂原則，量化主線絕對禁止套用（使用者當面定死）。 量化主線的標準是 CLAUDE.md 的三方簽核鐵律：任一方有疑就不通過——剩下多少都不是停輪的理由。 我用錯的標準停掉了第 2 批 b 的審查輪次——停輪的理由必須是「findings 全部閉合且可證偽」， 不是「剩下的不多」。

第 2 批 b 的兩件誠實紀錄： ①我第一版把「分簇」那段複製了一份到新檔，等於留了兩份算術——正是這張票要消滅的東西。 自查後改成真的抽出來、兩邊共用同一支，行為逐值不變。 ②破壞性驗證第一輪有 3 條沒抓到，不是實作對，是我的測試設計不夠： 訓練段的列是連續的，所以「區間」和「集合」在沒有缺口的資料上根本分不出來； 「同時落在兩邊」那道防呆在正常輸入下永遠走不到；每個事件各自成一簇時權重恆為 1， 把公式寫死成 1 也測不出來。三個 fixture 都改過之後才全紅。

第 2 批 c 做了什麼：凍結五組對照答案，任何一組對不上就紅，而且會指名是哪一筆事件 （只回「不一樣」等於把「哪裡壞了」丟給下一個人重查）。其中兩組特別重要： ①獨立答案——對照用的答案是我逐行另外推一遍得出的，不是呼叫被測程式產生的 （上一批就是因為拿被測程式當對照，測試變成了同義反覆）； ②負例——刻意把一筆訓練事件的答案窗推進驗證段，它必須被丟掉；正向全對但負例不擋， 等於沒有隔離保證。實測：把答案窗那道閘拿掉 ⇒ 三條測試同時變紅。

另外產出一份一次性遷移報告（不進綠燈路徑）：新舊兩種切法對同一批的差異， 實測差 1 筆（te0 只在新切法的驗證段）。這份不凍成 golden——凍一份「預期有差」的對照 等於把已知的不一致合法化。

第 2 批 c 審碼：五條，最深的一條打在「我的獨立答案其實不夠獨立」—— ①三家同時抓到同一條：我說要檢查「答案窗的頭和尾都要落在資料上」，實作只檢查了頭。 不過正確的修法和三家提的不一樣：三家都說「查不到尾巴的事件就該丟掉」，但規格前面幾輪 已經裁定過「這道檢查不歸切分函式管」（它手上根本沒有那份資料）——所以改成 驗上游有沒有把關，而不是把檢查硬塞進切分。照三家原話改，會讓錯誤永遠指錯人。 ②對照用的指紋我只凍了一個雜湊值，測試只檢查「它長得像雜湊」⇒ 算錯的指紋也會被凍進去。 改成把明細也凍進去，測試從明細自己重算一次再比對。 ③最深的一條：我的「獨立答案」雖然是逐行另推的，卻和被測程式共用同一組測資與同一支邊界函式—— 邊界算錯時兩邊會一起錯，測試照樣綠；而且用 --write 重凍還會把錯的一起凍進去。 修法是加第三個錨點：完全用測資的常數手算出「第 140 列切開、驗證段是第 144 到 199 列共 56 列」 寫死在測試裡，不經過邊界函式也不經過切分。實測證明關鍵方向成立：把邊界函式改壞、再重凍一次 golden， 這條手推錨點照樣紅。④⑤是可讀性：對不上時要指名第一個差在哪個位置；golden 檔壞掉時 要回「golden 壞了」而不是丟一段 Python 錯誤堆疊（分不出是資料壞還是程式壞）。

收尾時抓到的一個坑（記在這裡）：委員為了證明「golden 檔不見會紅」，把兩份對照檔搬到自建的 暫存夾裡，收工只還原了一份 ⇒ 主線兩條測試整輪紅在「檔案不存在」。已還原並確認內容逐位元相同。 以後審碼收尾一定要查一次「對照檔資料夾有沒有被動過」。

# 小項 狀態 說明

第 3 批審碼：三家講的是同一件事，但只有一家說「必須現在修」——我採了那一家。

三家各自跑出同一個洞：我拿來判斷「兩份切分計畫是不是同一批」的那個指紋，只是一段字串。 有人可以帶著相同字串、卻把計畫建在另一份 K 線網格上；也可以把傳進來的網格整體平移幾十根。 兩種情況下「第 140 列」指的都不是同一個時刻，程式完全不會報錯，只會安靜地把事件分錯邊 （其中一家的實測：某個事件本來在驗證段，平移之後變成訓練段）。

嚴重度上他們分歧：一家說「這條不修不准進下一批」，一家說「可以進，但接上去之前一定要修」， 一家說「不擋」。我採最嚴的那個版本，當輪就修完了——理由不是二比一，而是：說「不擋」的 兩家給的理由都是時間性的（「反正現在的正式流程還沒走到投影」），而那個理由會在下一批 接上第一個呼叫點的當下消失，修補成本卻不會變便宜。

修法是三家一致提的形狀，而且不動既有指紋的算法（動它會讓一批既有的凍結值全部位移）： 拿計畫自己記著的「起訖時刻」，跟傳進來的網格在同樣那幾列上逐值對照，對不上就報錯。 配了四條測試（兩條是三家的反例原封搬過來）和一條破壞性驗證。

還有一條是我自己的錯，不是碼的錯：我在派工單裡寫「事件那邊永遠拿不到特徵表」， 其中一家實查後指出——IC 那條路由是拿得到的（它同時握有事件批和特徵 run）。我複查屬實。 正確的說法是：「事件掃描頁」拿不到（第 3 批的裁定不變），但 IC 那條有，而那正是下一批 要接投影的地方——也正是上面那個洞從「理論上可能」變成「真的會壓到」的原因。

第 3 批做完的當下發現一件事，值得記：原本有一條測試在守「宣告的答案窗深度要真的送進切分」。 這一批把事件掃描端改成不切分之後，那條測試的前提就不存在了——它變成一條會逼後人「把切分接回來 以求綠燈」的測試。我把它改寫成守同一件事的現行形態：宣告的數字不得靜默消失（切分沒被呼叫、 隔離寬度明確回報「不適用」而不是 0、宣告值仍看得見）。前提消失時要改寫測試，不是刪掉也不是留著。

# 小項 狀態 說明

第 4 批兩輪審碼，三家把我的「機械判準」連打兩次，兩次都是同一個毛病的不同深度：

第 4 批做的時候，實測打掉了我的第一版判準——這件事值得你知道，因為它就是這張票的核心：

我原本以為「驗證段有幾個」只會有一個數字，所以測試寫成「兩個地方的數字必須相等」。 實跑出來是 335 vs 13：同一段裡有 335 根 K 線，其中 13 根上面有事件。 兩個數字都是對的，只是在回答不同的問題。真正要禁的是「同一個問題有兩個答案」 （你 UAT 看到的 31 vs 33 就是這種），不是禁止報告同時出現列數與事件數。

所以改成：報告裡「驗證段事件數」這個語意的鍵只准有一個，其他相關數字要嘛是別的語意 （列數）、要嘛只在降級說明裡出現。哪個鍵算哪種語意，寫成一份清單檔由測試機械檢查—— 不是靠我在文件裡寫一段話說明，因為那種說明會過期而且沒人擋得住。

🔴 第三輪抓到一條真的會洩漏的問題——而且是我自己造成的

這是今晚最嚴重的一條，我先講清楚。

平台原本的事件切分裡有一行（event_split.py:114）：如果某個事件的答案窗 （就是「往後看幾根算報酬」的那一段）已經伸進了驗證段，那這筆事件就要被丟掉、 不能留在訓練集。這是事件那一側唯一擋「答案偷看未來」的閘。

我寫的新規格書，把切分改成「看事件的時間點落在訓練段還是驗證段」——聽起來很乾淨， 但那個判斷根本沒有讀答案窗。等於我把那道閘整個刪掉了： 答案窗已經伸進驗證段的訓練事件會留在訓練集，那就是實實在在的洩漏。

更難堪的是，「不准刪掉任何既有的閘」這條規則，是我自己在同一份規格書裡寫的。 前兩輪審查（各三家）都沒抓到，第三輪 codex 抓到了——它用的方法是我在派工單裡 要求的「把每個介面拿去對真實程式碼，看接不接得起來」。

已修：現在改成兩段式、順序不能調——先檢查答案窗有沒有跨界（跨了就丟掉）， 再判斷落在訓練還是驗證。另外加了一條破壞性測試：把第一段拿掉，測試必須變紅。

條件式已經確定（定向確認輪的結論）：新的驗證段起點本來就已經在緩衝之後， 所以不必再減緩衝——舊寫法要減，是因為它的起點在緩衝之前。 這件事已由第 2 批 a 的測試釘住（驗證段第一根 ＝ 分界點＋purge＋embargo）。

找碴第一輪（審規格本身）

抓到的重點都是我的疏漏，已改：我只寫「切分計畫要帶逐列指紋」，卻沒寫誰負責產生它——照原樣做下去，現行單標的的路徑會因為拿不到指紋而整批失敗；另外我把一條會被改到簽名的條款標成「依賴」而不是「覆寫」，等於給實作者互斥的指令。還有指紋的欄位名稱跟既有凍結答案不一致，會變成兩套對照表各凍一份。

閉合第一輪

🔴 這一條是這張票目前最有價值的一次攔截：兩家對規格裡同一句話讀出相反的意思——一家讀成「每個標的自己那份短索引」，另一家讀成「必須是能被整批列號查詢的那份大索引」。兩種讀法各自都說得通，所以這不是誰讀錯了，而是那句話本身有兩種解釋。機器完全抓不到這種問題。真正抓到它的是一條規矩：閉合輪一定要由原本提意見的那個人來驗。這輪一家說「可以開工了」、原提意見的那家說「我那條沒關掉」——如果按人數多數決，就直接放行進實作了。

同一輪還抓到我自己的一個錯，而且是「看起來很精確」的那種：我前一輪寫「座標轉換只發生在兩個地方」，指定了數量也指定了位置，讀起來很可靠。實際去數，程式裡用到那個座標的有五個地方，我只寫中了一個。寫死一份「清單」而清單本身是錯的，比不寫清單更危險，因為它讓後來的人以為這件事已經盤過了。

閉合第二輪

「有沒有第六個地方」的答案是沒有，我的清單這次是對的。但它抓到另一條更根本的：我寫的修法根本叫不動。我指定要複用一支既有的轉換函式，可是那支函式需要「整批資料裡每一列各屬於哪個標的」這份資訊，而我新定的介面和切分計畫裡都沒有帶這份資訊。等於規格寫了一個做不出來的步驟。

我沒有照它建議的方向補，而是改成讓產生切分計畫的那一端直接把標的內序號寫進計畫裡。三個產生端本來就都算過那個序號，寫進去零成本，而且它們手上正好有那份標的歸屬資料，可以當場驗證寫得對不對。這樣投影端完全不用碰整批座標。因為我換了方向、沒照委員建議做，所以下一輪我多派了一家，專門攻擊「你換的做法真的等價嗎」。

順帶挖出一件此前八輪都沒人指出的事：那個座標欄位的意思，在三個產生端之間本來就不一致——兩個寫的是整批位置，一個寫的其實已經是標的內位置。這種不一致平常看不出來，正是多標的一開就會咬人的那種。

閉合第三、四輪

第三輪抓到「切分計畫設成凍結之後，裡面的資料其實還能被改」；第四輪我照著修，又被抓到「你那個防護擋不住」。我實測之後發現這條路根本走不通：把資料設成唯讀，別人可以把開關直接翻回來；改用更硬的做法可以擋住翻回，但只要複製或存檔還原一次，又變回可以改。

所以我換了守衛的位置：不去保證資料不被動，而是在使用它的入口重新驗算一次。這個機制規格裡本來就有，只是先前沒把它當主力。這樣就不依賴「沒人動過」這個假設。

同一輪還有一件我自己弄錯又自己修掉的：我前一輪寫了一條防護，會把「資料沒按時間排好」的呼叫方直接擋下來。實測後發現正常路徑不受影響，但直接呼叫的舊路徑會被新擋住——那是我為了修一個問題而弄紅另一條路。改成用一個與排序無關的驗算方式之後，兩邊都成立，那條防護整個可以刪掉。

閉合第五輪

兩家第一次講同一件事，而且講的是我自己弄出來的矛盾。 前四輪每次都是兩家吵架、我實測裁決；這一輪兩家不約而同指向同一處——我在上一輪換掉驗算方式時，改了說明段和破壞性測試清單，卻漏掉驗收清單裡那條舊的。結果同一份規格裡三個地方互相打架，照舊那條做就會把正常資料擋下來。

同一輪還被抓到我的驗算式本身有洞：那個式子是「拿序號去索引，看取出來的值對不對」，而 Python 的負數索引會從尾巴倒數，所以序號寫成 -1 時，取出來的值剛好對得上，錯的資料就這樣通過了。修法是在索引之前先檢查「是整數、落在範圍內、不重複、而且遞增」。

我自己那條也有下文：指紋因為先排序再計算，所以把順序打亂不會改變指紋；真正擋住順序被打亂的是另一道「必須遞增」的檢查，而那道檢查先前只存在於程式碼裡、規格從沒寫過。另一家獨立跑出同樣結論，還補證了「同一組數字裡，能通過遞增檢查的排法只有原本那一種」。兩道檢查合起來才沒有缺口，所以兩道都得寫進規格。

閉合第六輪

兩家提出的六條，沒有一條打在機制上。他們分別攻擊那個驗算式和「兩道檢查合起來」，都找不到能同時騙過兩道又改變結果的做法。六條全部是我前幾輪改寫後留下的舊句子——包括同一個被我刪掉的判準，用另一個名字又寫了回去。

這一輪我因此改變做法：不再逐條補，而是把那一節整個重寫成單一現行版本，把「某輪曾如何、為何不採某方案」全部移出到收斂檔，並把義務逐條編號，讓「有沒有漏掉」可以被逐條比對。下一輪只驗一件事：重寫有沒有漏掉任何已定案的義務。
