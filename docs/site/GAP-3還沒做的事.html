GAP-3 還沒做的事 — 逐條白話

這份回答三件事：是什麼、為什麼現在不做、接下來要怎麼處理。

技術版登記在 docs/IC_QUANT_GAP_REGISTRY.md（那邊是給我和委員看的，欄位是三值理由與觸發條件）。 這份是同一批東西的白話版，不是另一份清單——兩邊對不上就是我的錯，以技術版為準。

🔴 「為什麼不做」只有三種合法答案（你 2026-08-17 定的，不准寫「之後再說」）：

  • 被卡住（blocked-by）：有個前置條件不在，做了也是白做
  • 要先研究（needs-research）：做法本身沒定，硬做會做出一個錯的東西
  • 你裁定的（user-ruling）：你說過不做或改順序
  • （另有一種 cost：太貴而且現在沒有非做不可的理由——已經全部清掉了）

先講結論：一件是缺陷，其餘是殘留

缺陷 = 現在的行為是錯的。殘留 = 現在的行為是對的，只是還沒做到更好。 這兩者不能混在一起講，混了你就無從判斷哪個要緊。

治理／測試環境（跟產品無關） 5 條 不會

✅ 本次已清掉一條：B1-VERIFY-1（「收 epic 前要把兩套全量測試各再跑一次」） 已於 2026-09-06 履行——tests/api 867 通過、tests/governance 1739 通過， 失敗的那些經對等比較確認全部在動工前就已經在失敗。這條不再是欠帳。

一、🔴 唯一的缺陷 — 這條你要知道

G3-D1 匯出前篩選只有一組條件，正反例被同時截斷

是什麼：/search 匯出之前那個「篩選」，只有一組條件，而且同時套用在正例和反例上。

為什麼是錯的：如果你的條件引用了 future_*（未來幾根的報酬）欄， 那麼正例和反例會同時被結果截斷。後果是：

  • 反例不再是對照組（它們也是被結果挑過的）
  • 三組報酬表會三組皆正，看起來「怎麼選都贏」
  • 條件 IC 建立在照結果挑過的樣本上（統計上叫 range restriction ＋ collider bias， 偏誤方向不可預測——不是「偏高」或「偏低」，是不知道往哪偏）
  • 畫面上完全沒有提示

為什麼現在不做：你已經裁定了修法（2026-08-31），但那個修法不小——

  1. 正例、反例各自獨立條件，絕不共用
  2. 篩選不再兼差推導答案窗深度，改成直接問你「哪個 timeframe 的第幾根 bar 用來區分正反例」
  3. purge（切分時要隔開的距離）＝ 正反例深度取大者

第 2 點是關鍵：現在的深度是從條件反推出來的，而我自己記錄過四種反推不出來的情形。 這等於要重做匯出流程的一段規格，不是補一個 if。

接下來怎麼處理：這是下一張票，不是這張票的殘留。要做的時候： 先重開 /search 匯出段的規格（正反例雙條件 ＋ 深度改為明問），再走完整流程。 在那之前，如果你的篩選條件引用了 future_* 欄，那批事件的 IC 不要當真。

二、你看得到的四條殘留

這四條不影響正確性，但你在畫面上會遇到，先講清楚免得你以為是壞掉。

1. B5-SINGLECLASS-1 隨機對照批「全是 0」會被擋下來

是什麼：產隨機對照批時，如果抽出來那批的答案全部都是 0（或全部是 1）， 匯入會被拒絕，理由是 missing_control_group。

為什麼會遇到：你的事件越罕見，隨機抽一批的正例率就越低——低到 0 是很正常的。 而那正是最需要看 lift 的時候（「隨便挑 0%、我挑的 25%」才是強訊號）。

為什麼現在不做：missing_control_group 這條規則的原意是「使用者標註的一批要有正反例」。 隨機對照批算不算例外，沒有人裁定過。我可以直接放寬它，但那是弱化一個既有的檢查 ——這種事我不自己決定。

接下來怎麼處理：要你或委員會裁一句：「無條件抽樣批是否豁免 missing_control_group」。 裁完我改一行。在那之前，如果你撞到，把想抽的筆數調大或把門檻調低就會過。

2. B4-TIMEOUT-1 掃描網格的兩個逾時秒數是我判斷的，不是量出來的

是什麼：k/h 掃描網格有兩道保護——單格 60 秒、整體 900 秒逾時。

為什麼要講：benchmark 我只量到五階段（單格 6.9 毫秒）， 沒有量到每格的條件 IC（真正貴的那段）。所以我不能說「60 秒足以吸收合理的單格 IC」 ——那句話沒有數據支撐。現在那兩個數字是保守的上限，作用是讓卡死的格子一分鐘內被切掉。

為什麼現在不做：要量它得先有一個已物化的 feature run，在上面跑含 analyzer.analyze 的單格 p50/p95/p99。那是一次獨立的量測工作。

接下來怎麼處理：等你實際跑一次大網格。如果你發現正常的格子被逾時切掉， 那就是這個數字太小，告訴我，我拿你那次的實測值去凍結它。

3. B4-ORPHAN-WORKER-1 逾時的格子不會真的停下來

是什麼：單格逾時後，畫面會標它 unavailable、其餘格子照常， 但那個工作其實還在背景跑，會佔 CPU 到它自然結束。

為什麼現在不做：Python 沒辦法從外面殺掉一個執行緒（asyncio.wait_for 只取消等待， 不取消工作本身）。真正的修法是把單格改成子行程——那是另一個設計題，會動到整個掃描的架構。

接下來怎麼處理：短期沒有動作。如果你掃大網格時感覺機器變慢，這就是原因。 真要修得排一張「掃描改子行程」的票。

3b. B4-FACTORY-COST-1 掃描網格有一段固定開銷（110 格約 2.8 秒）

是什麼：掃描網格的每一格都會自己建一個分析器。codex 實測：建 110 次共 2.835 秒 （每次 25.8 毫秒），其中 2.216 秒花在重讀 YAML 設定檔上（每格都重讀一次）。

為什麼不直接快取分析器：因為那會讓第一輪那個嚴重問題復活—— 分析器帶著可變狀態，格與格之間共用就會互相污染（逾時的格子會改到別格正在用的東西， 而算出來的數字仍然合法、不會報錯）。

為什麼現在不做：兩個原因。①沒有已批准的時間門檻可以據以判斷「2.8 秒算不算高」 ——那要先量到含條件 IC 的整格成本，也就是上面那條 B4-TIMEOUT-1。 ②可行的方向是只快取「已驗證過的設定」（用檔案路徑／修改時間／契約版本當 key）， 分析器本身每格照樣新建——那是一個獨立的設計題，不是順手改。

接下來怎麼處理：跟 B4-TIMEOUT-1 綁在一起評估。等你實際跑一次大網格， 如果覺得慢，兩條一起量、一起修。

4. G3-R9 事件模式的「辨別表」顯示「沒有模型分數」

是什麼：/ic-analysis 事件模式的辨別表會顯示 not_computed：no_model_scores_in_event_pipeline，而不是數字。

為什麼現在不做：那張表要的是模型對每個事件打的分數， 而分數來自 ML 層／pattern 橋——那一層在你的成熟度地圖裡標的是「不完整」。 匯入管線本身不產生分數，沒有東西可餵。

接下來怎麼處理：等 ML 層那條線做起來。畫面已經誠實寫出原因，不是靜默空白。 /pending-features 頁面有它的占位卡。

三、規格本身有洞、我當場補的（3 條）

這三條的共同形態：規格沒寫到，我實作時當場補了一個 fail-closed 的做法， 但那個補法沒有經過規格輪的審查。它們現在行為是對的，欠的是「寫回規格」。

代號 規格沒寫到什麼 我補了什麼
B4-SPECGAP-1 「選到非法組合就把另一欄重設為契約預設值」——但契約的預設值本身就在那個非法組合裡，這方向無解 預設值合法就用它；不合法就取契約清單裡第一個合法值，並在畫面寫明原因
B5-SPECGAP-1 「按 period 分層」——但只給了一個起訖區間，那樣只會有一層；同一份規格另一處又寫「跨月分層」 分層粒度定為自然月（UTC），層的名字是「標的|週期|年-月|方向」
B1-KIND-1 端點回 422 時的 kind 字面（missing_/mixed_/invalid_decision_offset_bars）不在契約的 reason 清單裡 維持現狀——它是傳輸層的分類，不是資料層的 reason，兩者混在一起反而更糟

為什麼現在不做：規格檔（D-001）是已凍結的，重開它要跑三家蓋章。 為了一兩條 UI 規則重開一份凍結規格，成本遠大於收益。

接下來怎麼處理：下次因為別的原因重開那份規格時，順手把這三條寫回去。 這不是拖延——它們的行為已經對了、已經有測試守著、理由已經寫在契約檔的註解裡。

這幾條都是「測試證明力不足」，不是「程式有問題」。我列出來是因為 測試不夠強 = 以後改壞了不會有人發現，那是真的風險，只是不是現在的風險。
