查到的三件事

一、外面沒有更好的偵測器可以買。 最接近的開源專案在真實散文上試過：篩出 254 組候選、判定只有 1 組是矛盾， 專案自己寫下「訊號對成本的比值實際上是零」，然後把那個功能預設關掉。 GitHub 官方的 Spec Kit 也做同一件事，但明文寫死「只報告、不擋」。

二、我們現在的做法（兩家委員互相挑戰）已經是這條路的最強版本。 9/20 那兩輪就抓出 23 條我自己寫出來的矛盾。問題不是抓不到，是抓不穩， 所以不能拿來當「過／不過」的自動判定。

三、真正有效的是「同一件事只寫一次」，而我們只裝了 6.5%。 我們早就有這個機制（改一處、所有文件自動同步，手改會被擋）。 但它只裝在 14 份文件上，而且 18 個受保護的事實全部是治理自己的記帳—— EVENTSCAN、IC、Feature Factory 的任何裁定，一個都沒有。 這就是為什麼之前兩張文檔票花了很多時間卻沒效：它們加的是格式規則（摩擦），不是保護。

下一件事

兩條路，請你選一條。

路 A：先做 EVENTSCAN 寫規格（你原本排的主線） 條件成立時買入、持有 N 期的報酬，跟隨機買入比。方向與做法已定案， 完整說明見 EVENTSCAN方向與做法.md。 🔴 是「寫規格」不是「實作」——大票要走完整流程： 寫 SPEC → 兩家對抗審 → 凍結 → 寫 TODO → 兩家對抗審 → 凍結 → 分批實作 → 每批審碼。

路 B：先把「同一件事只寫一次」裝到量化主線 把 EVENTSCAN／IC／FF 的每個裁定登記成一個受保護的事實， 規格書、白話說明、路線圖三處都從同一份生成，改一處全同步、手改直接被擋。 不需要新建任何工具（機制已經在跑，只是沒裝上去），但要一條條把裁定搬進去。

我的建議是 A 先走，B 在寫 EVENTSCAN 規格的同時順手做—— 因為 EVENTSCAN 的九項裁定正是現在散在三個地方、最容易被我改漏的那批。
