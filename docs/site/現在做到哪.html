查到的三件事

一、外面沒有更好的偵測器可以買。 最接近的開源專案在真實散文上試過：篩出 254 組候選、判定只有 1 組是矛盾， 專案自己寫下「訊號對成本的比值實際上是零」，然後把那個功能預設關掉。 GitHub 官方的 Spec Kit 也做同一件事，但明文寫死「只報告、不擋」。

二、我們現在的做法（兩家委員互相挑戰）已經是這條路的最強版本。 9/20 那兩輪就抓出 23 條我自己寫出來的矛盾。問題不是抓不到，是抓不穩， 所以不能拿來當「過／不過」的自動判定。

三、真正有效的是「同一件事只寫一次」，而我們只裝了 6.5%。 我們早就有這個機制（改一處、所有文件自動同步，手改會被擋）， 但它只裝在 14 份文件上，18 個受保護的事實全部是治理自己的記帳—— EVENTSCAN、IC、Feature Factory 的任何決定，一個都沒有。

🔴 這件事的上限也要講清楚：那是零件型號表，不是組裝圖。 它管「同一個值不會在三份文件寫成三個樣」，不管架構對不對、零件怎麼接、為什麼這樣設計。 論述那一半外面沒有解，我們也沒有，只能靠委員審查，而且會漏。
