R3 複核輪的結果（2026-09-04）

三家的結論又不一致：composer 和 grok 說各自的問題都關閉了、可以往下走； codex 說有一條沒關、還多找到兩個。我取聯集全修——一家說有問題就修，不投票、 不用二比一壓過去。

沒關閉的那一條：我上一輪擋的是「兩列填了不同的決策位移」， 但一列填了、一列根本沒填的情況我的檢查會直接跳過沒填的那列，於是看起來「只有一個值」就放行了， 而分析實際用的是第一列（沒填）⇒ 有宣告的那些事件被對齊到錯的時間點。 🔴 這一格是我在派工單裡自己列出「我沒查」卻沒去查的那一格，codex 去查了、打中了。 同樣的模式這個 epic 已經發生第二次（上一輪的第 3 條也是）。

兩個新問題：

  1. 你沒選報酬量法時，畫面上「答案窗」欄顯示 1，但後端其實會照你這批宣告的深度跑（宣告 3 就跑 3）。 畫面上的數字和實際跑的不一樣。 我上一次只修掉了紅字誤導，沒修數字誤導。 現在改成：沒選時那格空白且不可編輯，旁邊寫明「由後端依這批宣告的深度決定」。 刻意不在畫面上自己算——那會變成同一條規則的第二份實作。
  2. 兩份程式註解把「是誰擋下混值」寫成錯的機制。註解寫錯正是上一輪第 1 條問題的成因之一，所以照改。

修的時候我自己的測試又抓到修法的洞：第一版把「沒填」和「型別錯」混為一談， 結果整批都是 true 這種壞值時反而被當成「大家都沒填」而放行。已拆成兩種拒絕理由。

一個查清楚的事實（沒有因此降級）：那條沒關閉的問題，正常匯入流程其實擋得住 （契約規定那一欄必填）。唯一能走到的路是「繞過匯入、直接寫檔的歷史批」。 我還是照修了，並把這件事寫進下一輪派工單交 codex 判「這樣還算不算阻擋」—— 不自己把別人的判定降級。

三家審碼抓到什麼（B-D1，2026-09-04）

三條真缺陷（都附委員的實跑證據）：

  1. 「這批答案哪來的」可以混著填而系統不擋（三家全員命中）

    • 一半的列填了、一半沒填 ⇒ 系統把「填了的那個」當成整批的答案來源

  2. 每列的「決策位移」可以不一樣，而分析只取第一列的值套用全批

    • 其餘事件會被對齊到錯的決策根，算出來的數字仍然合法、看不出異常
    • 已改成：混值就擋下不分析（要嘛拆批，要嘛等 k 的參數化上線）

  3. 我上一段做的「依深度自動選量法」根本沒接到畫面上

    • ⇒ 你宣告深度 3 的批，「持有」實際跑成 h=1。兩端都對，就是沒接上。

三條較輕的：凍結檔的 --check 沒驗「t0 是否仍等於登記處導出的值」（改了會悄悄失去覆蓋）； 「混情境先擋」的承諾在某條路徑上落空；「UI 比後端嚴」這個刻意設計沒有測試釘住（改掉不會紅）。

全部已修並補上可證偽的測試；破壞測試 15 種仍全紅。

派複核輪之前，我又抓到一個自己造成的缺陷（已修）

問題：上面第 3 條的修法是「使用者沒設定時，前端完全不送那個欄位」。 但這讓面板落到「認不出量法」那條分支，畫面顯示紅字「送出會被擋下」—— 而送出守衛只在「有設定」時才跑，所以其實送得出去、後端照你宣告的深度決定。 畫面講的跟實際發生的相反，這比原本的 bug 更容易誤導你。

修法：把兩種狀態分開。「還沒選」＝灰字中性提示（告訴你會由後端依深度決定）； 「選了一個算不出來的組合」＝紅字才會出現。 刻意不在畫面上自己算那個預設值——那會變成同一條規則的第二份實作，兩份遲早會不一樣。

另外補了一件該做而漏做的事：那六條修正當時沒有配破壞測試 （原有的 15 種破壞測試針對的是更早的實作）。現在補了第三批 7 種，每一種都確認會讓對應測試變紅。 六條修正＋這次的自查修正，各有一種破壞測試守著。

R4 複核輪的結果（2026-09-04）

R3 修完的三條，R4 又被打回兩條。這一輪最值得記的是委員的做法，不是找到什麼：

🔴 codex 拒絕替另外兩家背書。群集 D（註解寫錯）是 grok 和 composer 提的， codex 明寫「不代替兩家裁定；不得宣告本輪三件全 CLOSED」。 閉合輪的判定權屬於當初提出問題的那一位，第三方不能代簽——這跟「實作者不自審」是同一個道理。

新抓到的兩條：

  1. 我的測試斷言寫太鬆，剛好把一個真缺陷蓋住（P1）。 我寫「整批都沒填決策位移 ⇒ 應該仍然放行」，斷言寫成 in (0, None)——None 也算過。 codex 實跑證明：放行之後，程式會在更深的地方炸掉， 而使用者看到的是一個完全無關的錯誤訊息。 判準更正：「放行」根本不是值得保留的既有行為，它只是把錯誤推到更深處。 現在改成當場拒絕並說明「這批繞過了匯入驗證，請重新匯入」， 而且不替你猜一個你沒宣告過的決策位移（猜 0 就是替你做決定）。 🔴 寫鬆的斷言比沒有斷言更危險：它看起來有守，其實沒有。我已把所有新測試掃過一遍。

  2. 同一個數字在同一個畫面有第二處顯示，我只修了第一處（P2，codex 和 grok 各自獨立抓到）。 上一輪我把「答案窗」輸入框改成未選時空白，但同一面板下方那句 「本次答案窗 ＝ 1 根」還在報 1。同一個病第三次了。 這次除了修那一行，我把整個檔案的「答案窗」出現處全掃過（共 4 處）， 並加了一條「下方那句話的根數必須等於輸入框的值」的對證測試。

掃全檔時自己又發現一件：你一點選報酬量法，答案窗就會被定成 1， 所以「依你宣告的深度自動決定」其實只有在你完全不碰面板時才有效。 這個我沒有擅自改——要改就得讓畫面自己算深度，那又變成第二份實作。 登記成待辦（B1-DEPTH-1），並加測試把現況釘住，日後有人改動不會靜默發生。

三家意見不一致時我怎麼處理：composer 和 grok 說某條舊待辦「足以涵蓋」新問題， codex 說不行。我取比較嚴的那一版，另立一條新待辦。 理由：把一條很窄的裁定（「那 9 個測試檔不用遷移」）拿來蓋一個很寬的類別 （「任何繞過匯入的欄位損壞」），正是待辦理由被稀釋掉的典型走法。

順帶解決一半的老問題：codex 這輪跑了全套 API 測試——820 通過、4 條失敗， 四條都是本來就紅的（與本票無關）。這是我一直列為「太貴沒跑」的那一格，現在有數字了。

R5／R6 — 第 1 段收工（2026-09-04）

R5 又被打回一條，但這一條讓我看清自己的做法有問題。

負數的決策位移（-1）通過了我的檢查——它確實是整數——要到很深的地方才炸。 數一數：R3 我補「型別」、R4 補「沒填」、R5 補「負數」，每一輪我都在同一個地方手刻一條新規則， 而契約檔案裡從頭到尾就寫著這一欄是「整數、最小 0」。

手刻永遠補不完，因為值域是資料、不是程式碼——契約改了，手刻的那份不會跟著改。 所以這次不是再補一條，而是改成從契約讀：新增一個出口，把契約宣告的最小／最大值交出來， 連錯誤訊息裡那句「必須 >= 0」的數字都由它產生。以後契約改，程式和訊息會自己跟著改。

（過程中解耦檢查當場擋下我用錯的引入方式，改走正確的出口。這是機制在做事，不是我記得。）

🔴 然後破壞測試抓到我自己造的假貨：我寫了一條測試宣稱「證明值域來自契約」， 破壞測試把它換成手刻的「最小 0」——測試照樣綠。因為契約裡的值也是 0， 兩種寫法產生一模一樣的字串，那條測試根本什麼都沒證明。

判準記下來：一條宣稱「證明 A 來自 B」的測試，如果 A 在兩種做法下長得一樣，它就什麼也沒證明。 改成把契約的值臨時改成 2（跟手刻的 0 不同）再看行為變不變，才真的釘得住。

這件事的意義：抓到它的不是委員，是我自己跑的破壞測試。 如果這輪省掉那批破壞測試，那條假測試會一路綠著上線。這就是為什麼每條新測試都要配破壞測試。
