GAP-3 驗收清單 — 照著做就好

這份是給你照著操作的。 每一項都有三欄：你做什麼 → 你應該看到什麼 → 如果不是這樣代表什麼。 全部通過並簽字，GAP-3 才算收案（這是你自己定的規矩：未簽不收案）。

🔴 這是重寫版（8/29），不是 8/22 那份。舊版有兩項現在照做會失敗—— 不是程式壞了，是那兩件事被規格改掉了：

  • 舊版說「匯出前先選答案窗 N 根」→ 那個選項已移除，答案窗改在 IC 分析頁決定
  • 舊版說「匯出檔裡每筆含 label_value」→ 匯出檔已經不寫答案，答案改在分析當下才算

技術版在 docs/GAP3_UAT_CHECKLIST.md（簽字欄在那份，A 段機械檢查也在那份）。

開始之前

開兩個終端機視窗：

# 視窗 1：後端
source venv/bin/activate && python run_api.py

# 視窗 2：前端
cd frontend && npm run dev

瀏覽器開 http://localhost:3000。

要準備的東西：一份你自己標好正反例的 CSV（B6 會用到）。沒有也可以——B1–B5 會產生一份， 你把它轉成 CSV 就能用。

第一段：把事件匯出來（/search）

B1 ── 跑一次搜尋

你做什麼：開 /search，設好條件，按搜尋。

應該看到：結果列表出現。往下捲，底部有一整區匯出面板，裡面由上而下依序是： 匯出前篩選 → 筆數 → 附帶報酬欄 → 這批事件的五個設定 → 這批匯出實際會帶什麼 → IC decay 的說明 → 兩顆按鈕（「導出CSV檔案」「匯出事件契約 JSON」）。

不是這樣代表什麼：如果只看到兩顆按鈕、中間那幾區都沒有，代表你開的是舊版前端—— 重新 npm run dev。

B2 ── 匯出前篩選與筆數

你做什麼：在「匯出前篩選」按「新增條件」，挑一個數值欄（例如 price_change）， 設一個門檻。再按一次「新增條件」加第二條。

應該看到：

  • 每加一條，上方筆數即時變：將匯出 N 筆（原 M 筆）／你聲明的正例 X／反例 Y
  • X + Y 要等於 N（如果有些列沒有正反例標記，會另外顯示「另有 Z 筆沒有標記」， 而且會告訴你 CSV 仍然會含那幾筆、事件 JSON 不會）
  • 把條件全部刪掉 ⇒ N 回到 M

不是這樣代表什麼：如果 X + Y ≠ N 而且沒有任何說明，那是計數錯誤，記下來告訴我。

🔴 這一項要特別看：篩選面板只挑選要匯出哪幾列，不會改任何欄位的值。 如果你看到某一欄的數字因為加了篩選而變了，那是嚴重缺陷。

B3 ── 這批事件的五個設定（新的）

你做什麼：找到「這批事件的五個設定」那一區，每一個下拉都點開看看。

應該看到：五個控制項——scenario／control_kind／entry_price_semantic／ label_return_mode／decision_offset_bars。而且：

你會看到 為什麼
scenario 只有 C 能選，A／B／two_stage 是灰的，而且下面寫著為什麼 那三種是「預測型」，需要另外一套產生答案的東西，本批沒做
control_kind 有三個能選，platform_random_bars 是灰的並寫著 not_implemented_platform_random_bars 契約層就恆拒這個值
entry_price_semantic 只有 trigger_close 能選 分析層目前只支援這一種組合
label_return_mode 只有 close_to_close 能選 同上
decision_offset_bars 是數字框但打不進去（唯讀），固定 0，旁邊寫著理由 同上
每個下拉底下都有一行白話說明 那行字是從契約檔直接取的，不是另外寫的

試著違規：把游標點進 decision_offset_bars 打 3。

應該看到：打不進去（唯讀）。

🔴 不是這樣代表什麼：如果你真的把它改成 3 了，那就是三家審查員在 R3 抓到的那個缺陷復活了 （我宣稱鎖死卻只加了提示屬性）。記下來告訴我。

B4 ── 這批匯出實際會帶什麼（七項，新的）

你做什麼：看「這批匯出實際會帶什麼（你沒選過但一直存在的設定）」那一區。

應該看到 七行：scenario / control_kind / 進場價語意 / 報酬算法 / 決策位移 / lookahead 深度 / purge 下界。而且：

  • 每一行都是活的：回到 B3 把 control_kind 換一個值，這一區的那一行當場跟著變
  • 深度和 purge 是逐個週期各一行：如果你的結果含 1h 和 12h 兩種週期， 就會看到 lookahead 深度（1h）＝… 和 lookahead 深度（12h）＝… 兩行，不是一行
  • 深度那行會告訴你來源是哪幾個欄位（就是你在 B2 設篩選時引用到的欄）
  • 沒設任何篩選時，深度那行會寫「來源＝…：無（沒有設篩選條件）」

不是這樣代表什麼：如果換了設定但那一區文字不動，代表它顯示的是寫死的預設值而不是你的實際設定 ——那是「說一套做一套」，記下來。

B5 ── 匯出事件契約 JSON

你做什麼：按「匯出事件契約 JSON」。

應該看到：

  1. 可能先跳一個確認框，逐個附帶欄告訴你「future_1bar_return：X/Y 筆可算、Z 筆因資料尾端不足而缺」 —— 缺欄不會擋你匯出，按確定即可
  2. 下載兩個檔：
    • gap3_events_<日期>.json —— 事件本體
    • gap3_events_<日期>.source.json —— 來源檔（它的 sha256 就是每筆的 source_file_digest）

打開那個 JSON 檢查（用任何文字編輯器）：

應該有 應該沒有
event_id、symbol、timeframe、t0（13 位數的毫秒）、label（0 或 1） 🔴 label_value（答案）——匯出檔不寫答案了
scenario、control_kind、entry_price_semantic、decision_offset_bars、direction
label_definition（裡面有 window.horizon_bars、label_return_mode、filters）
lookahead_bars_declared（逐週期的深度）
future_1bar_return 之類的附帶欄（純供你在 Excel 看）

🔴 label_value 不在裡面是對的，不是漏掉。答案改在 IC 分析當下才算—— 這樣同一批事件可以用不同的答案窗重複分析，不必重新匯出。

如果你沒設任何篩選條件：按下去應該會被擋住並跳訊息說深度還沒取得—— 等一兩秒再按就會成功。那是刻意的：拿不到深度就不讓你匯出。

B6 ── IC decay 的邊界說明

你做什麼：看匯出面板最底下那段黃字。

應該看到：它明白告訴你四件事——decay 曲線不是本批交付、附帶的 future_* 欄 不會進 IC 計算、要換答案窗請去 IC 分析頁改、不必再匯出一次、整條曲線等 GAP-6。

不是這樣代表什麼：如果它叫你「重新匯出」來換答案窗，那是錯的（那正是這段話要否定的事）。

第二段：把事件匯進系統（/data-preparation）

B7 ── 用 JSON 匯入（先只驗證）

你做什麼：開 /data-preparation → 「匯入事件（GAP-3 新契約）」→ 選 B5 下載的 gap3_events_*.json → 勾「僅驗證不落檔」 → 送出。

應該看到：「驗證通過 N 筆（未落檔）」。

故意弄錯：把 JSON 裡某一筆的 label 改成 2 再上傳。

應該看到：逐列的拒收原因表格（哪一列、哪個欄位、什麼原因），不是空白畫面、 不是 500 錯誤。

B8 ── 真的匯進去

你做什麼：取消「僅驗證」，再送出一次。

應該看到：顯示 import_id；右側「已匯入事件批」列表多出這一批， 每列有 import_id／筆數／匯入時間／symbols／timeframes。

B9 ── 用 CSV 逐欄對映匯入（新的）

你做什麼：用「CSV 欄名對映匯入」那一區，選一份你自己的 CSV。

應該看到（依序）：

  1. 前 5 列預覽 ＋ 全部欄名
  2. 一組下拉，讓你把 CSV 的欄對到契約欄（symbol／timeframe／t0／label…） —— 🔴 每一個下拉的初始值都是「未選」，系統不會幫你猜哪一欄是 label
  3. 這批的五個設定（同 B3，但這裡 scenario 四個值全部可選）
  4. 「批次預設（JSON 物件）」文字框
  5. 「你聲明的正例 X 筆／反例 Y 筆」＋一個必須勾的確認框

試著違規一：不要勾那個確認框，直接按「匯入」。

應該看到：被擋下來並列出原因，而且完全沒有任何網路請求發出（開瀏覽器開發者工具的 Network 分頁看，應該一片空白）。

試著違規二：在「這批的五個設定」選了 scenario = A，同時在「批次預設」文字框裡 也寫 {"scenario": "B"}。

應該看到：被擋下來，訊息說 scenario 同時由兩個地方給值、請只留一個來源 —— 🔴 系統不會替你決定誰優先。

試著違規三：把 decision_offset_bars 打成 1.9。

應該看到：被擋下來，說必須是整數。🔴 不應該看到它自己變成 1 （那是 R4 抓到的「靜默改值」缺陷）。

B10 ── 答案窗宣告

你做什麼：B9 對映齊全並勾了確認之後，往下看「答案窗宣告」那一區。

應該看到：逐個週期各一個輸入框，預設值是該檔案能支援的最大深度； 下方列出你的條件引用到哪些未來欄。

試著違規：把某個週期的數字調低。

應該看到：出現一個必須勾選的聲明（大意是「我知道這樣可能不可驗證」），不勾就送不出去。

B11 ── 舊格式擋得住

你做什麼：拿一份舊的三欄 CSV（symbol／timestamp／Positive_case）丟進「匯入事件」。

應該看到：拒收，原因 legacy_schema_detected，並附欄位對照的搬遷提示。

反過來：把 B5 的新 JSON 轉成 CSV 丟進舊的「導入案例」。

應該看到：拒收，原因 new_schema_on_legacy_endpoint，訊息指向新端點。

🔴 兩個方向都要試——只試一個方向的話，一個「永遠拒收」的實作也會看起來正常。

B12 ── 刪掉一批事件（新的）

你做什麼：在「已匯入事件批」列表，對某一批按刪除。

應該看到：確認框，裡面有：

  • 「確定要刪除這批事件嗎？此操作無法撤銷。」
  • 該批的 import_id、筆數、匯入時間
  • 如果這批在這台瀏覽器上曾被拿去分析過，會多一段黃色警語： 「在這個瀏覽器上，這批事件曾被拿去分析：刪除後，引用它的分析結果將無法重現。仍可刪除。」 並註明這筆紀錄只存在本機

先按取消：列表沒有任何變化，而且沒有發出刪除請求（Network 分頁確認）。

再按確定：該批從列表消失。

驗殘留：

ls data_cache/events/ | grep <剛才那個 import_id>

應該看到：空的（一個檔都不剩）。

第三段：拿事件去分析（/ic-analysis）

B13 ── 切到事件模式

你做什麼：開 /ic-analysis，分析模式選「Event-Driven 模式」。

應該看到：出現「從已匯入案例選事件（GAP-3）」下拉。 沒匯入過任何批的話，顯示「尚未匯入任何事件批——請先到『數據準備』用新契約匯入。」

B14 ── 選一批：批次事實 vs 分析參數（新的，這是這批最重要的觀念）

你做什麼：下拉選 B8 匯入的那批。

應該看到 兩個分開的區塊：

區塊一「這批事件的事實（不可在這裡改）」——五行： scenario／control_kind／direction／t0（筆數＋最早最晚時間）／label（正反例各幾筆）。

試著違規：想辦法點進去改任何一行。

應該看到：改不了——那一區裡連一個可以打字或下拉的元件都沒有。

區塊二「這次分析要用的參數（只影響這一次分析，不會寫回事件批）」——四項：

  • 答案窗 horizon_bars：可以自由填任意正整數，🔴 初始值一定是 1
  • entry_price_semantic／label_return_mode：只有一個值能選，其餘灰掉並寫理由
  • decision_offset_bars：唯讀鎖 0

🔴 horizon_bars 初始值必須是 1。如果你匯入的那批 label_definition.window.horizon_bars 是 3，這裡還是要顯示 1——那個 3 是「深度宣告」不是「答案窗」，兩件事不能混用。

B15 ── 改分析參數不會動到事件批

你做什麼：把答案窗改成 7，跑一次分析。跑完之後回到 /data-preparation， 查看同一批的內容。

應該看到：那批的 label_definition.window.horizon_bars 沒有變（還是原本的值）。

🔴 不是這樣代表什麼：如果它被改成 7，代表分析參數回寫了事件批—— 那會讓「同一批事實」隨著每次分析而改變，是這一整套分層要防的事。

B16 ── 事件後報酬表：正／反／全體三組（新的）

你做什麼：跑完分析後，看「事件後報酬表」。

應該看到：三組垂直排列——

  1. 正例組（label = 1）
  2. 反例組（label = 0）
  3. 全體組（正＋反）

每組各有一張表，逐個 horizon 一列，欄位是 mean／median／win_rate／n／n_eff。 表頭每個欄位名都可以滑上去看它的白話定義。

檢查一件事：正例組的 n ＋ 反例組的 n，應該等於全體組的 n。

如果你匯入的那批 control_kind 不只一種（例如你手動混了兩種來源的反例）：

應該看到：全體組不給數字，而是顯示 not_computed：mixed_control_kind_in_batch， 滑上去會告訴你「平台不取多數決，要看全體組請把不同來源的反例分成不同批」。 🔴 正例組與反例組仍然正常顯示——control_kind 只影響全體組。

不是這樣代表什麼：如果全體組給了一張空表（全是 0 或 —）而不是原因，那是錯的 ——空表會讓你以為「算出來就是 0」。

B17 ── 條件 IC 真的算得出來（這是本批補的洞）

你做什麼：在同一批上跑分析，找報告裡的「條件 IC」段。

應該看到：有數值。

🔴 背景：在這批之前，從 /search 匯出的事件永遠算不出條件 IC—— 因為匯出檔不含答案，而分析端也還沒開始算，兩頭都沒有。 現在答案在分析當下由後端產生，所以這條路才通。

如果顯示 unavailable：missing_label_value：代表你用的是手動 CSV 匯入而且沒帶答案欄 ——那是正常的（系統只照抄你給的），不是缺陷。

B18 ── 特徵 run 沒涵蓋事件期會被擋（新的）

你做什麼：選一個時間範圍明顯比事件期短的特徵 run（例如事件在 2024 年， run 只涵蓋 2025 年），按開始分析。

應該看到：被擋下來，訊息說特徵 run 的時間範圍不涵蓋事件期。

反過來也要試：選一個確實涵蓋事件期的 run。

應該看到：正常跑起來。

🔴 兩個方向都要試——只試前者的話，一個「永遠擋」的實作也會看起來正常。

B19 ── 特徵太多會在啟動前被擋（新的）

你做什麼：如果你手上有超過 80,515 個特徵的 run，選它並按開始分析。

應該看到：在任務啟動之前就被擋下來，訊息會告訴你： 這個 run 有幾個特徵、上限是多少、為什麼擋（記憶體會爆）、 上限是實跑量測出來的、以及這個 run 目前無法分析。

🔴 訊息不應該叫你「去縮減特徵數」——系統沒有提供那個介面，那樣講等於指路到死巷。

沒有那麼大的 run 就跳過這項，註明「無可用樣本」即可。

B20 ── 切回全域模式

你做什麼：分析模式切回「Global」。

應該看到：事件下拉與所有事件專屬區塊消失；全域分析照常運作、結果與以前一致。
