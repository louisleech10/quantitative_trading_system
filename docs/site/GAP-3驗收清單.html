GAP-3 驗收清單 — 照著做就好

這份是給你照著操作的。 每一項都有三欄：你做什麼 → 你應該看到什麼 → 如果不是這樣代表什麼。

🔴 2026-08-31 起，B3 必定不會過——你裁定灰色項目要真的做出來、不接受永久灰著。 所以這份清單現在的用途是驗這一批做的東西對不對， 不是「全部打勾就結案」。結案條件已改變，見下方兩處標紅的待辦 （匯出前篩選之設計缺陷、五個設定之灰色項目）。

🔴 這是重寫版（8/29），不是 8/22 那份。舊版有兩項現在照做會失敗—— 不是程式壞了，是那兩件事被規格改掉了：

  • 舊版說「匯出前先選答案窗 N 根」→ 那個選項已移除，答案窗改在 IC 分析頁決定
  • 舊版說「匯出檔裡每筆含 label_value」→ 匯出檔已經不寫答案，答案改在分析當下才算

技術版在 docs/GAP3_UAT_CHECKLIST.md（簽字欄在那份，A 段機械檢查也在那份）。

開始之前

開兩個終端機視窗：

# 視窗 1：後端
source venv/bin/activate && python run_api.py

# 視窗 2：前端
cd frontend && npm run dev

瀏覽器開 http://localhost:3000。

你做什麼：在「匯出前篩選」按「新增條件」，挑一個 t0 可觀測的數值欄 （例如 volume_multiplier），門檻用小數。再按一次「新增條件」加第二條。

應該看到：

  • 每加一條，上方筆數即時變：將匯出 N 筆（原 M 筆）／你聲明的正例 X／反例 Y
  • X + Y 要等於 N（若有列沒有正反例標記，會另外顯示「另有 Z 筆沒有標記」， 並告訴你 CSV 仍會含那幾筆、事件 JSON 不會）

  • X + Y ≠ N 且無說明 ⇒ 計數錯誤

🔴 本項已知的設計缺陷（2026-08-31 使用者裁定；驗收時避開，不是驗它）

缺陷：匯出前篩選只有一組條件、同時套用在正例與反例上。 搜尋階段本來就分開（search_task_service.py:184 有 negative_conditions）， 是匯出前篩選把它們壓回同一組。

後果：條件一旦引用 future_* 欄，正例與反例會同時被結果截斷 ——反例不再是對照組，三組報酬表會三組皆正，看起來「都贏」； 條件 IC 也建立在被結果挑過的樣本上（range restriction ＋ collider bias，偏誤方向不可預測）。 畫面上沒有任何提示。

已裁定的修法方向（使用者定）：

  1. 正例與反例各自獨立的篩選條件，絕不共用
  2. 匯出前篩選不再兼差推導答案窗深度；深度改為直接問使用者 「哪個 timeframe 的第幾根 bar 用來區分正反例」
  3. purge ＝ 正例深度與反例深度取大者

為什麼直接問比推導好：現行由篩選條件反推深度（Task 2.1b）， 程式自己記著四種抽不出引用欄的失敗形態，抽不出來最後還是要問使用者； 而且使用者若在系統外標記（例如用 Excel 依未來報酬標），篩選面板裡什麼都沒有 ⇒ 推不出深度、purge 會是 0，沒有任何東西會喊。直接問沒有這個破口。

排程：見 docs/IC_QUANT_GAP_REGISTRY.md 之 GAP-3 缺陷登記。

🔴 上面那三條修法方向已於 2026-09-02 被你自己的新裁定取代：不是「改成兩組條件」， 而是整區移除。第 2、3 點（深度直接問、purge 取大者）仍然成立，那是移除之後的做法。
