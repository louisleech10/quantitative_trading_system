EVENTSCAN — 條件掃描 → 持有報酬 vs 隨機對照

這份是給你看的方向說明，不是規格。 你看過同意，我才去寫規格。 依據＝2026-09-20 委員唯讀偵察（composer 已交件、codex 進行中）＋我自己的讀碼查證。 🔴 文中所有「數字」分兩類：標「實查」的是我實際從 repo／資料讀出來的；標「示意」的是排版用的假數字，不是實測結果。

一、一句話

你設一個條件，系統在 K 線上找出所有符合的時點，算「從那時買入、持有 N 根之後賺多少」，再跟「隨機挑同樣多的時點、持有同樣久」比。

二、名詞對照（後面會一直用）

白話 系統裡的說法 意思
根 bar 一根 K 線。1h run 一根＝1 小時，12h run 一根＝12 小時
觸發點 事件 / event，時間點叫 t0 條件成立的那一根
觸發批 事件批 / event batch 一次掃描找出的所有觸發點，打包成一批
對照批 隨機對照批 / random control batch 隨機挑的時點，用來當「不挑時機」的基準
持有期 horizon（h） 買入後持有幾根。可以一次看好幾個（你要的複選）
答案欄 label（0 或 1） 這次「算不算成功」。你不用填，系統自己算
算好的特徵 FF run / Feature Factory run 事先算好的所有指標（EMA、RSI、MACD…），存在檔案裡

第 2 步：你選持有期（可以複選）

你 2026-09-20 裁定：用「根」計算，但畫面要顯示大約幾天；而且要支援複選。

所以畫面會長這樣（示意）：

持有期（直接輸入，逗號分隔，要幾個都行）
  ┌─────────────────────────────┐
  │ 5, 10, 30, 55               │
  └─────────────────────────────┘
  → 5 根 ≈ 5 小時 ｜ 10 根 ≈ 10 小時 ｜ 30 根 ≈ 1.3 天 ｜ 55 根 ≈ 2.3 天

不是勾選清單（你 2026-09-20 裁定）：直接打字輸入，想看幾個就打幾個，不受預設選項限制。 你一邊打，底下就即時顯示每個數字大約是多久。

換算由系統算：根數 × 週期長度。同樣打 55，在 12h run 上會顯示「≈ 27.5 天」。

第 3 步：系統掃描

在 20,352 根裡逐根求值你的條件，找出所有成立的根。

假設找到 340 根（示意）。

第 4 步：系統填 label（你不用做任何事，也不會被問任何門檻）

🔴 你 2026-09-20 裁定：完全不要門檻，也不會給。 這一步照你的裁定設計。

匯入契約強制每筆要有 label（0 或 1），而且一批裡必須兩類都有——這是硬的， 實查 momentum/Analysis/contracts/event_import_contract.json 的 required_fields，繞不過去。

所以 label 用漲跌的正負號填：

  • 報酬 > 0 → label = 1
  • 報酬 ≤ 0 → label = 0

這不是門檻，是漲跌的定義。 沒有任何數字要你設定，畫面上也不會出現門檻欄位。

🔴 誠實講：這個 label 對你要的統計數據一點貢獻都沒有（勝率是另外從報酬直接算的，見第 6 步）。 它純粹是匯入契約的形式要求，你在畫面上完全不會看到它。

如果你連這個內部欄位都不想要，另一條路是完全不走事件匯入、另建一條掃描→報酬統計的路徑。 你看到的數字會一模一樣，但既有的未來資料防護、時點對齊檢查全部用不到，等於一條沒護網的平行路。 我不建議，但這是你的選擇。

第 5 步：系統產一批隨機對照

從同一個 run 隨機挑 340 根（跟觸發批同樣多），規則：

  • 避開觸發點附近（前後各留緩衝，免得對照組其實也在條件成立的區間裡）
  • 同一個標的、同一個週期、同一段期間

第 5 步：系統產一批隨機對照

從同一個 run 隨機挑 340 根（跟觸發批同樣多），規則：

  • 避開觸發點附近（前後各留緩衝，免得對照組其實也在條件成立的區間裡）
  • 同一個標的、同一個週期、同一段期間
  • 亂數種子固定 → 同樣的設定重跑會得到一模一樣的結果

第 6 步：兩批各自算報酬，並排給你看

報酬公式（實查 momentum/Analysis/event_samples/tables.py）：

報酬 = (出場那根的收盤價 − 進場價) / 進場價

做空會反號。資料不夠長的事件（例如最後 55 根之內的觸發點算不出 55 根報酬）直接排除，不會灌 0 拉低平均。

🔴 「進場價」有兩種算法，這件事要先講定（codex 2026-09-20 查出）：

口徑 進場價是什麼 白話
ret_entry 依設定的「進場語意」取價（預設＝觸發那根的收盤價） 「條件成立那根收盤時買進」
ret_label_anchor 一律用觸發那根的收盤價當基準 固定基準，不隨設定變

兩個算出來的平均都合法，但不是同一件事。如果不講清楚用哪個，觸發批跟隨機批可能各用一個口徑去比，數字會失真。

我的建議：兩批一律用同一個口徑，並在畫面上標出來是哪個。這條要寫進規格鎖死。

🔴 上一版我寫「勝率是 label 加總得來的」——那是錯的，我查了程式才發現。 勝率是直接從報酬的正負算的，跟 label 無關。

這件事讓 label 的定位更清楚了：它對你要的統計數據一點貢獻都沒有，純粹是匯入契約的形式要求。 你看到的每一個數字都是從報酬直接算出來的。

其他兩點：

  • 筆數會隨持有期變少（340→335），因為資料尾端算不出長持有期的報酬，那些事件直接排除不灌 0
  • 為什麼要中位數和標準差：平均值會被少數極端值拉走。中位數告訴你「典型情況」，標準差告訴你「有多不穩」——只看平均會誤判

這張表就是你要的東西。

缺的四塊

# 缺口 白話
1 掃描函式沒有 API 接口 函式在，但 api/ 裡零個呼叫者——前端根本碰不到它
2 條件讀不到 FF 欄位 「讀特徵表」和「求條件」兩端都有，中間沒接：沒有任何程式把 FF 的欄位名註冊給條件引擎。🔴 而且現在寫錯欄名不會報錯——找不到該欄時條件直接判「不成立」，你會得到「零筆命中」而不是錯誤訊息（codex 查出）。這條必須在規格裡改成報錯，否則你永遠分不清「條件真的沒成立」和「欄名打錯」
3 比較比的是達標率，不是報酬 現有比較端點回「觸發批裡 label=1 佔幾成 vs 隨機批佔幾成」，不是平均報酬。而且它常常是灰的——它要求觸發批帶「標籤規則收據」（label_rule），一般匯入沒有，就回「無從確認兩批用同一條規則」而不並排
4 隨機抽樣現在不公平 見下表
5 統計欄位差兩個 現成的有筆數／平均／中位數／勝率／信賴區間；標準差與最好／最差沒有，要加（實查 tables.py:118-131）

缺口 4 細項（四項都要修）

項 現況（實查） 應該是
抽幾筆 前端預設 100 筆，不跟著觸發批 跟觸發批同筆數
候選資格 只看單一答案窗長度 看你選的最長持有期

期間池 取自觸發批最早～最晚的 t0 應為整個 run 的期間

五、做法：六步

  1. 條件引擎吃 FF 欄位——把讀到的特徵表欄位名註冊給條件引擎，讓你能寫 close_1h_trend_EMA_5 > close_1h_trend_EMA_10。並且欄名打錯要報錯，不能靜默回零命中
  2. 掃描函式接上 API——條件 → 事件批 → 匯入
  3. 報酬表補兩個統計量——加上標準差與最好／最差
  4. 產隨機對照批——走既有端點，修掉缺口 4 的四項
  5. 比較端點改成比報酬——現在只讀 label 算達標率，要改成讀報酬表並排全部統計量
  6. 前端——掃描設定畫面（持有期直接輸入、即時顯示約幾天）＋ 兩組統計並排的表（現在沒有並排元件）
