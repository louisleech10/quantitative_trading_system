EVENTSCAN — 條件掃描 → 持有報酬 vs 隨機對照

這份是給你看的方向說明，不是規格。 你看過同意，我才去寫規格。 依據＝2026-09-20 委員唯讀偵察（composer 已交件、codex 進行中）＋我自己的讀碼查證。 🔴 文中所有「數字」分兩類：標「實查」的是我實際從 repo／資料讀出來的；標「示意」的是排版用的假數字，不是實測結果。

一、一句話

你設一個條件，系統在 K 線上找出所有符合的時點，算「從那時買入、持有 N 根之後賺多少」，再跟「隨機挑同樣多的時點、持有同樣久」比。

二、名詞對照（後面會一直用）

白話 系統裡的說法 意思
根 bar 一根 K 線。1h run 一根＝1 小時，12h run 一根＝12 小時
觸發點 事件 / event，時間點叫 t0 條件成立的那一根
觸發批 事件批 / event batch 一次掃描找出的所有觸發點，打包成一批
對照批 隨機對照批 / random control batch 隨機挑的時點，用來當「不挑時機」的基準
持有期 horizon（h） 買入後持有幾根。可以一次看好幾個（你要的複選）
答案欄 label（0 或 1） 這次「算不算成功」。你不用填，系統自己算
算好的特徵 FF run / Feature Factory run 事先算好的所有指標（EMA、RSI、MACD…），存在檔案裡

第 1 步：你寫一個條件

你原本舉的 EMA5 > EMA10 > EMA30 不能直接用——因為這個 run 裡沒有 EMA_30。

這是「短期均線在中期之上、中期在長期之上」——多頭排列，跟你原本的意思一樣，只是用 34 代替 30。

🔴 那你怎麼知道有哪些欄位、名字怎麼拼？（你 2026-09-20 提問）

這是真問題。光這一個 run 就有 18 萬個以上的欄名（實查：close_1h_ 開頭的就有 32,747 個）， 平鋪一張清單給你完全沒用。

好消息是欄名完全有結構：

close_1h_trend_EMA_5
 │     │    │     │  └ 參數（5）
 │     │    │     └ 指標（EMA）
 │     │    └ 類別（trend）
 │     └ 週期（1h）
 └ 來源欄（close）

實查這個 run 的五個層級各有什麼：

層級 有哪些（實查）
來源欄 close、volume、hlc、hl、tr、ms
週期 1h、12h（這個 run 同時有兩個週期）
類別 trend、momentum、statistics、Lag…
指標 見上面的家族表
參數 每個指標各自的週期數，例如 EMA 有 14 個

為什麼會到 18 萬：因為還有兩兩組合的衍生欄，例如 close_12h_momentum_CMO_13_144_Cross（CMO13 與 CMO144 的交叉）、..._Ratio（比值）。

所以畫面要這樣做（這是本票要新做的東西）：

  1. 逐層下拉：選來源欄 → 選週期 → 選類別 → 選指標 → 選參數。每一層只有幾個到幾十個選項， 選完自動把正確欄名填進條件式。你永遠不用自己拼字串。
  2. 打字搜尋：想直接打 EMA 就跳出所有含 EMA 的欄位，選一個貼進去。
  3. 打錯要報錯：現在系統找不到欄位時直接判「條件不成立」，你會看到「零筆命中」而不是錯誤訊息 （缺口 2）。本票會改成明確報錯並告訴你最接近的欄名。

現況：後端已經有 GET /api/v1/ic/features/list（給 標的＋週期＋run識別碼，回該 run 的全部欄名）， 前端也有呼叫它的程式（fetchAvailableFeatures）。缺的是上面這三件事——現在只能拿到一整包平鋪清單。

第 2 步：你輸入持有期

你 2026-09-20 裁定：用「根」計算，但畫面要顯示大約幾天；而且要支援複選。

所以畫面會長這樣（示意）：

持有期（直接輸入，逗號分隔，要幾個都行）
  ┌─────────────────────────────┐
  │ 5, 10, 30, 55               │
  └─────────────────────────────┘
  → 5 根 ≈ 5 小時 ｜ 10 根 ≈ 10 小時 ｜ 30 根 ≈ 1.3 天 ｜ 55 根 ≈ 2.3 天

不是勾選清單（你 2026-09-20 裁定）：直接打字輸入，想看幾個就打幾個，不受預設選項限制。 你一邊打，底下就即時顯示每個數字大約是多久。

換算由系統算：根數 × 週期長度。同樣打 55，在 12h run 上會顯示「≈ 27.5 天」。

第 3 步：系統掃描

在 20,352 根裡逐根求值你的條件，找出所有成立的根。

假設找到 340 根（示意）。

第 4 步：系統填 label（你不用做任何事，也不會被問任何門檻）

🔴 你 2026-09-20 裁定：完全不要門檻，也不會給。 這一步照你的裁定設計。

匯入契約強制每筆要有 label（0 或 1），而且一批裡必須兩類都有——這是硬的， 實查 momentum/Analysis/contracts/event_import_contract.json 的 required_fields，繞不過去。

所以 label 用漲跌的正負號填：

  • 報酬 > 0 → label = 1
  • 報酬 ≤ 0 → label = 0

這不是門檻，是漲跌的定義。 沒有任何數字要你設定，畫面上也不會出現門檻欄位。

🔴 誠實講：這個 label 對你要的統計數據一點貢獻都沒有（勝率是另外從報酬直接算的，見第 6 步）。 它純粹是匯入契約的形式要求，你在畫面上完全不會看到它。

如果你連這個內部欄位都不想要，另一條路是完全不走事件匯入、另建一條掃描→報酬統計的路徑。 你看到的數字會一模一樣，但既有的未來資料防護、時點對齊檢查全部用不到，等於一條沒護網的平行路。 我不建議，但這是你的選擇。

第 5 步：系統產一批隨機對照

從同一個 run 隨機挑 340 根（跟觸發批同樣多），規則：

  • 避開觸發點附近（前後各留緩衝，免得對照組其實也在條件成立的區間裡）
  • 同一個標的、同一個週期、同一段期間

第 5 步：系統產一批隨機對照

從同一個 run 隨機挑 340 根（跟觸發批同樣多），規則：

  • 避開觸發點附近（前後各留緩衝，免得對照組其實也在條件成立的區間裡）
  • 同一個標的、同一個週期、同一段期間
  • 亂數種子固定 → 同樣的設定重跑會得到一模一樣的結果

第 6 步：兩批各自算報酬，並排給你看

報酬公式（實查 momentum/Analysis/event_samples/tables.py）：

報酬 = (出場那根的收盤價 − 進場價) / 進場價

做空會反號。資料不夠長的事件（例如最後 55 根之內的觸發點算不出 55 根報酬）直接排除，不會灌 0 拉低平均。

🔴 進場價用哪一根、哪個價——這一條交委員會，還沒定案。

你的想法（2026-09-20）：用條件成立那根的下一根開盤價（系統裡叫 next_open）。 你同時聲明：這只是想法，沒深入評估是否有風險、統計數據或量化金融計算上的誤區。

我查到的現況：next_open 系統已經支援——實查 momentum/Analysis/event_samples/alignment.py:102-106， 取 t0_idx + 1 那根的 open，資料不夠（t0 是最後一根）就標 missing_bar 排除。 五個可選值為 trigger_open／trigger_close／next_open／decision_bar_open／decision_bar_close。

我為什麼覺得你的直覺有道理：條件要用到 t0 那根的收盤價才算得出來（EMA 是收盤價算的）。 如果進場價用 t0 的收盤價，等於假設「收盤瞬間同時算完指標並成交」。 用下一根的開盤價比較接近真的買得到的價格。

但這正是要交委員會的原因——我不是量化金融專家，下面幾件事我沒有能力自己判斷： 跳空風險怎麼處理、不同選擇會不會讓報酬統計產生系統性偏誤、 隨機對照批是否必須用完全相同的進場語意、事件研究的標準做法是什麼。 這一條在委員會給出結論前不算定案。

另外系統有一個並列揭露的口徑 ret_label_anchor（一律以 t0 收盤價為基準，不隨設定變）， codex 2026-09-20 查出兩者並存。不論最後選哪個：觸發批與隨機批一律用同一個，且畫面標明是哪個， 否則兩批各用一個去比，數字會失真。

你要的是「統計數據」，不只是一個平均值。所以每個持有期都給這幾個（示意數字，非實測）。

🔴 只有「全體」一組——委員會 2026-09-20 裁定：不得顯示「正例組／反例組」，那在本票的 label 定義下是套套邏輯（見 7-2）。 🔴 筆數是「每段連續成立算一次」，不是每根都算（見 7-4）。

🔴 上一版我寫「勝率是 label 加總得來的」——那是錯的，我查了程式才發現。 勝率是直接從報酬的正負算的，跟 label 無關。

這件事讓 label 的定位更清楚了：它對你要的統計數據一點貢獻都沒有，純粹是匯入契約的形式要求。 你看到的每一個數字都是從報酬直接算出來的。

其他兩點：

  • 筆數會隨持有期變少（340→335），因為資料尾端算不出長持有期的報酬，那些事件直接排除不灌 0
  • 為什麼要中位數和標準差：平均值會被少數極端值拉走。中位數告訴你「典型情況」，標準差告訴你「有多不穩」——只看平均會誤判

# 缺口 白話
1 掃描函式沒有 API 接口 函式在，但 api/ 裡零個呼叫者——前端根本碰不到它
2 條件讀不到 FF 欄位 「讀特徵表」和「求條件」兩端都有，中間沒接：沒有任何程式把 FF 的欄位名註冊給條件引擎。🔴 而且現在寫錯欄名不會報錯——找不到該欄時條件直接判「不成立」，你會得到「零筆命中」而不是錯誤訊息（codex 查出）。這條必須在規格裡改成報錯，否則你永遠分不清「條件真的沒成立」和「欄名打錯」
3 比較比的是達標率，不是報酬 現有比較端點回「觸發批裡 label=1 佔幾成 vs 隨機批佔幾成」，不是平均報酬。而且它常常是灰的——它要求觸發批帶「標籤規則收據」（label_rule），一般匯入沒有，就回「無從確認兩批用同一條規則」而不並排
4 隨機抽樣現在不公平 見下表
5 統計欄位差兩個 現成的有筆數／平均／中位數／勝率／信賴區間；標準差與最好／最差沒有，要加（實查 tables.py:118-131）
6 沒有欄位選擇器 這個 run 有 18 萬個以上欄名，後端能回清單但前端只能拿到一整包平鋪的。沒有逐層下拉＋搜尋，你寫不出條件

五、做法：九步

（原本七步；委員會 2026-09-20 挖出兩件我沒算進去的工作，見第七節）

  1. 條件引擎吃 FF 欄位——把讀到的特徵表欄位名註冊給條件引擎，讓你能寫 close_1h_trend_EMA_5 > close_1h_trend_EMA_10。並且欄名打錯要報錯，不能靜默回零命中
  2. 欄位選擇器——逐層下拉（來源欄→週期→類別→指標→參數）＋打字搜尋。沒有這個你根本沒辦法從 18 萬個欄名裡挑出要的
  3. 掃描函式接上 API——條件 → 事件批 → 匯入（label 用漲跌正負號填，進場價用 next_open）
  4. 🔴 統一「持有 N 根」的時鐘——鎖定「從成交那根起算」，並讓 label 與報酬表用同一個出場根（現在差一根，見 7-3）
  5. 🔴 連續成立只進場一次（first-of-run）——否則 340 筆可能只是 10 段趨勢（見 7-4）
  6. 報酬表補兩個統計量——加上標準差與最好／最差
  7. 產隨機對照批——進場語意／出場錨／持有期集合由觸發批帶入，並修掉抽樣四項（見 7-6、7-7）
  8. 比較端點改成比報酬——現在只讀 label 算達標率；並加上 Δ 的時間塊／群集 bootstrap 區間（見 7-5）
  9. 前端——掃描設定畫面（持有期直接輸入、即時顯示約幾天）＋ 兩組統計並排的表＋硬性橫幅（無區間時不得讀成會賺）

兩條我查過、確定不走的路

曾考慮 為什麼不走
改匯入契約，允許「只有觸發點、沒有反例」的批 不需要。label 系統自己算，契約天生就滿足

7-3 🔴「持有 N 根」現在有兩套時鐘（我完全沒想到）

兩張會同時出現的表，對「持有 5 根」的定義不一樣：

表 出場在哪

7-4 🔴 均線條件會連續好幾根都成立（我完全沒想到）

多頭排列一旦成立，通常會連續維持好幾十根。如果每一根都算一筆「買入持有 N 根」：

340 筆可能其實只是 10 段趨勢，你會以為有 340 次獨立的買賣，實際上沒有。

處置：主要數字用「每一段連續成立只進場一次」（first-of-run）。每根都算的版本保留為參考，但不當主數字。

7-5 「差 +0.72%」是真的還是運氣？現在答不出來（推翻我）

問題長這樣：表上寫「觸發批平均 +1.05%、隨機批 +0.33%、差 +0.72%」。

那 +0.72% 到底是這條規則真的有效，還是剛好抽到好樣本？ 這是你看完表最該問的問題。

一般統計用信賴區間回答：「差是 +0.72%，區間 [+0.31%, +1.13%]，不含 0 ⇒ 大概不是運氣」。 但這條路現在算不出這個區間，兩個原因：

原因一（技術性的）：系統算區間需要先做「切分」這個前置步驟，而事件掃描這條路沒有做切分 ⇒ 系統直接標「無法提供」。

原因二（比較根本的）：你的 340 筆不是 340 個獨立樣本。

多頭排列連續成立時，第 100 根和第 101 根的「持有 30 根報酬」 有 29 根是重疊的同一段價格。它們幾乎是同一筆交易，不是兩次獨立的下注。

如果拿「340 個獨立樣本」的公式去算區間，算出來會太窄——讓你以為「很確定有效」，其實資訊量遠沒有 340 筆那麼多。

還有一個常見的誤用：有人會分別畫觸發批和隨機批各自的區間，看它們重不重疊。這不能回答「差是不是 0」——兩個區間重疊，差仍可能顯著；不重疊，也不保證顯著。要看的是**「差」本身的區間**。

處置：用 bootstrap（把資料重複重抽幾百次、每次重算一遍差、看這些差分布在哪）算出「差」的區間，而且重抽的單位要是「一整段連續成立」而不是「一根」，這樣才不會把重疊當成獨立。

在做出來之前，表上方會有一條硬性橫幅：

「無信賴區間；平均差為正不得讀成這條規則會賺。」

如果從整個 run 挑（2024-01 到 2026-04，兩年多）：

假設你的條件剛好都在 2024 年那波多頭成立。那你比的是 「2024 多頭的報酬 vs 兩年平均的報酬」—— 差異來自行情，不是來自你的條件。條件根本沒被驗證到。

所以要從有觸發點的那些月份裡挑，這樣兩邊在同一種行情下比。我先前寫「該用整個 run」是錯的，自己推翻掉。

但還不夠，委員又抓到一層：

現在系統分配名額是按「每個月有多少根可以挑」，不是按「每個月有幾個觸發點」。

假設觸發點 80% 集中在 1 月，但 1、2、3 月的 K 線數量差不多 ⇒ 隨機批還是會平均分到三個月。結果又變成「以 1 月為主 vs 三個月平均」， 同一個毛病換個形式又出現。

  1. 期間池＝有觸發點的那些月份（UTC）的聯集
  2. 名額按觸發筆數分：1 月有 80% 觸發，1 月就抽 80% 的對照。某月候選不夠就直接回報失敗，不把缺額倒到別的月充數
  3. 「整個 run」那版只能當另一張參考表，標題要寫清楚它回答的是不同的問題（「這個條件是不是只是選到了好行情」）

7-9 手續費與滑點要不要算？（你 2026-09-20 提問）

業界做法分三層，答案不一樣：

算什麼 扣不扣成本 為什麼
IC 本身 不扣（業界標準） IC 是「因子值 vs 未來報酬」的相關係數，衡量排序能力。成本發生在換倉，不發生在「某個時點的相關性」上——扣了沒有明確定義
淨 IC（net IC） 扣 進階診斷：扣掉換手成本後因子還有沒有效。不是 IC 的標準定義，是額外一層
事件研究的報酬 學術通常不扣 它要衡量的是「資訊效應」，所以報未扣成本的異常報酬。但實務要判斷「能不能真的賺」就得扣
回測 一定扣 它宣稱的就是「這樣做會賺多少」，不扣就是假的

本專案現況（實查 momentum/Analysis/net_ic_analyzer.py）：

  • 已有淨 IC，公式＝淨值 = 毛值 − (成本bps ÷ 10000) × 換手率
  • 預設關閉（cost_enabled = False）
  • 🔴 裡面有一個設計比「扣成本」更有用：breakeven_cost_bps

breakeven_cost_bps 是什麼：它不要你猜費率，而是反過來告訴你「成本要高到多少，這個獲利才會被吃光」。

例：它回 3.2，而幣安吃單費約 5 bps ⇒ 你當場就知道 這條規則扣完手續費就沒了，完全不必去設定任何費率。

我對 EVENTSCAN 的建議：

  1. 主數字報未扣成本（跟事件研究慣例一致，也跟委員建議一致）
  2. 但加一欄 breakeven：這批事件的平均報酬，在多少 bps 成本下會歸零
  3. 不在本票發明費率——我不知道你用哪家交易所、什麼手續費等級、吃單還是掛單

理由：讓你猜一個費率再扣，猜錯了整張表就是錯的；breakeven 反過來給你一個不需要假設的判準。

委員另外提醒的三項成本（算不進報酬公式，只能揭露）： 開盤第一筆成交價 ≠ 你真的買得到的均價、永續合約的資金費、滑價。
