一句話

委員寫了「不可進下一批」，我照樣進了——而且每一個批次邊界都是這樣過的。 擋在批次之間的那道閘只檢查「有沒有派出去審」，不讀結論；而且它只在「派工給委員」時觸發，我自己寫程式時根本不會經過它。這票把閘改成會讀結論、而且不論誰實作都會經過。

偵察時三家推翻我什麼（值得你知道）

  1. 我說「委員的結論在檔案裡根本無法用程式讀」——講過頭。全庫 628 份審查裡 490 份有結論行、152 份照範本格式。真正的病是：每家用自己的字眼（可進／不可進／可收票／已全數閉合），而且從來沒寫進稽核日誌，所以閘想讀也沒地方讀。
  2. 我想把「commit 訊息要標批次」的檢查放在 pre-commit——那個階段根本拿不到 commit 訊息，只有 commit-msg 拿得到。而 commit-msg 裡既有的一道檢查是你 9/5 裁定「只警告不擋」的。照我原案做，一個 commit 都擋不住。
  3. 這不是 SPLITUNIFY 一票的問題：GAP-3、EVTLABEL 都有同樣的事，路徑是「清完債 → 直接開下一批」。

R1 抓到什麼

  • 最重的一條（grok）：我設計的閘只看「最新一輪」的結論——委員在下一輪把「不可進」改寫成「可進」但沒說哪一條關掉了，閘就放行。改成：該批所有輪次寫過的「擋」全部累積，每一條都要由原提出的那家明確寫「已關」才解除；寫「可進」本身不算。
  • 我原本想用關鍵字（「不可進」「可進」…）回頭判定舊審查的結論——三家實跑證明兩個方向都會判錯（63 份「需修補」被當成通過、10 份閉合輪被當成擋）。改成不回頭判：舊的一律標「未知」、不進閘（你 8/5 定的「面向未來不溯及既往」），只出一份透明清單。
  • 「小任務 commit 不用領權限」的規則可以被拆成好幾個小 commit 繞過——改成 push 時把所有小 commit 動到的生產檔合起來算，超過 3 個檔就擋。
  • git commit --amend -m 會把批次標記弄丟——邊界條件寫錯，已改。

R2 抓到什麼（R1 的修法又被打穿一條，另五條是我沒改乾淨）

  • R1 那條「小 commit 合起來算」的修法，三家不約而同打穿：我用「這次 push 的範圍」算聯集，可是 push 完範圍就歸零——分兩次 push、每次 3 個檔，6 個檔從來沒被合在一起算過。改成寫進稽核日誌、累計到下一次正式領權限為止，push 完不歸零。
  • 我改規格書只改了一段，另外六處還寫著舊做法（凍結基準檔）——實作的人會不知道要照哪個。全部清掉。這是「改裁決要同步所有引用」那條老毛病再犯。
  • codex 抓到最重的一條：委員交審查檔之後，根本沒有任何程式會自動把結論登記進稽核日誌——現在全靠我手動補。閘讀日誌、日誌是空的 ⇒ 閘永遠放行。補上自動登記，且「派了卻沒登記」一律當作擋。
  • 「我自己領實作權限」那段和現有程式的行為對不上（第一批沒有前一批可驗），已改成走完全同一條路。
  • 上線前就存在的跨批傷口（SPLITUNIFY 每批都是）閘不回頭管——這是你 8/5 的裁定，但要具名列出來讓人看得到，不能就此消失。

R3 抓到什麼（R2 修法的文字被挖出兩個縫，另四條是接線細節）

  • 我寫「小 commit 累計到下一次領權限或下一個正式批次 commit」——第二個起算點根本不會產生事件（死文），若實作者取「較晚的那個」，先領權限、塞 3 個小 commit、打一個正式 commit、再塞 3 個、一次 push ⇒ 又是 6 個檔放行。改成只認領權限一個起算點。
  • 記錄小 commit 的時機寫在 commit 訊息階段，那時 commit 的 ID 還沒定案；--amend 之後舊記錄變幽靈、會多算。改到 commit 完成後才寫，讀的時候過濾掉已不存在的。
  • 「派了卻沒交結論就當擋」——我用「有交過結果」的家族當名單，可是掛死被砍的家族連結果都沒有，就從名單消失了。改讀開輪時就登記好的名單。
  • SPLITUNIFY 復工前要補一輪機械裁決——我只寫成「主委要記得派」，codex 指出這樣 B5 照樣可以先開。改成閘直接擋：前一批有派過審、卻沒有機械結論 ⇒ 不准開下一批，訊息告訴你去補。這是三家裡較嚴的版本（另兩家認為不擋也行）；你離線時的規則是分歧採較嚴。
  • 事件格式登記錯檔案（新檔 vs 既有唯一寫入點讀的檔）——改登記到既有那個。
