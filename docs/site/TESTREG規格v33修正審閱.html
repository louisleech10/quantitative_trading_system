一、漏洞是什麼（第 33 版）

「測試裡的檢查只能變多不能變少」這條規則，要算出每個測試有哪些檢查，包括它用到的共用準備步驟（pytest 叫 fixture）裡的檢查。

第 32 版只算兩種「用到」：

  • 測試在參數裡點名要哪個準備步驟；
  • 自動套用到所有測試的準備步驟。

漏了第三種：在測試上方加一個標註「先跑某某準備步驟」（@pytest.mark.usefixtures(...)），或在檔案開頭對整個檔加這個標註。pytest 會照跑，但第 32 版不算它。

後果：那個準備步驟裡的檢查被刪掉，或提供它的外掛被拿掉，不會被擋。真實專案有 15 處這樣寫（都是 IC 相關測試，用來確保測試不會把結果寫進真實資料夾）。

修法：這三種「用到」都算。標註寫在測試上、寫在測試所屬的類別上（包括從別的類別繼承來的）、寫在檔案開頭，都算。

二、第 34 版：第 33 輪 codex 找到的 3 處

  1. （會漏擋）繼承寫成「模組.類別」時沒算到：例如 class TestX(base.Base)，而標註寫在另一個檔案的 Base 上。修好後，另一個檔案的基底類別、基底的基底，都會追到。也順手補了兩個同類的洞：
    • 在共用檔裡把基底類別的標註拿掉 → 現在會擋，並列出所有繼承它的測試；
    • 在測試檔裡把某個類別的標註拿掉 → 現在會擋，連同繼承它的子類別一起列出。
  2. （會誤擋）把標註「當成資料」也算進去：例如把標註放在參數清單裡當值、或塞在別的標註裡面，pytest 其實不會照跑，但第 33 版會算。改成只算 pytest 真的會套用的寫法。
  3. （格式）試做補丁檔有多餘空白：已重產並確認仍能正確套用。

二之一、第 35 版：第 34 輪找到的 3 處

  1. （會漏擋）同一個資料夾套件內用「相對路徑」引用基底類別（from .helpers.base import Base）時追不到。原因是程式只認得完整路徑的引用。修好後，整支程式所有找引用的地方都會把相對路徑換成完整路徑，不只這一處。
  2. （會漏擋）引用基底類別時改了名字（from ... import Base as B，再寫 class TestX(B)）時，快速篩選只認原名而跳過。改成原名與改名後的名字都認。
  3. （我判斷錯誤，grok 抓到）：第 34 版我說「參數化測試的某一組參數掛這個標註，pytest 會對那一組套用」，所以要算。grok 實測 pytest 8.4 遇到這種寫法直接報錯拒收，我也重現了。所以這種寫法根本跑不起來，改為不算，驗收也改正。

二之二、第 36 版：第 35 輪 codex 找到的 3 處

  1. （會放錯行）「完全重複」的判定沒看別的檔案裡的基底類別：淘汰測試時有一種證據是「這個測試和另一個一模一樣」。第 35 版只比對同一個檔案裡的基底類別，兩個測試若各自繼承「不同檔案、內容不同、但同名」的基底類別，會被誤判成一模一樣而允許淘汰。改成連別的檔案的基底類別內容也一起比。
  2. （會漏擋）用 from 某模組 import *（一次引用全部）取得基底類別時追不到。改成也會去那個模組找，並照 Python 的規則：模組有列出公開清單（__all__）就只認清單內的；沒有清單就不認底線開頭的名字。
  3. （小）相對路徑往上跳太多層的寫法（Python 本身會拒絕）被當成有效：改成不算。

二之三、第 37 版：第 36 輪 codex 找到的 1 處

（會放錯行或漏擋）同一個名字被引用好幾次時，舊版取「第一個」，Python 實際上取「最後一個」。例如先 from A import *、再 from B import *，兩邊都有 Base，Python 用的是 B 的。我沒有只修這一種，而是把「名字到底指向哪個定義」整個改成照 Python 的規則：照程式由上往下，最後一次指定的為準；類別繼承的基底以「類別定義那一行之前」的為準。驗收直接讓 Python 實際載入四種寫法，比對我們的判斷和 Python 的結果一模一樣。

二之四、第 38 版：第 37 輪 codex 找到的 1 處，以及「到此為止」的邊界

  1. （會漏擋）同一個檔案裡同名的基底類別寫了兩次（先寫一個、讓測試繼承它、再寫一個同名的），舊版會把測試對到後寫的那個。Python 實際上用的是測試定義當下的那一個。已改成記住「當時」是哪一個，驗收同樣讓 Python 實際載入比對。
  2. 劃出邊界，請委員判定是否以此收斂：第 33 輪起，codex 每輪都在「名字指向哪個定義」上找到下一個更少見的寫法（模組.類別、相對路徑、改名、一次引用全部、引用順序、同名重寫），我們都已補齊。程式要事先判斷，只能照「由上往下讀」的規則；Python 還有一些要真的執行才知道的寫法（例如寫在 if 裡的條件引用、程式執行中動態改名字、第三方套件一次引用全部的內容、metaclass 改寫標記）。這些事先判斷不了，規格明列為「不可事先判定」，交給審碼委員逐次看，不再無限追下去。

二之五、第 39 版：第 38 輪 codex 找到的 2 處（都在邊界之內，已補）

第 38 輪兩家都同意上面那條邊界；codex 指出邊界之內還有兩處沒做完：

  1. （會放錯行或漏擋）「模組.類別」寫法裡的模組簡稱之後又被改指別處：例如先 import helpers as h、讓測試繼承 h.Base，後面又把 h 指到別的模組。Python 用的是「類別定義當下」h 指的那個；舊版用最後指的那個。已改成取定義當下的，驗收同樣讓 Python 實際載入比對。
  2. （會漏擋）同一個檔案裡同名類別寫兩次時，改「前一個」的標註沒被發現：第 38 版判斷「哪裡改了」時，只記同名類別的最後一個。若測試繼承的是前一個，拿掉前一個的標註不會被擋。已改成每一個同名定義都記。
