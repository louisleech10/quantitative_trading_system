一、為什麼要改規格

第 3 批要把特徵工廠相關的 149 個測試檔逐檔判定「留、改、淘汰」，然後真的去改。開始改之前發現一個卡死的情況：

測試清冊有一條規則——改一個既有測試時，必須證明「把程式改壞，這個測試會失敗」（不然改完的測試可能是空殼）。做法是故意把程式改壞幾種方式，看測試有沒有抓到。

但有 33 個測試本來就是紅的（在我們開工前就已經失敗，以前沒登記）。本來就紅的測試，故意改壞程式它還是紅，「抓到了」這件事無從證明。結果是：這些測試沒有任何合法的修法——修了會被清冊擋，不修就一直紅。

二、決定：新增「本來就壞的測試改寫證明」

只有一種修法允許走這條路：測試期望的答案已經過期（程式的行為改了、而且改得對，測試卻還寫舊答案）。要附一份證明，條件全部要成立：

  1. 只准改「期望的答案」那一個值。例如 == 3 改成 == 4、錯誤訊息的文字。
    • 不准改輸入（例如把 scale(1) 改成 scale(2)）；
    • 不准放寬誤差（例如容許誤差從十億分之一改成 10）；
    • 不准順便刪掉別的檢查。
    • 第 44 輪 codex 和 grok 各自做出「改輸入、放寬誤差也能過」的反例，所以收緊成這樣。
  2. 只准一個檢查，而且必須正是現在失敗的那一個。
  3. 必須指出是哪一次修改弄壞的，並用真實歷史證明：
    • 那次修改之前，測試是綠的；
    • 那次修改之後，測試是紅的，而且紅在同一個檢查上。
    • 第 44 輪 codex 指出：原本沒檢查「紅在哪一個檢查」，可能拿別的檢查失敗來充數，所以補上。
  4. 委員的裁定文件必須點名這個測試和那次修改。
  5. 改完之後，要證明新的期望值抓得到錯：故意把程式改壞，每一個檢查都要有至少一種改壞方式讓它失敗。

為什麼這樣不會被拿來掩蓋程式錯誤：只准改答案，所以不能把檢查改鬆。指出弄壞的那次修改之後，委員要判斷那次修改是「本來就該這樣」還是「程式錯了」。如果是程式錯了，就改程式，不准改測試。

三、決定：「空心測試」不走這條路

另有一種問題測試是空心的：它永遠會過，但其實什麼都沒驗到。

最常見的例子是：生成程式現在只回傳時間、不回傳特徵值，拿它的回傳去比數值，等於拿空表比，永遠會過。

第 44 版原本也想讓空心測試走證明路線。第 43 輪三家一致指出「證明它是空心的」那個方法不可靠：拿一個無關的檢查來替換也能通過。所以改成：

  • 空心測試的修法：保留原本的檢查，把它比對的對象換成真正存下來的資料，讓檢查變成有實質內容。檢查只增不減，所以不需要特別證明。
  • 確定永遠跑不到的舊程式碼裡的空心檢查：本來想直接刪，但要機械證明「這行從來沒被執行過」需要逐行執行紀錄，現在還沒有。所以先不刪，列為之後的事（見第六節）。

四、決定：把一個檢查從約 3.6 秒加速到約 0.1 秒

證明裡有一步要確認「這份證明對應的正是目前的程式碼狀態」。

原做法是在暫存區複製一整份專案再比對，真實規模一次約 3.6 秒，一份證明要做約 7 次，合計約 25 秒。這違反「寫檔當下的檢查要秒級」的規定（第 44 輪 codex 指出）。

改成不複製整份專案，只在 git 的暫存登記區比對：

  • 真實規模約 0.05–0.13 秒；
  • 結果和原做法逐位元相同（我實測 7 種情況、三家各自又加測檔案權限變更、檔尾沒換行、圖片檔等情況，全部相同）；
  • 只有改動含新增、刪除、改名檔案時才退回原做法。

五、分類與實際改測試的規則（第 44 版定的）

  1. 分類方法：
    • 我先自己判一版，三家各自獨立判一版，判完才看我的版本，避免互相影響。
    • 四版比對：「留或改」要至少 3 版同意；「要改寫的測試函式」取四版的聯集（寧可多改）；淘汰要至少 3 版同意。
    • 比對程式遇到格式不對直接報錯，不會靜默略過。
  2. FRAMEPATH 管轄的 52 個檔先不動：FRAMEPATH 有一條檢查把這些檔凍結了，要等 FRAMEPATH 修好那條檢查、經審查蓋章後才改。之前的小批只改其他檔。
  3. V-6 檢查（你 10/12 問的「粗接細」）：三家同意加上「主週期較細、來源較粗」（例：主 1 小時接 12 小時）這種，原本的「細接粗」保留。這是純新增，另加故意做錯的對照（偏舊一根、開收盤混用等），證明它抓得到錯。
  4. 重新凍結標準答案檔：要獨立一筆提交，經三家刻意找錯式審查，並寫明是哪次修改造成的。如果造成的那次修改不是預期行為，就不重新凍結，改列為程式錯誤。
  5. FRAMEPATH 第一批弄壞、但當時沒選到的 2 個測試：由 FRAMEPATH 在第二批開工前的修訂處理，本票只分類。

六、沒做、留到之後的（三家同意的理由）

  • FRAMEPATH 管轄的 52 檔的改寫：要等 FRAMEPATH 修好它那條檢查（上面第五節第 2 點）。
  • 刪除確定跑不到的空心檢查：要先有逐行執行紀錄才能機械證明；現在先保留、另補實質檢查。
  • 已寫好的驗收測試只能新增不能改：這次我改驗收時發現，測試一提交就受「只增不減」約束，連自己票裡還沒實作的驗收也一樣。要設計「草稿期可改」的判準，又不能被拿來弱化已凍結的驗收，需要另外研究。這次的處理是：舊的驗收逐字保留，用新增的方式補。
