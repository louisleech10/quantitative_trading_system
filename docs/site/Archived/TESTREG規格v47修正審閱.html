一、為什麼又要改規則

第 3 批要開始實際改測試時，發現有三種測試在現行規則下沒有合法的改法：

規則要求：改一個被判「要改寫」的測試檔，必須附一份證明，證明「舊測試本來抓得到錯、新測試沒變弱」。證明的方式是故意把正式程式改壞，看舊測試的每一個檢查都會失敗。

但下面三種舊測試，這個證明做不出來：

  1. 本來就壞、而且壞在準備步驟（7 個檔、13 支測試）：測試一開始準備資料時就出錯，檢查一行都沒跑到。原因是共用的輔助程式沒給週期，被 10/04 那次修改改得更嚴格的正式程式拒絕。
  2. 抓不到錯的舊測試：例如把錯誤全部吞掉、或檢查寫在永遠空轉的迴圈裡。故意改壞程式它也不會失敗。
  3. 根本沒有測試函式的檔（1 個檔）：程式碼直接寫在檔案最外層，連「哪個測試」都指不出來。

另外審碼還抓到我上一版規則的一個漏洞：有參數的測試（同一支測試帶不同輸入跑好幾次），只跑其中一組也會被當成「全部通過」。

二、決定：三種新的證明方式

1. 本來就壞在準備步驟的：只修共用輔助程式

  • 測試檔一字不動，只修共用的輔助程式（讓它在沒有週期設定時給一個合法的週期）。
  • 我和三家都在真實資料上實測過：這 13 支測試全部恢復正常，結果和 10/04 弄壞之前一樣。週期標記的名字會從「unknown」變成「1h」，這一點和以前不完全相同，但計算長度和結果都一樣。
  • 清冊分類不改（三家都反對趁機把它們從「要改寫」名單拿掉，因為那等於繞過規則）。改為附一份修復證明，證明內容：
    • 修之前，失敗的位置在輔助程式裡，不在任何檢查上；
    • 修之後全部通過；
    • 追溯到弄壞前的版本是好的、弄壞後的版本壞在同一種地方；
    • 修好之後，每一個檢查都能被故意改壞的程式抓到（證明修復沒有讓測試變鬆）。
  • 但要等 FRAMEPATH：這個輔助程式剛好在 FRAMEPATH 的凍結範圍裡，所以實際修改要等 FRAMEPATH 修好它那條檢查之後才能提交。

2. 抓不到錯的、沒有測試函式的：舊的不動，只新增

  • 舊測試函式一個字都不准改、不准刪。
  • 只准新增：新的測試函式、只含測試的測試類別、import。不准新增會影響全檔的東西（例如每支測試前都會自動執行的準備步驟、模組最外層的程式碼、整檔套用的標記），因為那些可能偷偷改變舊測試的行為。
  • 新加的每一個檢查，都要能被故意改壞的正式程式抓到。
  • 新測試要測到舊測試原本想測的東西：舊測試用到哪些正式程式的函式，新測試也要用到；而且至少要有一種「改壞那些函式」的方式能讓新測試失敗。這是為了防止「舊的空殼留著，另外加一個不相干的測試交差」。
  • 沒有測試函式的那個檔：原本寫在最外層的程式碼要依原順序搬進新的測試函式裡；原本「出錯就結束程式」的寫法不准搬，要改成正式的檢查。

3. 有參數的測試：一組都不能少

  • 跑的時候不准帶任何篩選條件（例如只跑某幾組的選項）。
  • 從測試原始碼直接數出「應該有幾組」，和實際跑到的筆數比對，必須一樣多。
  • 數不出來的情況（例如參數是程式動態產生的），一律判定證明不成立，寧可擋下也不放行。
  • 這條同時套用到上一版「本來就壞的測試改寫證明」，補上審碼抓到的漏洞。

二之二、第 48 版：第 46 輪 codex 抓到的 7 處（都照改）

  1. 「只新增」可能被拿來偷懶：舊測試其實抓得到錯，卻不走正規的改寫證明，只加一個新測試交差。
    • 改成：新加的測試必須抓得到「舊測試抓不到」的錯——至少一種改壞方式讓新測試失敗、但舊測試照樣通過。
    • 舊測試若對所有這類改壞都會失敗，就不准走「只新增」，必須走正規證明。
  2. 措辭澄清：「模組最外層要搬進函式的程式碼」，指的是 import、函式和類別定義、說明文字、單純常數以外的東西。原文容易讀反，程式本來就照正確意思做。
  3. 新增的 import 可能偷偷改掉舊測試用的名字：例如新 import 一個同名函式，覆蓋舊測試呼叫的那個。
    • 改成：新 import 的名字不能和檔裡已有的任何名字重複，也不准「一次 import 全部」。
    • 新測試前面的標註只准用「參數化」那一種。
  4. 參數組數可能數錯：
    • 用「先跑某準備步驟」標註帶進來的參數，現在也算進去；
    • 繼承自同一檔裡父類別的參數也算進去；
    • 父類別在別的檔，數不出來，一律判定不成立。
  5. 同一支測試重複跑：用「保留重複」選項跑的紀錄一律不算；另外改成逐筆數原始紀錄，防止重複的被合併掉看不出來。
  6. 「一次 import 全部」取得的函式：判斷「新測試有沒有測到舊測試測的東西」時，現在也追得到這種寫法。
  7. 修復證明不放行「刪檢查」：修共用輔助程式時，任何測試的檢查都不准變少，原本的檢查規則照常擋。

二之三、第 49 版：第 47 輪 codex 抓到的 1 處（照改）

  • 數參數組數時漏看「外掛檔」：測試要用的準備步驟，可以放在共用設定檔指名載入的另一個檔裡。上一版只看測試檔本身和共用設定檔，沒看這種被指名載入的檔，帶參數的準備步驟會被漏算，組數就數少了。
  • 改成：連「共用設定檔指名載入的檔」一起看。
  • 補了一支驗收：造一個這樣的外掛檔，確認工具判定為「數不出來」而不放行。拿掉新加的掃描後，這支驗收會轉紅（實測過）。
  • composer、grok 這一輪零意見。

二之四、第 50、51 版：只補驗收、規則不變

  • 第 48 輪 codex 指出：第 49 版那支驗收只測「測試直接要用外掛裡的準備步驟」，沒測「外掛裡的準備步驟自動套用到每個測試」。把工具處理後者的程式拿掉，驗收照樣通過。第 50 版補上這一支。
  • 第 49 輪三家各自實測，都指出同樣兩個沒蓋到的寫法：
    1. 自動套用的準備步驟本身沒有參數，但它又用到另一個有參數的準備步驟；
    2. 「要用哪個準備步驟」寫在整個類別或整個檔的標註上，而不是寫在單一測試上。
  • 第 51 版補了四支驗收。每一支都實際把工具對應的那段程式拿掉，確認只有那一支會失敗。
  • 第 50 輪三家一致判定兩個規則漏洞的補法，第 52 版照做；你 10/14 裁定「不要摳細節、照主流做法」後，規則定案在第 52 版，三家蓋章、已放進正式程式。本審閱稿至此結案、封存。
