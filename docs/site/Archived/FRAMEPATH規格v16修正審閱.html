一、試做時發現的前提修正（A1–A10）

條 改了什麼 為什麼
A1 舊路徑的「預處理（L6.5）與存檔（L7）入口」整批刪掉，不留成「呼叫就報錯」的空殼 試做刪除後追查發現，正式程式從來不會走到它們（新路徑有自己的一套）；留空殼只是多一堆沒人用的碼
A2 多週期模組裡一個舊的「欄名加週期標記」函式也整個刪掉 同上，只有舊路徑用；新路徑用另一個逐欄規則，那個保留
A3 「刪完不能留下沒人用的函式」這條檢查，排除改動前就已經沒人用的 3 個函式；要刪的清單現在就定死，施工時若又冒出新的「沒人用」，要回頭重審 那 3 個本來就是死碼，不是這張票造成的，算進來會永遠過不了
A4 允許在「資料層研究（FFSTORE）」那行路線圖登記一條新殘留（見 A9） 規格原本只准改本票的那幾行
A5 一份文件登記表允許出現本票的規格書與施工清單兩行 規格書起草時已登記，原規則會誤擋
A6 收尾時「全專案不得再出現舊路徑字樣」的掃描，允許本票新寫的測試出現這些字（它們就是在檢查舊東西不存在） 不然測試本身會讓掃描失敗
A7 一個「凍結過的舊測試清單」相關檢查，原本就已經是紅的，本票會再觸發；改成每批同步補登，並把一份 NaN 傳播基準提前到第一批重產 試做實跑發現
A8 生成函式的 require_raw 參數一起刪（它只傳給被刪的快取查詢） 刪了快取後它變成無作用參數
A9 新登記一條殘留：舊版 manifest 的一條寫讀鏈，現在正式流程到不了，但要不要刪牽涉資料層設計，交 FFSTORE 那張票研究 為何現在不做：需要研究（不是偷懶）；登記在路線圖 RM-FFSTORE
A10 「同一個資料夾第二次生成」那一格的驗收語意更正：實測新路徑會進續跑流程但仍重算一遍，輸出逐位元相同；驗收改成驗「輸出不變」而不是「有跳過計算」 原本的假設在現行程式不成立（有實跑收據）；中途中斷的跳過語意另有既有測試負責

二、檢查工具加嚴（A11–A14，審查第 25–31 輪）

這幾條全部是「確保施工時照清單做、沒偷偷放寬測試」的檢查工具本身的漏洞，不影響要刪什麼：

  • A11：改寫測試時「要保留的原檢查」必須留在會執行的位置（不能搬進永遠不跑的分支）；檢查「本機被 git 忽略的檔」改成只看這張票開工後新出現的（你電腦上 11 個舊的前端本機檔不再干擾）；死碼掃描不再把「同名的文字」當成有人在用。
  • A12：相同的兩個檢查只留一個會被抓；記憶體數字必須真的來自取樣器、不能自己填；死碼掃描只認明確的動態呼叫寫法。
  • A13：施工許可發下的那一刻，委員審過的驗收測試與施工清單就被鎖定（以管控工具寫入稽核紀錄的提交編號為準，施工清單自己改不到）；「格式錯誤回 400」的檢查只認最外層、確實包住服務呼叫的那段。
  • A14：改寫時拿掉的原檢查要逐條寫理由（實測補了 11 條，全是舊路徑專用稽核或已由新檢查接手）；逐項閱讀的處置表改放進版控；同一行寫兩個檢查、宣稱刪了卻還留著、呼叫錯物件，都算不合格。
