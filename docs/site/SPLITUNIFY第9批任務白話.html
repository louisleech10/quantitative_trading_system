先講清楚：整批在解什麼問題

你篩出一批事件（例如「RSI 超賣」觸發了 165 次）。系統要為每個事件算特徵， 而特徵可以來自不同的 K 線週期——同一個事件，可以有 1h 的特徵、也可以有 4h 的特徵。

原本的系統只留一個週期，其餘整批丟掉，而且不告訴你丟了多少。

更糟的是：決定「這個事件算訓練組還是測試組」時，用的是該週期的取數時點。 1h 和 4h 的取數時點不一樣 ⇒ 同一個事件的兩個週期可能被分到兩邊。 一邊進訓練、一邊進測試，等於答案漏進了訓練資料，而且全程沒有任何錯誤訊息。

這一批（第 9 批）就是把這兩件事修掉。五個小任務是一條依賴鏈，不能跳：

9.1（誠實記帳） → 9.2＋9.2a（全部留下來） → 9.2b（判邊改事件級）
                                              → 9.3（下游九處）∥ 9.4（顯示）
                                                          → 9.5（基準檔）

Task 9.1 — 先誠實記帳

在做什麼：不改「只留一個週期」這個行為，但要說出丟了哪些、各丟幾列。

為什麼先做這個：如果一次把「記帳」和「不要再丟」一起做，出問題時分不出是哪一個弄壞的。 所以先做只加不減的那一半。

怎麼做：

  • 產生資料的那支函式，回傳值從「一張表」改成「一張表 ＋ 一份丟棄清單」。 清單長這樣：{"4h": 2} ＝ 被丟掉的 4h 有 2 列；沒丟東西時是空的 {}，不是 null、也不是沒這個欄位。
  • 這份清單原樣一路帶到報告的 summary 裡，中間不加工、不重算。

舉例：一批事件有 1h 和 4h 兩種特徵週期，你選了 1h。 以前：報告只寫「投影完成」。現在：報告多一行 discarded_rows_by_feature_tf = {"4h": 2}。

踩到的坑：

  • 週期欄位如果是空值，字串化之後會變成一個叫 nan 的假週期混進清單。已改成直接報錯——缺資料就是缺資料，不是一種週期。
  • 多標的時文件寫「逐標的相加」，但實際上那支函式是整批算一次的，照字面相加會重複計數。實作採原樣傳遞，文件改掉。

Task 9.2 ＋ 9.2a — 停止只挑一個（整批的核心）

在做什麼：全部週期都留下來。同一個事件可以同時有 1h 和 4h 兩列，各自帶自己的週期標記。

為什麼四層要一起改（少改一層等於沒改）：

  1. 產生資料的函式：從「必須指定一個週期」改成「不指定就給全部」
  2. 呼叫它的那一行：把強制轉字串拿掉——不拿掉的話「不指定」會變成字面的 "None"， 被當成一個叫 None 的假週期，產出空表
  3. 流程入口的檢查：從「四個參數都要給」改成「三個」——不改這裡，連走到那支函式都走不到
  4. 資料合併方式：改成以週期為行粒度，並新建一個「特徵週期」欄位

第 4 點的關鍵：這個新欄位不能拿現成的「觸發週期」欄冒充。 「觸發週期」是事件在哪個週期上被偵測到的，「特徵週期」是特徵從哪個週期算出來的—— 兩件事。拿前者冒充，同一事件的兩列會同值，複合鍵直接撞在一起。

9.2a 做的是配套：兩張輸出表各加「特徵週期」欄；唯一性的判準從「每個事件一列」 改成「（事件, 特徵週期）這個組合唯一」；報告的欄位數從 12 個增為 16 個 （多了「事件數」「事件×週期列數」「被丟棄的列數」等，因為事件數和列數從此是兩個不同的量）。

舉例：3 個事件 × 2 個週期 ⇒ 以前輸出 3 列，現在輸出 6 列； 報告會同時寫「事件數 3」和「列數 6」，不會再用同一個數字代表兩件事。

刻意沒動的：基準檔（golden）維持單一週期 ⇒ 既有數值一個都沒變。 這樣萬一之後出問題，可以確定不是這批弄的。擴成多週期是 9.5。

Task 9.2b — 判邊改成看事件自己

在做什麼：決定「訓練還是測試」時，不再看該週期的取數時點，改看事件自己的決策時刻， 判一次之後廣播給該事件的所有週期列。

為什麼：這正是本批要消滅的洩漏。1h 的取數時點和 4h 的不一樣， 逐列判就可能一列進訓練、一列進測試——同一個事件的答案漏進訓練組。 改成看事件自己的決策時刻，結構上就不可能分兩邊。

怎麼判（三段式，順序不能換）：

決策時刻落在哪 判成
早於等於訓練段最後一根的時刻 訓練
晚於等於測試段第一根的時刻 測試
夾在兩者中間（隔離帶） 丟棄（合法且預期，不報錯）
落在整段 K 線範圍外 直接報錯

🔴 最後一列是重點：界外不是第四種分類。寫成第四種分支就等於恢復重疊， 越界的事件會被「合法地」分到某一邊。

兩道 fail-closed（缺一不可）：

  • 同一事件的列若出現異側 ⇒ 報錯
  • 同一事件若同時出現在「分配表」和「丟棄表」⇒ 報錯 （後面這道不能省：丟棄表沒有側別欄，第一道結構上看不到這種混態）

舉例：事件 e_x 有 1h（取數時點在訓練段）和 4h（取數時點在測試段）兩列。

  • 9.2b 之前：1h 判訓練、4h 判測試 ⇒ 兩邊都有它，沒人報錯
  • 9.2b 之後：看 e_x 自己的決策時刻（假設在訓練段）⇒ 兩列都是訓練

還做了：流程入口在做投影之前先驗證訓練／測試兩段的完整性（空段、隔離帶踩線都在這裡先擋）。

Task 9.3 — 下游九處消費面

在做什麼：資料表的行粒度變了（一個事件可能多列）， 讀這張表的地方要逐處確認會不會出錯。

🔴 重點是「逐處判斷」，不是「全部改成複合鍵」。九處裡多數是維持原樣 ＋ 補防誤改測試：

Task 9.4 — 讓你看得見

在做什麼：現在「測試段事件數不足」這個警告只存在於報告資料裡，畫面一個字都沒印。 而且那個數字是用列數算的——同一事件有兩個週期就會讓 1 個事件冒充 2 個，靜靜通過門檻。

怎麼做：計數改成依事件去重；並把顯示補上。 🔴 兩件要綁在一起做——只改計數等於修了也沒人看得到。

Task 9.5 — 基準檔擴成多週期

在做什麼：把 golden 基準檔從「單一週期」擴成「多週期平行組」， 並把比對從「只比事件編號清單」改成「比（事件, 週期）的組合」。

為什麼非做不可：現在一個事件有多列，只比事件編號會把週期這個維度整個吃掉—— 新增或漏掉一個週期，比對照樣綠燈。

為什麼排最後：它會把前面所有任務的結果凍結下來。 前面還在動的時候凍，等於凍一份半成品。
