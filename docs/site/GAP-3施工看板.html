第六批做了什麼（2026-08-26，已收斂）

第六批＝刪除，三個 Task。一句話：讓你刪掉一批匯錯的事件，而且不留半個孤兒檔。

  1. 後端刪除（3.1）——刪掉整批事件與它的全部產物。刪不存在的批會回「找不到」而不是當掉。 不會連帶刪掉 K 線快取或特徵庫，也沒有「一次刪光全部」這種端點。 🔴 這裡做了一個刻意的設計：刪除範圍不是寫死那一個檔名，而是列舉「屬於這一批的所有檔」。 現在這批的東西剛好都住在同一個檔裡，所以列舉只會找到一個；但將來若有人把收據拆出去， 刪除端自動就涵蓋到，不必回頭改——這樣「同步擴張」是結構保證，不是靠人記得。
  2. 刪除鈕與二次確認（3.2）——確認框會顯示這批有幾筆、什麼時候匯入的。 沒按確認之前，一個刪除請求都不會發出去。確認框是真正的畫面元件，不是瀏覽器內建的那個小視窗。
  3. 已被引用的警語（3.3）——如果這批被拿去分析過，確認框會多一段話告訴你 「引用它的分析結果將無法重現」，但仍然可以刪。沒被分析過的批就不顯示這段話 （否則警語每次都出現，等於沒說）。

🔴 有一件事我沒有自己決定，交給三家裁：「這批到底算不算被引用過」現在沒有伺服器端的紀錄 可查——分析過程完全不寫檔，而分析結果的檔案是用另一組編號存的。我先做了一個臨時方案 （記在你這台電腦的瀏覽器裡），並把它跟確認框切開：三家若裁另一種判準，換掉的只是資料來源， 確認框和它的驗收都不用動。四個候選方案的優劣已寫進派工單請他們選。

破壞測試 12 → 18 條全部通過（故意改壞會轉紅、還原轉綠）。過程中抓到我自己的三條假綠： 一條是防護測試根本沒走到防護（網路層先把畸形路徑正規化掉了）， 一條是斷言放在「怎麼改都不會變」的地方， 一條是我在註解裡寫了一句證明不了的話（詳見下）。三條都查了根因才修，不是把測試改鬆。

第一輪審查抓到什麼（三家意見分歧，我採了嚴格的那一家）

Composer 和 Grok 都說「可以收」、零問題；Codex 提了五條，我逐條實跑，五條全部成立—— 所以採 Codex 的版本。這跟上一批一模一樣（上次也是兩家說可收、Codex 五條全中）。 看誰拿得出可以重跑的反例，不是數幾家同意。

# 抓到什麼 為什麼是真的問題
A 孤兒檔永遠刪不掉 「這批還在不在」只問事件檔，但刪除範圍問的是「所有屬於這批的檔」。兩邊問的不是同一件事 ⇒ 只剩收據時，端點回「找不到」，那個檔就永久卡在硬碟上。這正是這個 Task 要防的事情的反面
B 連點兩下會送出兩次刪除 上一批為了避免假綠，刻意讓確認鍵保持可按；這批沒補防重入 ⇒ 兩件事相乘就出洞。第二次會收到「找不到」，錯誤訊息還會寫進已經關掉的確認框。這是上一批的修法自己開的破口，本次專案第 6 次同型
C 警語措辭在說一件不成立的事 紀錄只在這台電腦，文案卻用全域語氣「這批已被引用」。換台電腦就看不到 ⇒ 你會以為沒被引用。Codex 說這比「乾脆永遠不顯示」更糟，我同意：不顯示是「什麼都沒說」，這個是「說了一件不成立的事」
D 我的測試會誤判正確的實作 檢查殘留時用了太寬的比對，note-<編號>-backup.txt 這種碰巧名字裡有編號的無關檔也被算成殘留 ⇒ 正確的刪除實作反而會被判失敗
E 符號連結會讓刪除中途失敗 如果有人在資料夾裡放一個同名的捷徑，刪除會拋錯 ⇒ 端點回 500、那批留在硬碟上

我自己那句證明不了的話：修 B 的時候我在註解寫「用 React state 守不住，必須用 ref」， 結果破壞測試錄到空的紅集合——代表在當時的測試下，用 state 守也會過， 兩種寫法根本分不出來。我補了一條真的能分出來的測試（用原生點擊、不讓 React 先更新畫面）， 現在「拿掉守衛」會弄紅兩條、「改用 state」只弄紅新加的那一條， 兩者的差就是那條新測試的作用範圍。這才叫證明。

第二輪審查（閉合輪）抓到什麼

第一輪那五條，由原本提出的那一家（Codex）逐條重跑自己的反例確認真的關掉了， 另外兩家獨立複驗結論一致。這是規矩：不憑「我已經修了」信任。

Composer 和 Grok 也交代了第一輪為什麼漏抓，逐字是**「依綠燈與修法說明收斂， 沒有去跑孤兒／符號連結／同一瞬間連點／措辭範圍的反例」。 我把這件事變成往後的機械要求寫進派工單：對每一條「存不存在／範圍多大／先後順序」 性質的宣稱，都要附一個實跑的反例**，不准拿「測試全綠」和「我的修法說明」代替。

本輪 Codex 再提兩條，我實跑複驗都成立：

# 抓到什麼 為什麼是真的問題
F 斷掉的捷徑會漏掉 指向不存在檔案的捷徑，系統問它「是檔案嗎」「是資料夾嗎」兩個都答不是 ⇒ 我的清單看不見它。事件檔還在時 ⇒ 說刪好了但它還在；它是唯一殘留時 ⇒ 永遠回「找不到」、永久刪不掉。修法＝認定歸屬只看名字不看型別，型別只在真的要刪的那一步才分
G A 的回應會關掉 B 的視窗 你確認刪 A（還在傳）→ 取消 → 改開 B 的確認框 ⇒ A 傳完回來時會無條件關掉你正在看的 B。修法＝回應處理前先確認「畫面上開著的還是我這批嗎」；順帶把防重入從「全域一把鎖」改成每批一把，否則 A 在傳的時候 B 會被靜默擋住

🔴 G 又是我第一輪的修法自己開的破口（本專案第 7 次同型）：第一輪的防重入只想到 「同一批被連點兩次」，沒想到「不同批之間的先後回應」。

另外有兩條破壞測試的比對標記被我這輪的修改弄失效了，工具當場報錯擋下， 我重新對上標記——不是繞過去。破壞測試 18 → 20 條。

第三輪審查抓到什麼

第二輪那兩條，由 Codex 重跑自己的反例確認關掉了。本輪兩件新事：

① Grok 當場抓到我一條「假的綠燈」（已修）。這條抓得好：畫面上「刪除中…」這個提示 是一個單一開關，但同時在傳的批次可以有好幾個。取消之後這個開關會殘留在「開」的位置， 我靠開新視窗時的一行程式把它同步回來——但我沒有任何一條測試在管那一行。 Grok 不是用讀的，他真的把那行刪掉跑一次，結果測試全綠（證明那行沒人守）， 再寫一個臨時測試證明「A 還在傳的時候開 B，B 會誤顯示刪除中」。我補上了守衛。

這正是我在派工單裡自己問的「會不會改壞產品碼測試還是綠的」。他給了實證，不是意見。 本輪新設的規矩（任何關於「存不存在／範圍多大／先後順序」的判斷都要附實跑反例， 不准拿測試全綠代替）當輪就見效。

② 一條我沒有自己決定、交三家裁的事（RULING-2）。Codex 提了一條最嚴重等級的問題： 如果存放事件批的資料夾本身是一個捷徑（指向別的磁碟），刪除會跟著捷徑走、 刪掉那邊的檔案。我實跑複驗，事實成立——但同資料夾的無關檔案完好無缺， 所以規格寫的邊界「只刪該批、不連帶刪 K 線快取或特徵庫」其實沒有被違反。

爭的是「跟著捷徑走算不算缺陷」這個判斷，不是事實：

  • 這是作業系統的標準行為（你在終端機 rm 那個檔也是一樣的結果）；
  • 改成「拒絕動作」會破壞一個正當的維運做法（把儲存目錄連到大容量磁碟）；
  • Codex 判最嚴重、Grok 上一輪實跑後判安全——兩家都有實證，分歧在判斷。

依規矩我不自己決定。本輪我做的是：把現行行為用測試明文釘死（標明「記錄之，非背書」）， 再加一條破壞測試鎖住真正的越界（刪到無關檔案）——不論三家怎麼裁，越界永遠該紅。 破壞測試 20 → 22 條。

第四輪審查：那件交裁的事定案了，另外又抓到同一型的第二個

RULING-2 三家一致裁「維持現狀」 ——連 Codex 自己都撤回了他上一輪的最嚴重判定。 他的理由：跟著捷徑走本來就是「存放目錄」這個設定的既有語意； 如果刪除拒絕它，那匯入、列表、刪除三件事的語意就會不一致（只有刪除特別龜毛）。 和我上一輪的分析一致。我已經把那條測試的說明從「待裁定」改寫成「已裁定行為」， 措辭直接採用 Codex 給的版本，並補上裁定經過。

第三輪那條（顯示「刪除中…」的開關）也確認關掉了（由原本提出的 Grok 重跑自己的反例）。

但 Composer 和 Grok 兩家各自獨立地抓到同一型的第二個：上一輪我修「A 的回應不能動到 B」時， 只鎖了成功的那一半，失敗的那一半沒鎖——catch 裡雖然有比對，卻沒有任何測試在管它。 兩家各自把那個比對拿掉跑一次，18 條全綠（又是假的綠燈）； Grok 再寫臨時測試證明：A 刪除失敗回來時，錯誤訊息「刪除失敗：HTTP 404」 會畫在你正在看的 B 的確認框上。

🔴 這正是我在派工單裡自己問的那題：「顯示錯誤的那個欄位，是不是下一個同樣的問題？」 答案是是。這是本專案第 8 次「我的修法自己開的破口」。已補測試與破壞測試， 拿掉比對現在會恰好弄紅那一條——和兩家預期的完全一樣。

破壞測試 22 → 23 條。

第五、六輪：收斂

第五輪出了一次派工意外（不是產品問題）：三家派出去，其中一家（Composer）在對方雲端服務 斷線、重試三次後失敗，沒有交出東西。另外兩家用同一條指令都正常完成，所以不是我這邊的問題。 另外兩家的結論都是零問題。

但這造成一個死結：規矩要求三家才算數，而「三家派出、只回兩家」讓銷帳被擋， 銷帳被擋又讓下一次派工發不出通行證。我沒有去改治理工具（那是你明令不碰的）， 而是照工具自己錯誤訊息指出的第二條路走：它有一個設計內的逃生口， 其中一種原因就叫「收集失敗」——正是這次的情況，而且有 log 可查。 我用那個逃生口銷帳、逐字附上斷線 log 當理由，然後重派第六輪三家全員。

第六輪：三家一致零問題、可收。 Composer 是第一次完整審這批的最後一個修法， 他重跑了一次：正常時 19 條全過；把那個比對拿掉，只有第 11 條變紅；還原，19 條又全過。 另外兩家獨立複驗同結論。三家也都實際跑過、確認沒有第三個同型問題。

🔴 Composer 還當場糾正了我一個講太滿的說法：我在派工單寫「三個破壞測試的紅集合兩兩不相交」， 他拿實際紀錄一比：其中兩個是有交集的（都會弄紅第 11 條之外的同一條）。 正確講法是「新加的那個跟另外兩個不相交」。這是我第 4 次「講的比做的滿」， 只出現在派工單、沒進產品碼，但一樣記下來。

第三批做了什麼（2026-08-25，已收斂）

第三批＝深度三層防線，三個 Task。這批只處理一件事：「這個欄位看到多遠的未來」如果系統 算不出來，該怎麼辦。

  1. 系統算不出深度時，強制你自己宣告（1.11）——並在畫面上明講「這個數字我驗證不了， 填錯會洩漏未來資料」。🔴 不准因為「其他欄都算得出來」就拿它們的最大值頂替。 另外，外部上傳的檔案，欄名一律不算證據：就算你把欄位取名成系統認得的名字， 一樣要你宣告——因為欄名可以隨便改，改名就能把隔離寬度騙小。
  2. 宣告缺失就禁止進入訓練／測試切分（1.12）——但仍然產得出事件研究表（不做訓練就不會洩漏）。 為此新增了一條「只做事件研究」的執行路徑，因為原本的主流程無條件會做切分， 照現況只能在「違規」和「產不出表」之間二選一。 🔴 沒切分時，信賴區間一律標成「無法計算」——不准硬算：那會產出一個看起來有效、其實錯誤的數字。
  3. 上傳 CSV 時收集答案窗宣告（1.9）——預設取檔案裡最大的可用值（有 1~12 就預設 12）， 要調低必須勾選聲明；批次裡有多種時間週期時逐個各填一格，用一格套用全部會被擋下。 宣告值會直接決定 train/test 的隔離寬度（每個標的各算一個）。

✅ 這批有兩個地方是「先想清楚才寫」而不是寫完再補的：

  • 切分到底有沒有被呼叫，用的是執行期計數（把切分函式換成計數器，跑完看是不是 0）， 不是「翻原始碼裡有沒有出現那個名字」。後者這個 epic 已經被繞過三次了。
  • 兩條路徑會不會各算各的深度，用的是同一個函式物件的身分比對＋呼叫探針。 故意改成「自己算一份」時，算出來的數字完全一樣，所有比數值的測試都抓不到—— 只有呼叫探針轉紅。這正是規格要求「呼叫同一個函式」而不是「結果相等」的原因。

⚠️ 有一處兩個 Task 的規則直接相撞，已具名回報：第二批的「一批裡混了不同定義就拒收」 會把第三批「多種時間週期各填一格」判成不一致（因為逐個週期的根數本來就不同）。 處理方式是把宣告值的寫入排在同質檢查之後——理由是第二批擋的是你宣告的不一致， 不是平台自己導出的逐週期差異。這條已列進審查必答題，三家一致裁定成立。

🔴 第一輪審查抓到 6 條，最重的一條是真的會洩漏：我宣告的隔離寬度根本沒接到切分， 收據上寫 20 根、實際只隔 1 根。 🔴 第二輪確認第一輪反例全死，但抓到我修第一輪時新弄出來的一條：把逐標的的下界壓成全批一個數字， 會讓窗較小的標的被過度隔離——規格書有一行明令禁止這件事。 ✅ 第三輪三家零問題、一致判可以進第四批（審查軌跡 6 → 3 → 0）。 兩輪共 9 條全數修好並各配一條破壞測試（7 → 13 條）。逐條敘述見 GAP-3施工進度.md。

第二批做了什麼（2026-08-25 已收斂）

第二批＝CSV 匯入主線，四個 Task 都做完了：

  1. 用你自己的 CSV 欄名匯入（1.2）——新端點 POST /api/v1/case/import-events/csv。 你上傳自己的 CSV，再逐項告訴系統「我的『是不是正例』那欄＝系統的 label」， 不必先把標頭改成系統要的欄名。沒對映的欄會被忽略，但會明講忽略了哪些，不靜默丟掉。 🔎 這裡有個開工前查出的事實：CSV 其實本來就能匯入——所以 1.2 不是「加 CSV 功能」， 是「加欄位對映」。這個差別決定了做法：不另寫一條解析路徑，對映完就交給既有那條。
  2. 事件編號與指紋改由後端統一算（1.3）——以前前端自己算「來源指紋」，而且只取五個欄， 所以刪掉或改名任一個「未來報酬」欄，指紋都不會變（等於認不出被動過手腳）。 現在改成後端就每一列的完整內容算，前端只負責帶著走，一次都不准自己算。
  3. 時間戳是秒還是毫秒自動判（1.4）——判得出來就轉成毫秒，判不出來就直接拒絕，不猜。
  4. 一批裡混了不同方向／情境就拒收（1.8）——不自動分批、不拿第一列的值套用全批， 而且會指出前 3 個衝突在哪幾列。

✅ 有幾個問題是「把程式故意改壞」才抓出來的，值得記一下：

  • 1.8 一開始擋太兇：把「預設值沒寫出來」誤判成不一致，還誤擋了系統自己產生的多標籤批次 （那本來就該逐列不同）。改成只在你匯入的那條路徑上檢查。
  • 前端那組測試本來會假綠：後端指紋算法改壞時，前端比對用的基準檔沒有跟著重生， 測試照樣全綠。修好之後，同一個壞法會讓前端 5 條測試一起轉紅。
  • 前端另有一個看不見的死角：它比的是「自己跟自己對得起來」，所以後端把序列化換掉它察覺不到。 補上「收到的內容本身還像不像規格」這條獨立檢查後才抓得到。
