🔧 第十批（最後一批）現在在做什麼

這批叫「全棧接線」，九個 Task，是 GAP-3 的最後一批。意思是： 後端早就做好了的東西，前端一個都沒接上。舉例——匯出事件時有五個設定 （情境／對照組怎麼來／用哪個價格進場／報酬怎麼算／決策往前挪幾根）， 後端五個都認得，但前端從頭到尾一個都沒傳，全部走寫死的預設值。

已完成 Task 7.0：把那五個設定變成「可以傳」的參數（還沒有畫面，畫面是下一個 Task）。 順便修正一個預設值——原本進場價預設是「觸發那根的開盤」，但分析層根本不支援這個組合， 等於預設值本身就是個算不出答案的設定。改成「觸發那根的收盤」。 這不影響任何已經算出來的數字（匯出檔早就不寫答案了），變的只有宣告欄的字面。

進行中 Task 7.0b：這是本批最大的一個，它補的是一個現在就存在的洞—— 你從搜尋頁匯出的事件批，裡面沒有「答案」（每個事件後來到底漲跌多少）。 匯出端已經不寫了，分析端又還沒開始算，所以條件 IC 對真實批次目前根本跑不起來。 7.0b 就是把「算答案」這件事搬到分析當下做。

🔴 這批第一天就撞到的兩件事（都不是程式 bug，是規格本身的問題）

一、我的偵察猜錯兩件事，被三家審查員當場打穿。 開工前要先查清楚程式現在長什麼樣， 我列了六個「我沒查但我猜是這樣」的項目——其中兩個猜反了：

我猜的 實際
分析流程裡已經有「事件」這條分支，只是接法可能不乾淨 連那條分支都不存在，要從零建
報酬表還沒有分組結構 早就有了，我要做的是加一組進去，不是新建

第二個特別危險：照我原本的理解做下去，會多做一個結構出來，直接違反規格明文。

二、規格自己跟自己打架。 規格一邊要求「做空的事件，答案要帶負號」， 一邊又把函式的參數表和資料結構都寫死成「拿不到多空方向」。照字面實作必然做不出來。

這件事不是形式問題。我實跑確認：下游沒有任何一層會補這個負號。 所以如果答案不帶負號，做空批次算出來的 IC符號整個是反的—— 數字看起來完全正常，方向卻是錯的，而且沒有任何一關會攔下來。

三家審查員獨立查證後一致判定「必須開修訂檔」。我開了 D-005，把方向做成批次層的一個值 （因為契約本來就禁止一批裡混多空），而不是掛在每一列上。 其中一家（grok）主張掛在每一列，我沒採納——理由是程式證據不是票數： 規格自己的分類表就把「方向」歸在批次層，而且契約既然已經禁止混方向， 做成逐列反而造出一個「寫得出來但不合法」的狀態。 我把 grok 的異議具名保留，並寫死了失效條件：哪天如果放寬「一批不能混多空」， 這個決定就失效、要改回逐列。

順手補上的一個真實破口（Task 7.7 的把關函式）

做 7.0b 的過程中，把 Task 7.7 的把關函式一起做了（兩者必須同批，因為共用同一份 時間換算表）。它擋的是：你選的特徵 run 根本沒涵蓋事件發生的那段期間，卻照樣送去算 IC。

我實掃本機 14 份特徵 run 的描述檔：12 份有時間範圍、2 份完全沒有那個欄位。 規格只規定了「欄位在、但值是空的」怎麼辦，沒規定「欄位根本不存在」。 我裁定兩者一樣擋——資訊量相同（都不知道範圍），放行等於把保護弱化。

這個閘門 18 條測試，每一格都有兩個方向：該擋的擋住，以及不該擋的沒被誤擋。 例如時間格式那條，除了驗「沒帶時區的時間要拒絕」，也驗「帶了時區的要正常通過」—— 只測前者的話，一個「永遠拒絕」的實作也會全綠。這正是上一批五輪重工的病根， 這批從第一個 Task 就這樣做。

破壞測試跑完了：23 條全過，但它抓到的是我自己的四個問題

破壞測試的作法是：故意把程式改壞，看該紅的測試有沒有真的紅。沒紅就代表那條測試是假的。

23 條全部通過。但過程中它抓出四個問題，沒有一個是產品程式的錯，全是我的：

問題 性質
我把「改壞」寫成了語法錯誤，程式根本載入不了 —— 測試在收集階段就掛掉，看起來像「沒有測試變紅」 破壞方式寫錯
我把「改壞」放在錯的那一層 —— 那條保護根本不在我改的地方 測試設計缺陷
我的測試資料把兩個欄位設成同一個值 —— 於是「用哪一個欄位」這件事根本分辨不出來 測試設計缺陷
🔴 我的測試完全沒有經過真正把資料帶出來的那段程式 —— 把後端那一半整個拿掉，我全部測試照樣綠 真實的覆蓋缺口

最後一個最值得講：我原本驗了「資料格式有宣告這個欄位」和「檔案裡有這個值」， 但沒有驗中間那段真的把值搬出來的程式。宣告不會讓任何東西在執行時出現。 這種洞如果沒被抓到，畫面上就會永遠是空的，而所有測試都是綠的。

還有一個要記的：其中一條我改了三次才讓它真的可證偽。原因是我把測試資料放在一個 「好幾層保護剛好重疊」的極端位置——拆掉第一層，第二層還撐著，所以看不出來。 往內移一點之後只剩一層擋，這條保護才真的被測到。

後半段（Task 7.1–7.6）：把那五個設定真的搬到畫面上

前半段（7.0）只是讓那五個設定「可以被傳」，後半段是讓你看得到、改得動：

Task 白話
7.1 匯出頁與匯入頁各長出五個下拉。不能選的值不是藏起來，是灰掉並寫出為什麼——例如「A／B 情境」在匯出頁灰掉，理由是那兩種的答案要靠預測，本批沒做出產生答案的東西
7.2 一道機械閘：畫面上「真的能點」的選項集合，必須等於系統算出來的合法集合；而且選了之後真的要傳到檔案裡。第二層是重點——上一批的病就是「畫面有、但沒傳」
7.3 匯出前把七項設定全部講出來（原本只講四項），而且每一句都由當下實際的設定產生，不是寫死的字
7.4 明講「這批不提供 IC decay 曲線」，並告訴你換答案窗要去哪裡改（不必再匯出一次）
7.5 事件後報酬表由一組變成正例／反例／全體三組垂直排列。全體組會依「反例是怎麼來的」決定算不算得出來，算不出來就講原因，不給你一張空表
7.6 IC 分析頁分成兩區：這批事件的事實（只能看，不能改） 與 這次分析的參數（可以改，而且不會寫回去）

7.6 這個拆分是這批最重要的觀念：以前「批次設定」跟「分析參數」混在一起， 於是改一個分析參數就可能把事件批本身改掉——那會讓同一批事實隨著分析而變。 現在事實欄在畫面上連可以打字的框都沒有（測試直接驗 DOM 裡沒有輸入元件）， 分析參數則另外一區，改了只作用於這一次分析。

這半批我自己抓到的三個問題（都不是產品程式的錯）

問題 怎麼被抓到
我寫的機械閘根本不會紅 —— 我讓測試把真契約塞進畫面元件，於是「契約改了、畫面沒跟」時兩邊一起變，永遠測不出來 破壞測試錄到空紅集合
我的測試資料把其餘四個設定灌成空字串 —— 測試照樣綠，但落檔的四個欄位是非法值 型別檢查（tsc）當場抓到；npm run build 看不到測試檔，所以只跑 build 會漏掉
我的新文案寫了「不需重新匯出」，撞到既有的一條斷言（那條禁止「重新匯出」四個字出現） 既有測試轉紅。我沒有去放寬那條斷言，而是改自己的措辭成「不必再匯出一次」——為了讓自己的新東西過關去鬆綁既有守衛，正是這個 epic 反覆付過代價的形態

還有一個工具面的潛伏缺陷被踩出來：破壞測試的隔離機制整個起不來， 因為 repo 裡有被版控的 numba 快取檔（跑過測試就變髒），而複製工作區時漏了 --binary 參數。 前九批都僥倖沒踩到。已修。

兩輪審查抓到什麼（8/29）

第一輪（R3）三家提了八條，全部成立、全部修掉。 最重的一條三家同時抓到：

我在「匯出頁／IC 分析頁」把「決策位移」這個設定宣稱鎖死為 0， 但實際上只加了 HTML 的提示屬性——使用者打字就能改成 3，而且那個 3 真的會寫進檔案。 更難堪的是：我自己寫了一條測試去確認那個輸入框「不是唯讀」—— 那條測試在保護缺陷本身。

還有一條是老毛病第八次：我在程式碼註解裡寫「這一頁的欄位由那份清單決定」， 但實際上是七段手寫的、連那份清單都沒有 import——往清單加欄位，畫面不會有任何變化。

另外我在派工單裡寫「我沒查的」那一欄，其中一項答案跟我猜的相反： 我以為前端沒辦法直接讀契約檔，其實可以。但兩家審查員同時指出：知道歸知道，不能改—— 改了會讓另一道機械閘失效。所以只改了說明文字，沒動程式。

第二輪（R4）是閉合輪：規則是「誰提的問題，誰自己回來重跑自己的反例」， 不是換個人說「看起來修好了」。三家逐條確認關閉，其中兩家零 finding。

但第三家又抓到一條——而且是我修第一輪時自己弄出來的： 我為了擋住「打字改成 3」加了一個夾值函式，順手把小數也截掉了（1.9 → 1）。 問題是契約規定那欄必須是整數，後端本來就會明白拒絕小數； 前端先偷偷截掉，使用者就永遠看不到那個拒絕，還以為自己填的 1.9 被接受了。 這種「修法自己開新破口」在這個 epic 已經是第六次。已改成：不截值、擋下來、講清楚為什麼。

最後一件值得記的：我在第二輪的派工單裡，把一條我自己沒驗證的宣稱具名交出去請審查員代打 （「兩層防護必須一起拆掉才測得出來」）。審查員實跑後確認我是對的—— 但重點是那條原本只是我的說法，不該由我自己說了算。

✅ 第九批已收案（8/28，IC 分析的「記憶體止血閘」）。這批要做的事很單純： 在 IC 分析啟動之前先看一眼這個 run 有幾個特徵，太多就直接擋下來， 不要等它把記憶體吃爆才發現。上限是實跑量出來的（不是猜的）：本機 8GB， 量到 161,031 個特徵時會撞牆，所以上限設在它的一半＝ 80,515。

🔴 這批的教訓比程式碼本身更值得看：五輪審查，每一輪都抓到同一種錯—— 我把閘門做成「看請求上有沒有寫特徵數」，而不是「看後端待會兒實際會載入哪一個 run」。 於是每一輪都冒出一種新的繞法：

輪次 繞法 方向
一 直接給檔案路徑就繞過 該擋沒擋
二 橫截面把 run 放在另一個欄位 該擋沒擋

前三輪我一直在「補這個欄位」，第四輪才改成模擬後端的選擇邏輯， 第五輪才做到兩邊共用同一段程式——不一致從此在結構上不可能，而不是靠我維持。

🔴 第五輪之後我停下來問了三家「這件事要怎麼才算做得完」——不是再找錯，是問方法。 三家一致給了同一個答案，而且否決了我原本想做的大改：

第六批做了什麼（2026-08-26，已收斂）

第六批＝刪除，三個 Task。一句話：讓你刪掉一批匯錯的事件，而且不留半個孤兒檔。

第三批做了什麼（2026-08-25，已收斂）

第三批＝深度三層防線，三個 Task。這批只處理一件事：「這個欄位看到多遠的未來」如果系統 算不出來，該怎麼辦。

  1. 系統算不出深度時，強制你自己宣告（1.11）——並在畫面上明講「這個數字我驗證不了， 填錯會洩漏未來資料」。🔴 不准因為「其他欄都算得出來」就拿它們的最大值頂替。 另外，外部上傳的檔案，欄名一律不算證據：就算你把欄位取名成系統認得的名字， 一樣要你宣告——因為欄名可以隨便改，改名就能把隔離寬度騙小。
  2. 宣告缺失就禁止進入訓練／測試切分（1.12）——但仍然產得出事件研究表（不做訓練就不會洩漏）。 為此新增了一條「只做事件研究」的執行路徑，因為原本的主流程無條件會做切分， 照現況只能在「違規」和「產不出表」之間二選一。 🔴 沒切分時，信賴區間一律標成「無法計算」——不准硬算：那會產出一個看起來有效、其實錯誤的數字。
  3. 上傳 CSV 時收集答案窗宣告（1.9）——預設取檔案裡最大的可用值（有 1~12 就預設 12）， 要調低必須勾選聲明；批次裡有多種時間週期時逐個各填一格，用一格套用全部會被擋下。 宣告值會直接決定 train/test 的隔離寬度（每個標的各算一個）。

✅ 這批有兩個地方是「先想清楚才寫」而不是寫完再補的：

  • 切分到底有沒有被呼叫，用的是執行期計數（把切分函式換成計數器，跑完看是不是 0）， 不是「翻原始碼裡有沒有出現那個名字」。後者這個 epic 已經被繞過三次了。
  • 兩條路徑會不會各算各的深度，用的是同一個函式物件的身分比對＋呼叫探針。 故意改成「自己算一份」時，算出來的數字完全一樣，所有比數值的測試都抓不到—— 只有呼叫探針轉紅。這正是規格要求「呼叫同一個函式」而不是「結果相等」的原因。

⚠️ 有一處兩個 Task 的規則直接相撞，已具名回報：第二批的「一批裡混了不同定義就拒收」 會把第三批「多種時間週期各填一格」判成不一致（因為逐個週期的根數本來就不同）。 處理方式是把宣告值的寫入排在同質檢查之後——理由是第二批擋的是你宣告的不一致， 不是平台自己導出的逐週期差異。這條已列進審查必答題，三家一致裁定成立。

🔴 第一輪審查抓到 6 條，最重的一條是真的會洩漏：我宣告的隔離寬度根本沒接到切分， 收據上寫 20 根、實際只隔 1 根。 🔴 第二輪確認第一輪反例全死，但抓到我修第一輪時新弄出來的一條：把逐標的的下界壓成全批一個數字， 會讓窗較小的標的被過度隔離——規格書有一行明令禁止這件事。 ✅ 第三輪三家零問題、一致判可以進第四批（審查軌跡 6 → 3 → 0）。 兩輪共 9 條全數修好並各配一條破壞測試（7 → 13 條）。逐條敘述見 GAP-3施工進度.md。

第二批做了什麼（2026-08-25 已收斂）

第二批＝CSV 匯入主線，四個 Task 都做完了：

  1. 用你自己的 CSV 欄名匯入（1.2）——新端點 POST /api/v1/case/import-events/csv。 你上傳自己的 CSV，再逐項告訴系統「我的『是不是正例』那欄＝系統的 label」， 不必先把標頭改成系統要的欄名。沒對映的欄會被忽略，但會明講忽略了哪些，不靜默丟掉。 🔎 這裡有個開工前查出的事實：CSV 其實本來就能匯入——所以 1.2 不是「加 CSV 功能」， 是「加欄位對映」。這個差別決定了做法：不另寫一條解析路徑，對映完就交給既有那條。
  2. 事件編號與指紋改由後端統一算（1.3）——以前前端自己算「來源指紋」，而且只取五個欄， 所以刪掉或改名任一個「未來報酬」欄，指紋都不會變（等於認不出被動過手腳）。 現在改成後端就每一列的完整內容算，前端只負責帶著走，一次都不准自己算。
  3. 時間戳是秒還是毫秒自動判（1.4）——判得出來就轉成毫秒，判不出來就直接拒絕，不猜。
  4. 一批裡混了不同方向／情境就拒收（1.8）——不自動分批、不拿第一列的值套用全批， 而且會指出前 3 個衝突在哪幾列。

✅ 有幾個問題是「把程式故意改壞」才抓出來的，值得記一下：

  • 1.8 一開始擋太兇：把「預設值沒寫出來」誤判成不一致，還誤擋了系統自己產生的多標籤批次 （那本來就該逐列不同）。改成只在你匯入的那條路徑上檢查。
  • 前端那組測試本來會假綠：後端指紋算法改壞時，前端比對用的基準檔沒有跟著重生， 測試照樣全綠。修好之後，同一個壞法會讓前端 5 條測試一起轉紅。
  • 前端另有一個看不見的死角：它比的是「自己跟自己對得起來」，所以後端把序列化換掉它察覺不到。 補上「收到的內容本身還像不像規格」這條獨立檢查後才抓得到。
