## §1 判準（唯一，不隨情境改變）

**安全回歸測試選取（safe regression test selection）**：一條測試（函式層 nodeid）須重跑 ⇔ 自它上次通過以來，它的任一依賴（實際執行到之程式區塊、讀取之檔案、呼叫之外部程式、所處執行環境）有變。依賴未變 ⇒ 上次結果仍有效，不重跑（非不測：結果可證不變）。依賴有變 ⇒ 必跑，不論耗時。

- 禁止：依「是否 import 被改模組／是否用到被改檔案」整檔挑選（過寬）；依耗時跳過（＝不測）；依人工判斷「它驗的性質不受影響」排除（不可證）。
- 本判準只決定「跑哪些」；「每條測試跑多快」屬測試設計（§7），不得以少跑代替。

## §2 依賴之記錄（每次測試執行時自動更新）

以既有 TESTREG 記錄器（`tests/fixtures/testreg_recorder_plugin.py`，經 `tests/conftest.py` 作用於全部測試）為掛點，逐測試記錄：

| 依賴類 | 記錄法 | 比對粒度 |
|---|---|---|
| Python 程式 | coverage.py 動態 context（逐測試）＋分支覆蓋 | 函式／區塊內容雜湊（不用行號，避免行號平移誤判） |
| 子程序與多執行緒 | coverage 子程序支援（`COVERAGE_PROCESS_START`）與 `concurrency = thread, multiprocessing` | 同上 |
| numba 編譯核心（coverage 追不進 JIT 本體） | 靜態解析：核心函式 → 呼叫它之 Python 函式；核心原始碼雜湊併入呼叫者之依賴 | 核心原始碼雜湊 |
| 經 C 函式庫讀檔（h5py、pandas HDF/parquet、pyarrow、numpy load/memmap）及 Python `open` | 於上述函式庫之 Python 入口與 `sys.addaudithook("open")` 記錄路徑 | 檔案內容雜湊（大檔用大小＋mtime＋抽樣雜湊之既有 kline_sha_cache 機制） |
| 外部程式（shell 腳本、git） | `sys.addaudithook("subprocess.Popen")` 記錄命令；被呼叫之 repo 內腳本視為依賴檔 | 腳本雜湊；讀「目前 git 狀態」（HEAD、工作區）之測試每次必跑 |
| 執行環境 | Python 版本、`pip freeze` 雜湊、`pytest.ini`、`tests/conftest.py`、`tests/fixtures/*plugin*`、記錄器本身 | 任一變 ⇒ 全部重跑 |

每測試存：依賴集合＋各依賴雜湊＋最後結果＋記錄時之 commit。選取比對「現行雜湊 vs 該測試記錄時雜湊」（非比對 git 差異範圍，避免跨多提交漏判）。

## §3 選取規則（工具計算，不經人工）

1. 無依賴紀錄之測試（新測試、紀錄遺失）⇒ 必跑。
2. 測試檔本身內容變 ⇒ 該檔受影響之測試必跑（函式層，以內容雜湊）。
3. 依賴雜湊任一不同 ⇒ 必跑。
4. 執行環境類任一變 ⇒ 全部重跑（業界：依賴升級觸發全量）。
5. 上次失敗或錯誤之測試 ⇒ 必跑。
6. 其餘 ⇒ 不跑，沿用上次結果（收據記錄沿用來源）。

## §4 時機（業界：每次提交跑快的受影響測試，合併前跑全部受影響測試）

- **每批（提交）**：§3 選中且紀錄耗時 < 60 秒之測試＋該票規格指定之驗收。
- **收案（合併前）**：自該票起點至最終程式之累積改動，§3 選中之全部測試（含重型）對最終程式跑一次，全綠才准收案。重型不得因「中間批已跑過」而免跑，亦不在中間批重複跑。
- **流程**：每票於票分支施工，收案檢查通過才合併回 main（業界合併閘）。
- **兜底**：機器閒置時定期全量跑一次（抓依賴追蹤遺漏），失敗即開修正，不擋日常提交。

## §5 過渡規則（§6 完成前）

每批由主委列「本批改動之函式／檔案 → 依 §1 會執行到它的測試」清單，附理由，交使用者前先自查是否違反 §1 之禁止三項；收案前依 §4 跑重型一次。不得以模組 import 整檔挑選。

## §6 建置清單（完整；完成以 §8 驗收為準）

建置方式（2026-10-26 使用者核可）：子代理實作、主委驗收、委員審碼（輪數不設限，以漏洞少為準）。防漏三則：
- **核心用業界現成工具 pytest-testmon**（逐測試程式區塊依賴＋內容雜湊），自寫只限其未涵蓋之資料檔、numba 核心、外部腳本／git、執行環境四類；動工第一步實查其對 Python 3.9.6／pytest 8.4.2／coverage 7.10.7 之支援，不支援即回報、不自寫替代核心。
- **送審前 §8 驗收全數實跑通過**（含每類改壞對照轉紅），結果附於審碼 brief。
- **每條審碼 finding 先全文搜同類全部實例一次修完**，範圍寫入收斂檔。

1. 依賴記錄（§2 全表）。
2. 選取工具（§3），取代 `scripts/testreg.py impact` 之模組級 taint。
3. 時機分配（§4）：每批快速層／收案全受影響層之兩種選取輸出。
4. 兩道機器檢查：提交時（秒級）核對「本批選取集於此樹全通過」之收據；收案時核對「累積選取集於最終程式全通過」之收據。無收據即拒。
5. 非決定性處置：計時斷言移出正確性測試改列 `perf`（現有 `tests/performance/test_multi_window_perf.py`、`tests/feature_engineering/test_batch1_followup.py` 之計時項、`tests/momentum/test_feature_factory_optimization_perf.py` 等，建置時以全文 grep 列全）；隨機須固定種子；「依賴未變而結果翻轉」者標不穩定並經 `flaky_quarantine` 隔離。
6. 定期全量跑指令與收據。
7. 票分支流程（施工於分支、收案閘通過後合併）與既有 commit／push hook 之接合。
8. CLAUDE.md 一行指向本檔；HANDOFF 坑段；記憶。
9. 首次全量跑建立依賴紀錄（量化約 31 小時＋治理約 2.2 小時，依 `.testreg/summary.json` 加總；記錄負擔另計，實跑才知）；重型真實資料測試串行、輕量可平行；附卡死監看。
10. 自我驗證（§8）。
11. 已查得之測試內重複計算（屬 §7，不影響選取正確性）：`tests/momentum/Analysis/test_preprov_survivor_identity.py` 三次 IC 分析各約 4,200 秒、`tests/governance/test_govb1_contract_matrix.py` 三條各跑一次 `govb1_final_gate.sh --only g7`——讀碼確認是否同一計算，同者合併。特徵生成之跨檔重複僅佔重型層 5–8%（2026-10-26 唯讀盤點），不做共用。

## §7 範圍外（不得以選取取代）

測試本身寫法之效率（共用 fixture、去重複計算）、重型測試應否存在（依路徑覆蓋判準，見 CLAUDE.md「測試／量測設計＝路徑覆蓋」）。

## §8 驗收（可證偽）

- 只改某測試獨有執行之一個函式 ⇒ 該測試必被選中；未執行該函式之測試不被選中。
- 改 numba 核心本體 ⇒ 呼叫者之測試被選中。
- 改某資料檔（h5／parquet／json）⇒ 讀過它之測試被選中，未讀者不被選中。
- 改子程序執行之腳本 ⇒ 該測試被選中。
- 改 `pytest.ini`／`tests/conftest.py`／`pip freeze` ⇒ 全選。
- 新增測試 ⇒ 被選中。
- 每條反例各有改壞對照：關掉該類依賴記錄 ⇒ 對應驗收轉紅。
- 以 FFPROD b2 真實改動回放：列出選中集合與理由給使用者。
