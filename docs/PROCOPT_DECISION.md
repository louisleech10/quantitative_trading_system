## 一、先修正主委的測量錯誤

主委原以「全專案 798 個 reconcile 輪次」主張「12 輪是流程常態」。**這個推論錯了。**

| 指標 | 實測（委員） |
|---|---|
| 審查票數 | **135** |
| 輪數中位數 | **2** |
| p90 | **7** |
| ≥10 輪之票 | **僅 8 張** |

798 含 stamp／consult／歷史命名，**不是 SPEC 審查輪數之期望值**。

⇒ **12 輪是肥尾，不是常態。** 流程確實有問題，但要治的是
「**什麼條件讓一張票掉進肥尾**」，不是「所有票都太多輪」。

## 二、肥尾的機制（兩家獨立同判）

```
審查對象是「會在輪間被整份改寫的活文件」
    × 停輪條件＝「兩家零 finding」
    × 批次修補（一次改 N 處）
    ⇒ 非單調重輪
```

`templates/BRIEF_REVIEW_TEMPLATE.md` §6 **早已明文警告**此組合會製造非單調重輪。
寫在範本裡，實務仍在用——**這證明「寫進文件」不是有效的防護**。

加速器（會讓票掉進肥尾的額外條件）：
- **產品與治理共用同一審查佇列**：治理修補轉成產品零交付的額外輪次
  （本 session 實例：3.5 小時、4 輪、7 條 findings、產品端零交付）
- **需求反轉**（`splitunify-b9` 有，EVENTSCAN 沒有）
- **實作與審查混在同一輪**（同上）

## 四、業界對照（委員實查，具體非泛論）

| 尺度 | 本專案 | 業界常態 |
|---|---|---|
| 單票審查輪數 | median 2／p90 7／max 50 | 設計審查 1–2；RFC last-call 2–3；量化期刊 referee 1–3 |
| 寫 vs 審 wall-clock | EVENTSCAN **20 分 : 12 時（36:1）** | 同數量級（數小時到數日） |
| 何時開始寫碼 | 中／大鐵律：凍結 SPEC 前不實作 | 設計「夠用」後即開 spike／薄切片 |
| 停輪條件 | 近乎零 finding | **P0/P1 閉合、nits 可後補** |

⇒ **本專案的中位數 2 輪接近業界**。極端在肥尾，以及「36:1 的寫／審比且可執行產物 0」。

⇒ **最大的單一差距是停輪條件**：業界停在「P0/P1 閉合」，本專案停在「零 finding」。
當每次修補都可能引入新缺陷時，**零 finding 在數學上不可達**。

## 六、改法（主委五項 ＋ 委員五項，逐項附裁決）

### 主委五項

| 提議 | 兩家裁決 | 最終形狀（已依委員修正） |
|---|---|---|
| **A 薄切片先行** | 部分採納 | 時機自「第 3 輪前」提前到 **fan-out 之前（第 0 輪）**——等到 R3 已過曲線最陡的 R1–R2。對純治理票不強制（會變假門檻） |
| **B 逐條修補** | 採納（須配停輪） | 粒度自「一次一條」改為 **一次一個群集**（大量 1:1 配對，按條修會把同一缺陷做兩次）；且須配 **repair manifest**（changed fact／所有落點／預期不變項／驗證命令） |
| **C 範圍鎖** | 採納 | 審查標的 R1 定案後不得增加；**但不綁進 `brief_conformance_check.sh`**——該檔歷史上三次機械綁法皆失敗且使用者已裁定不綁。改為收斂後以 `git diff --name-only` 對審查標的做集合差 |
| **D 分類式停輪** | 部分採納 | 主委版之「兩類皆為零才凍結」**仍不可達**；改為 **規格不完備之 P0/P1 才擋凍結；copy-drift 不擋，凍結後 SMALL_INLINE** |
| **E 文件形狀** | 部分採納 | **駁回**以行數為拆檔閘（再拆會把「N 態」複製到更多落點）；只採「**禁止手寫計數詞，改指 fact-key 列序**」 |

### 委員另提五項

| 改法 | 內容 |
|---|---|
| **F 輪次熔斷** | 達到某輪數上限即強制停下重新界定範圍，不自動續輪 |
| **G 產品／治理分流** | 治理缺陷走獨立票；其 finding 可擋治理交付，**不得重新打開已鎖定的產品 contract block** |
| **H stamp 只重簽 delta** | 戳記失效不觸發全文重審 |
| **I Contract-block ledger** | 每個 block 固定 authority／owner／inputs／consumers／negative case／mutation／stop condition；審查輸入自「整張 SPEC」改為「**block baseline + diff**」，全文掃描只在 authority 變更或範圍擴張時做一次 |
| **J No-repair-without-evidence** | P0/P1 或動到資料／契約之 finding，修補同批須有可執行反例或明確 read-only proof；沒有 seam 就標殘留，不以「已採納」代替可行性 |

🔴 **委員獨立指出既有守衛之模型缺口（與本 session 之 RESID-14 是同一件事）**：
`spec_xref_check` 只驗「token **被拿掉**後是否仍有殘留引用」，
**不驗「新增一個 state／count／ordinal 後是否回填了所有 consumer」**——
這是單向而非雙向 closure。本 session R11／R12 的多數缺陷正落在未覆蓋的那一半。
⇒ 改法 I（contract-block ledger）之 `consumers` 欄即為補這一半而設。
