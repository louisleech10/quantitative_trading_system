### r2 推翻 r1 之三項（其中兩項是主委核心診斷）

**① 「停輪＝零 finding、故不可達」為假。**

錯因有二——主委把**範本文字當成執行中的規則**；並把 `P3-00` sentinel 算進剩餘 findings
（`splitunify`／`gap2` 末輪之「3 條」全是 sentinel，實質為 0）。

**② 「量化沒東西可跑、所以比治理嚴重」為假。**

無顯著差異，且方向與假設**相反**（最長的 EVENTSCAN 可跑率高、最短的 EVTLABEL 低）。

**③ 非單調之主因不是批次修補，是「換審查標的」。**
9 票最大回升點全部是相位切換：`gap2` r6→r7 為 **SPEC 實質 0 → TODO 首審 20 條**；
`gap3` r6→r7 為 **0 → 13**；`gap1` r7→r8 為 **1 → TODO 22 條**；`splitunify` r13→r14 換標的。
批次修補降為**同文件內之加速器**（EVENTSCAN R8 等仍成立），但解釋不了 0→20。

### 真因（兩家獨立同判）

**CLAUDE.md 中／大鐵律之相位串接**：規則要求「SPEC 對抗審 → 凍結 → TODO 對抗審」。
SPEC 達實質 0 後**自動開一輪 TODO 全審**，於是曲線出現 0→20、0→13。
⇒ 量化票相對治理票多出的輪數，主要來自**這個相位串接被當成同一條曲線**，
不是「量化票比較難審」。`gap2`／`gap3` 沒有治理岔路仍 ≥8 輪即為證。

## 二、肥尾的機制（兩家獨立同判）

```
審查對象是「會在輪間被整份改寫的活文件」
    × 停輪條件＝「兩家零 finding」
    × 批次修補（一次改 N 處）
    ⇒ 非單調重輪
```

`templates/BRIEF_REVIEW_TEMPLATE.md` §6 **早已明文警告**此組合會製造非單調重輪。
寫在範本裡，實務仍在用——**這證明「寫進文件」不是有效的防護**。

加速器（會讓票掉進肥尾的額外條件）：
- **產品與治理共用同一審查佇列**：治理修補轉成產品零交付的額外輪次
  （本 session 實例：3.5 小時、4 輪、7 條 findings、產品端零交付）
- **需求反轉**（`splitunify-b9` 有，EVENTSCAN 沒有）
- **實作與審查混在同一輪**（同上）
