# Optuna 參數優化系統文檔

## 一、系統概述

### 系統定位
量化研究工作平台 - 協助交易者從海量歷史數據中發現有效的交易策略

### 核心構想
不同於傳統量化平台的「策略→參數優化→回測」流程，本系統採用「案例探索→Pattern 發現→ML 優化→策略驗證」的創新路徑，透過機器學習自動發現市場中的盈利 Pattern

### 系統目標
- 從歷史數據中搜尋符合特定條件的案例（正例/反例）
- 使用技術指標，計算OLHC,VOLUME, TAKER RATIO，然後計算策略信號發生的次數，分析正反案例的信號密度特徵
- 透過 Optuna 優化引擎找出最佳參數組合
- 量化評估策略的有效性與穩定性

### 本系統 vs 傳統回測系統

#### 核心理念差異

| 維度 | 傳統回測系統 | 本系統（案例密度分析） |
|------|-------------|---------------------|
| **優化目標** | 最大化勝率或盈虧比 | 最大化正反例信號密度差異 |
| **數據來源** | 完整時間序列（所有K線） | 特定案例（關鍵時刻） |
| **參數搜索依據** | 基於回測績效 | 基於Pattern識別能力 |
| **過擬合風險** | 高（容易fitting noise） | 中等（專注於pattern） |
| **計算成本** | 高（需模擬所有交易） | 低（只計算密度統計） |

#### 為什麼不直接用勝率和盈虧比？

**傳統回測的問題：**

1. **過擬合嚴重**：
   - 參數可能碰巧在歷史上表現好
   - 無法區分「真正的策略優勢」和「運氣成分」
   - 在樣本外數據常常失效

2. **無法區分技能與運氣**：
   - 牛市中隨便買都賺錢，高勝率可能只是趨勢的結果
   - 熊市中再好的策略也難有高勝率
   - 績效受市場環境影響太大

3. **計算成本高**：
   - 需要模擬每一筆交易的進出場
   - 需要考慮滑點、手續費、資金管理
   - 優化50次試驗可能需要數小時

**案例密度分析的優勢：**

1. **專注Pattern發現**：
   - 研究「策略信號是否在起漲前聚集」這個本質問題
   - 不被短期績效波動干擾
   - 更容易發現市場微觀結構

2. **統計驗證嚴謹**：
   - 使用p-value檢驗統計顯著性
   - 使用Cohen's d衡量效果大小
   - 用CV驗證時間穩定性

3. **計算效率高**：
   - 只需判斷true/false，不需模擬交易
   - 50次試驗可能只需15分鐘
   - 適合快速迭代測試假設
   - 有效策略才會進入下一步ML訓練，然後再進入傳統回測測試

#### 適用場景

**本系統最適合：**
- 探索市場微結構（如「起漲前會出現什麼技術指標Pattern？」）
- 發現新的交易信號
- 驗證策略假設（如「三線排列真的能預測起漲嗎？」）
- 快速篩選大量參數組合

**傳統回測更適合：**
- 驗證完整交易策略（包含進出場、止損止盈規則）
- 計算實際績效指標（年化收益率、最大回撤）
- 優化交易執行細節（最佳進場點、倉位管理）
- 評估資金曲線和風險指標

#### 建議工作流程

**四階段漸進式開發：**

1. **第一階段（本系統）**：Pattern探索
   - 使用案例密度分析發現有效Pattern
   - 例如：找到EMA 7/17/28這組參數
   - 驗證統計顯著性和穩定性

2. **第二階段**：策略設計
   - 將Pattern轉換為完整交易策略
   - 加入進出場規則、止損止盈
   - 設計資金管理方案

3. **第三階段（傳統回測）**：績效驗證
   - 用回測系統計算年化收益、勝率等
   - 評估最大回撤、夏普比率
   - 在樣本外數據驗證

4. **第四階段**：實盤測試
   - 小資金實盤運行
   - 監控實際滑點和成本
   - 持續優化策略參數

### 核心組件功能說明

**Optuna優化引擎**
- 功能：智慧搜索最佳參數組合
- 特色：支援TPE、CmaEs等多種優化演算法
- 優點：自動化參數搜索，無需手動調整

**信號密度分析器**
- 功能：計算每個案例的信號密度
- 輸入：案例資料、策略參數
- 輸出：密度值、統計指標（separation、p-value等）

**結果分析器**
- 功能：分析優化結果，產生報告
- 提供：穩定性分析、收斂分析、參數重要性等
- 特別強調：按案例月份分析穩定性（2025-12-21修復）

### 數據流動過程

1. 用戶上傳案例CSV → 儲存到JSON
2. 用戶啟動優化 → Optuna開始試驗
3. 每次試驗 → 從HDF5讀取K線 → 計算密度 → 儲存到SQLite
4. 優化完成 → 從SQLite讀取結果 → 產生視覺化圖表
5. 用戶查看圖表 → 匯出最佳參數

### 優化引擎核心功能
- 自動搜索最佳策略參數組合
- 支援多種優化器（TPE、CmaEs、Random、GP、NSGA-II）
- 預設為使用TPE優化
- 斷點續跑機制（SQLite 持久化）
- 並行多進程優化
- 智能錯誤重試與檢查點保存

### 優化模式
根據訓練窗口配置自動切換：
- **單密度模式**：僅分析近期窗口的信號密度
- **雙密度模式**：同時分析近期與遠期窗口，比較信號聚集程度

#### 關鍵步驟說明

**1. 案例匯入**
- 用戶上傳CSV檔案，包含交易對、時間戳、是否為正例等欄位
- 系統驗證格式正確性
- 儲存到案例資料庫（JSON格式）

**2. 參數建議機制**
- Optuna使用TPE演算法智慧建議下一組要試的參數
- 系統會檢查參數約束（比如短期均線必須小於中期均線）
- 每次試驗的參數都不重複，有系統地探索參數空間

**3. 信號密度計算**
- 對每個案例，提取TO前的K線數據
- 計算技術指標（如EMA）
- 判斷每根K線是否符合策略條件
- 計算符合比例（就是密度）

**4. 統計檢驗**
- t檢驗：驗證正反例分布是否有顯著差異
  - 單密度模式：比較「正例密度」vs「反例密度」
  - 雙密度模式：比較「正例 $M$」vs「反例 $M$」（與優化目標對齊）
- Cohen's d：衡量效果大小（效果量），建議與 p-value 一起看
  - 單密度模式：以密度計算
  - 雙密度模式：以 $M$ 計算
- CV：衡量時間穩定性（按案例月份）
  - 單密度模式：正例每月「平均密度」的波動
  - 雙密度模式：正例每月「加權平均 $M$」的波動（並避免分母接近 0 造成爆炸）

#### Cohen's d 詳細說明

**為什麼需要 Cohen's d？**

p-value 只告訴我們「有沒有差異」，但不告訴我們「差異有多大」。即使差異很小，只要樣本數夠多，p-value 也可能顯著。Cohen's d 就是用來衡量「差異的實際大小」。

**白話解釋計算方式：**

想像有兩組學生的考試成績：
- 正例組（起漲成功）：平均分數 80 分
- 反例組（起漲失敗）：平均分數 60 分
- 兩組的標準差：大約 10 分

Cohen's d = (80 - 60) / 10 = 2.0

這個 2.0 表示「兩組的平均差距是 2 個標準差」。

**在本系統中的意義：**

$$ d = \frac{\bar{x}_{pos} - \bar{x}_{neg}}{s_{pooled}} $$

其中 $\bar{x}$ 代表群體平均（單密度用「密度」，雙密度用「$M$」）。

**使用的密度數據：**
- **單密度模式**：使用觀察窗口內的密度（比如 TO 前 24 根 K 線）
- **雙密度模式**：使用每個案例的 **歸一化聚集度 $M$**（同時考慮 Near 與 Far 的相對偏向）
  - 注意：雙密度模式的統計檢驗（p-value、Cohen's d）以 $M$ 為主，才能與 Optuna 的優化目標一致

**合併標準差（Pooled Standard Deviation）的計算：**

這個標準差是把正例和反例兩組數據的變異程度「合併」計算出來的：

$$
s_{pooled}=\sqrt{\frac{(n_1-1)s_1^2+(n_2-1)s_2^2}{n_1+n_2-2}}
$$

其中：
- `std1` = 所有正例密度的標準差
- `std2` = 所有反例密度的標準差
- `n1` = 正例案例數量（比如 30 個）
- `n2` = 反例案例數量（比如 70 個）

**實際計算範例：**

假設有 30 個正例案例、70 個反例案例：

**第1步：計算各組的統計數據**
- 正例密度：[0.72, 0.78, 0.71, 0.75, ...] 共 30 個數值
  - 平均值 = 0.75
  - 標準差 std1 = 0.08
- 反例密度：[0.42, 0.48, 0.43, 0.46, ...] 共 70 個數值
  - 平均值 = 0.45
  - 標準差 std2 = 0.10

**第2步：計算合併標準差**
```
pooled_std = sqrt( ((30-1)×0.08² + (70-1)×0.10²) / (30+70-2) )
           = sqrt( (29×0.0064 + 69×0.01) / 98 )
           = sqrt( (0.1856 + 0.69) / 98 )
           = sqrt( 0.8756 / 98 )
           = sqrt(0.00894)
           = 0.0946
```

**第3步：計算 Cohen's d**
```
Cohen's d = (0.75 - 0.45) / 0.0946
          = 0.30 / 0.0946
          = 3.17
```

這個 3.17 表示正反例的密度差距有「3.17 個標準差」那麼大，屬於非常大的效果！

**如何解讀數值？**

| Cohen's d 範圍 | 效果大小 | 實際意義 |
|---------------|---------|---------|
| < 0.2 | 很小 | 策略幾乎沒有區分能力 |
| 0.2 - 0.5 | 小 | 策略有一些區分能力，但不強 |
| 0.5 - 0.8 | 中等 | 策略有明顯的區分能力 |
| > 0.8 | 大 | 策略有很強的區分能力 |
| > 1.2 | 很大 | 策略有非常強的區分能力 |

**實際應用範例：**

**案例A：優秀策略**
- Cohen's d = 1.5
- 意義：正例的信號密度比反例高出 1.5 個標準差
- 結論：這個策略非常有效，能清楚區分起漲成功和失敗的情況

**案例B：普通策略**
- Cohen's d = 0.6
- 意義：正例的信號密度比反例高出 0.6 個標準差
- 結論：策略有中等效果，可以使用但不是特別強

**案例C：無效策略**
- Cohen's d = 0.15
- 意義：正反例的信號密度幾乎一樣
- 結論：這個策略基本無效，無法區分起漲成功和失敗

**重要提醒：**

- **Cohen's d 和 p-value 要一起看**：
  - p-value < 0.05：確認差異不是巧合
  - Cohen's d > 0.5：確認差異夠大、有實用價值

- **只有 p-value 小不夠**：可能樣本數很大，但實際差異很小（比如密度差距只有 0.05）
- **只有 Cohen's d 大也不夠**：可能是運氣好，樣本數太少不可靠

**5. 結果分析**
- 系統自動生成多種視覺化圖表
- 幫助用戶理解哪些參數最重要
- 評估策略的有效性和穩定性

## 三、統計指標計算方法

### 核心概念：信號密度（Density）

#### 什麼是信號密度？
信號密度是指在觀察窗口內，有多少比例的K線符合策略條件。這是一個0到1之間的數值，例如0.75表示75%的K線符合策略。

#### 計算方式（用白話說明）
假設我們觀察案例起漲點TO之前24根K線：
1. **確定觀察範圍**：決定要看TO前多少根K線（比如24根）
2. **逐一檢查**：對每根K線檢查是否符合策略條件（比如短期均線>中期均線>長期均線）
3. **計算比例**：符合條件的K線數量 ÷ 總K線數量

#### 實際範例說明

**正例案例（起漲成功）：**
- 觀察TO前24根K線(NEAR)，發現有18根符合三線排列
- 信號密度 = 18÷24 = 0.75（75%符合）
- 意義：在起漲前，策略信號密集出現

**反例案例（起漲失敗）：**
- 觀察TO前24根K線(NEAR)，只有6根符合三線排列
- 信號密度 = 6÷24 = 0.25（25%符合）
- 意義：策略信號稀疏，沒有聚集現象

#### Separation（分離度）的計算

收集所有案例的密度後：
1. 計算所有正例的NEAR平均密度（比如0.73）
2. 計算所有反例的NEAR平均密度（比如0.26）
3. 兩者相減得到Separation = 0.73 - 0.26 = 0.47

**解讀**：Separation = 0.47表示正例的信號密度平均比反例高47%，說明策略有區分能力。

### 單密度模式統計指標

**核心指標**
- **信號密度（Density）**：案例起漲點TO 前 N 根 K 線中符合策略的比例（0.0 ~ 1.0）
- **正例平均密度（Positive Avg Density）**：所有正例案例的NEAR平均信號密度
- **反例平均密度（Negative Avg Density）**：所有反例案例的NEAR平均信號密度
- **分離度（Separation）**：正例NEAR平均密度 - 反例NEAR平均密度（-1.0 ~ 1.0）

**統計檢驗指標**
- **P-value**：檢驗正反例密度分布的統計顯著性（< 0.05 視為顯著）
- **Cohen's d**：效果量大小（> 0.5 為中等效果，> 0.8 為大效果）
- **變異係數（CV）**：標準差/平均值，衡量穩定性（< 0.3 為穩定）

**計算方式**
1. 對每個案例，計算 案例起漲點TO 前 N 根 K 線的策略符合度
2. 匯總所有正例的NEAR密度值，計算平均值與標準差
3. 匯總所有反例的NEAR密度值，計算平均值與標準差
4. 計算 Separation = 正例NEAR平均 - 反例NEAR平均
5. 執行 t 檢驗計算 P-value，計算 Cohen's d 效果量

### 雙密度模式統計指標（黃金公式版）

**核心指標：歸一化聚集度 ($M$)**
我們不再使用比率 (Ratio)，而是使用歸一化指標 $M$ 來衡量信號是否聚集在近期。
- **公式**： 此處Near和Far為密度
  $$ M = \frac{\text{Near} - \text{Far}}{\text{Near} + \text{Far} + \epsilon} $$
- **範圍**：-1.0 到 +1.0
  - **+1.0**：完美聚集（信號只在近期出現）
  - **0.0**：隨機分佈（近期遠期信號一樣多）
  - **-1.0**：反向聚集（信號只在遠期出現）
- **\(\epsilon\)**：建議使用 $1e-5$，主要用於避免 `Near=0` 且 `Far=0` 時分母為 0
- **重要說明**：
  - 系統不再剔除 `Far=0` 案例；此時若 `Near>0`，會得到 $M\approx 1$，代表方向強烈偏向 Near
  - 但該案例是否會「主宰分數」取決於權重 $w$（Near 很小時權重也很小）

**強度加權 ($w$)**
為了避免「稀疏數據」誤導系統（例如只出現一次信號就拿滿分），我們引入權重。
- **公式**：$w = \text{Near信號數} + \text{Far信號數}$
- **意義**：信號出現次數越多的案例，對總分的影響越大。

**加權統計（對正例/反例各自計算）**
- **加權平均**：
  $$ \mu = \frac{\sum (w_i\cdot M_i)}{\sum w_i} $$
- **加權標準差**：
  $$ \sigma = \sqrt{\frac{\sum w_i (M_i-\mu)^2}{\sum w_i}} $$
  （這裡採用以 $\sum w_i$ 為分母的定義，方便一致比較與避免歧義）

**優化目標：黃金評分 (The Golden Score)**
Optuna 試圖最大化的最終分數。
- **公式**：$\text{Score} = \text{區分度} - \text{穩定性懲罰}$
- **區分度 (Separation)**：正例的加權平均 $M$ - 反例的加權平均 $M$
- **穩定性懲罰 (Penalty)**：如果正例的表現忽好忽壞（標準差大），分數會被扣減。

更完整的表示：

$$
  \text{Score} = (\mu_{pos}-\mu_{neg}) - \lambda\cdot(\sigma_{pos}+0.5\cdot\sigma_{neg})
$$

其中 $\lambda$ 建議預設為 1.0。

**邊界條件（避免 0/0 與退化解）**
- 若正例組的 $\sum w_i=0$：代表「正例完全沒訊號」，此 trial 沒有辨識力，應直接視為無效（剪枝/淘汰）
- 若反例組的 $\sum w_i=0$ 且正例組 $\sum w_i>0$：可能是好參數（低假陽性）
  - 實務上可視反例為中性：令 $\mu_{neg}=0,\sigma_{neg}=0$ 以完成計分
  - 但需搭配「正例覆蓋」門檻（例如正例有足夠多案例真的觸發），避免只靠極少數案例拿高分
- 若正例組的 $\sum w_i=0$ 且反例組的 $\sum w_i=0$：代表正反例都無訊號，屬於退化解，應直接視為無效（剪枝/淘汰）
- 若正例組的 $\sum w_i>0$ 且反例組的 $\sum w_i>0$：屬正常情況，使用黃金評分公式直接計分

**計算方式**
1. 對每個案例，計算 $M$ 值和權重 $w$。
2. 分別計算正例和反例的「加權平均 $M$」和「加權標準差」。
3. 計算 Score = (正例平均 - 反例平均) - (正例標準差 + 0.5 × 反例標準差)。

## 四、Optuna 最佳 Trial 選擇機制

### 單目標優化（預設模式）

**優化方向**
- Direction = "maximize"（最大化目標值）

**選擇邏輯**
1. 收集所有 COMPLETE 狀態的 trials
2. 按目標值（Separation 或 黃金評分 Score）降序排列
3. 取目標值最大的 Trial 為最佳解

**API 調用**
- `study.best_trial`：返回目標值最大的 Trial
- `study.best_value`：返回該 Trial 的目標值
- `study.best_params`：返回該 Trial 的參數組合

**範例**
- Trial #1：目標值 = 0.35，參數 = {short: 5, mid: 15, long: 25}
- Trial #2：目標值 = 0.42，參數 = {short: 7, mid: 17, long: 28} ← 最佳
- Trial #3：目標值 = 0.28，參數 = {short: 3, mid: 14, long: 22}

結果：`best_trial = Trial #2`，`best_value = 0.42`

### 多目標優化（啟用時）

**優化方向**
- Directions = ["maximize", "maximize"]（同時最大化 Separation 與 Stability）

**Pareto 前沿概念**
- 無單一「最佳」Trial，而是一組非支配解（Pareto Front）
- Trial A 支配 Trial B 條件：A 在所有目標上 ≥ B，且至少一個目標 > B
- Pareto 前沿：所有不被其他 Trial 支配的 Trial 集合

**系統提供**
- `study.best_trials`：返回 Pareto 前沿所有 Trials（複數）
- `pareto_analyzer.get_knee_point()`：推薦膝點（平衡兩目標的最佳解）

## 五、優化目標判斷標準

### 單密度模式優質參數標準
- Separation > 0.3（正反例有明顯差異）
- P-value < 0.05（統計顯著）
- Cohen's d > 0.5（中等以上效果量）
- Stability CV < 0.3（穩定性佳）

### 雙密度模式優質參數標準
- **Score > 0.3**：策略具有基本的預測能力。
- **Score > 0.5**：策略表現優秀。
- **正例加權平均 M > 0.4**：正例有明顯的信號聚集傾向。
- **Stability CV < 0.3**：策略在不同月份的表現穩定（這是最重要的過濾指標）。

### 策略穩定性分析

#### 什麼是穩定性？
穩定性衡量的是：最佳參數在不同時間段的表現是否一致。如果一組參數只在某幾個月有效，其他月份失效，就表示不穩定。

#### 為什麼要分析穩定性？
1. **避免過擬合**：如果策略只在特定月份有效，可能只是碰巧
2. **驗證泛化能力**：穩定的策略更可能在未來市場繼續有效
3. **風險控制**：提前發現策略在某些市場環境會失效

#### 如何計算穩定性？

注意：此處的 **Stability CV** 屬於「優化後過濾器（gatekeeper）」；它不直接納入 Optuna 的 Score。Score 內的 $\sigma$ 懲罰是跨案例的離散度，月度 CV 則是跨月份的時間穩定性，兩者衡量面向不同。

**Step 1：取得最佳參數**
- 系統從所有試驗中找出表現最好的參數組合
- 比如：短期均線7、中期均線17、長期均線28

**Step 2：按案例月份分組重新計算**
- 用這組最佳參數，重新計算每個案例的表現指標（單密度為「密度」，雙密度為「$M$」）
- 把案例按發生月份分組（注意：不是試驗執行時間，而是案例本身的時間）
- 計算每個月份的平均表現

補充（雙密度模式）：
- 每個月份計算「加權平均 $M$」（而不是只看 Near 密度），並保留該月可用案例/訊號覆蓋資訊

範例：
- 2025年1月的案例（100個）：平均密度0.35
- 2025年2月的案例（120個）：平均密度0.28 ← 表現較差
- 2025年3月的案例（95個）：平均密度0.32
- ...以此類推到10月

**Step 3：計算變異係數（CV）**
- CV = 標準差 ÷ 平均值
- 比如10個月的平均密度分別是[0.35, 0.28, 0.32, ...]
- 算出這10個數字的標準差和平均值，相除得到CV

雙密度模式建議使用更穩健的定義以避免平均值接近 0：

$$
CV=\frac{\text{Std}(\text{Monthly Means})}{\max(|\text{Mean}(\text{Monthly Means})|,\epsilon)}
$$

並必須加入「每月最少樣本/最少訊號強度」門檻：樣本太少的月份不納入 CV 計算，避免小樣本月份讓 CV 失真。同時建議在報表中提供「納入 CV 的月份數」與「被排除月份數」，方便理解是否存在空窗或稀疏問題。

#### CV值的意義

| CV範圍 | 穩定性評級 | 說明 |
|--------|-----------|------|
| < 0.3 (30%) | ✅ 穩定 | 策略在不同時期表現一致，對市場環境變化不敏感 |
| 0.3 - 0.5 | ⚠️ 中等 | 策略表現有波動，需要進一步分析原因 |
| > 0.5 (50%) | ❌ 不穩定 | 策略可能只在特定市場環境有效，泛化能力差 |

#### 重要修正（2025-12-21）

**之前的錯誤實現**：
- 系統錯誤地按「試驗執行時間」分組
- 導致顯示的是「不同參數在同一個月試驗的變異」
- 這個數據毫無意義（當然不同參數結果不同）

**修正後的正確實現**：

- 顯示「最佳參數在不同月份案例上的表現」

學到的教訓：
- 穩定性分析非常重要，不能只看Separation！
- 必須檢查CV<0.3才能認為策略可靠
- 事件驅動型信號難以系統化

#### 系統使用最佳實踐

1. **案例選擇要清晰**：確保正反例定義明確（如起漲>10% vs <5%）、避免模糊地帶（漲幅5-10%的案例難以分類）

2. **確保足夠樣本**：每類至少20個案例、樣本太少會導致統計不可靠、理想情況：正反例各30-50個

3. **時間跨度要充分**：涵蓋不同市場環境（牛市、熊市、震盪市）、建議至少6-12個月數據、確保穩定性驗證有意義

4. **必須驗證穩定性**：不能只看Separation高就滿意、務必檢查Stability CV < 0.3、查看月度柱狀圖，瞭解哪些月份表現差

5. **考慮多指標組合**：不要只依賴單一指標、結合趨勢指標和震盪指標、但要避免過度複雜化

## 九、開發者擴展指南

### 如何添加新策略

#### 概念說明
策略是一套判斷規則，用來決定某根K線是否符合條件。系統透過策略元數據定義策略的參數範圍和約束條件。

#### 添加步驟（概念流程）

**第1步：定義策略元數據**
- 在策略配置檔中加入新策略
- 定義策略名稱、說明文字
- 列出需要優化的參數（名稱、類型、範圍）
- 設定參數約束條件（如短期必須小於長期）

**第2步：實現計算邏輯**
- 創建新的策略計算函數
- 接收K線數據和參數
- 返回每根K線是否符合策略的判斷結果

**第3步：註冊策略**
- 在策略註冊表中登記新策略
- 將策略名稱對應到計算函數

**第4步（可選）：前端顯示**
- 如果需要在網頁上選擇策略
- 在前端策略清單中加入新選項

#### 實例說明：MACD金叉策略

假設要添加「MACD線上穿信號線」這個策略：

1. **定義元數據**：策略ID為macd_golden_cross、顯示名稱為MACD金叉、參數包括快速週期（8-16）、慢速週期（20-30）、信號週期（7-12）、約束為快速週期必須小於慢速週期

2. **計算邏輯**：先計算MACD線和信號線、檢測MACD從下方穿越信號線的時刻、標記穿越點為true，其他為false

3. **註冊**：在策略註冊表中加入「macd_golden_cross」對應到計算函數

### 如何添加新技術指標

#### 概念說明
技術指標是從K線數據計算出的衍生數值，如移動平均線、相對強弱指標等。

#### 添加步驟（概念流程）

**第1步：實現指標計算**
- 創建指標計算函數
- 接收K線數據和參數
- 返回計算結果（可能是單一數列或多個數列）

**第2步：註冊到指標引擎**
- 在指標引擎中登記新指標
- 設定指標名稱對應到計算函數

**第3步：在策略中使用**
- 策略可以要求指標引擎計算此指標
- 使用指標結果進行判斷

#### 實例說明：Keltner通道

假設要添加Keltner通道指標：

1. **計算邏輯**：中軌為收盤價的EMA、寬度為ATR（真實波幅）、上軌=中軌+N倍ATR、下軌=中軌-N倍ATR

2. **註冊**：在指標引擎的對應表中加入「KELTNER」項目

3. **使用**：策略可以檢查價格是否突破上軌或下軌

### API擴展：添加新分析端點

#### 概念說明
分析端點提供特定類型的統計分析結果，例如穩定性分析、收斂分析等。

#### 添加步驟

1. **設計分析邏輯**：決定要分析什麼資料、設計輸出格式

2. **實現分析函數**：從Optuna資料庫讀取試驗結果、進行統計計算、組織成結構化數據

3. **創建API端點**：定義URL路徑、實現請求處理邏輯、返回JSON格式結果

4. **前端整合**：呼叫新API、視覺化顯示結果

### 數據格式擴展

#### 在Trial中儲存額外數據

系統允許在每次試驗中儲存自訂數據：
- 使用Trial的user_attrs屬性
- 可儲存任何JSON可序列化的數據
- 例如：案例級別密度、月度統計等

#### 前端類型定義

當添加新的數據欄位時：
- 需要在TypeScript類型定義中加入
- 確保前後端數據格式一致
- 利用型別系統避免錯誤

### 測試建議

1. **單元測試**：測試單一函數的正確性、使用小範例數據驗證、確保邊界情況處理正確

2. **整合測試**：測試完整工作流程、使用真實但小規模的案例數據、驗證各模組協作正常

3. **性能測試**：確保新功能不拖慢優化速度、測試大量案例情況、監控內存使用

如果想貢獻代碼到主專案：

2. **創建分支**：為新功能創建feature分支
3. **開發與測試**：實現功能並添加測試
4. **提交Pull Request**：請求合併到主分支
5. **Code Review**：接受審查和修改建議
