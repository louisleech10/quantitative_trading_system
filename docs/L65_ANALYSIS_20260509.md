### 2.2 L6.5 內部拆解

#### Legacy 模式

```
[L6.5] Registry transform config:
  groups=124, workers=2, mode=replace
  use_fast=False, can_use_numba_fast=True
  winsor=True, rank=True, zscore=True
  fracdiff=True, adf=True, gaussian=True
  
任務分配: 122 full groups (fast=0, slow=122) + 2 slow_chunked
```

**所有 122 個 group 全走 slow path**，原因分析如下：

`_group_requires_slow_transform()` 判斷邏輯（per-group 路由，與全域 `use_fast` 無關）：

```python
# feature_preprocessor.py line 438
if bool(transform_context.get("do_adf", False)):
    return True  # ← 全域判斷！ADF 只要啟用，所有 group 都走 slow
# ...
if not bool(transform_context.get("do_fracdiff", False)):
    return False  # fracdiff 若不啟用則 fast
# 以下才有 per-layer fracdiff 過濾
```

Legacy 中 `do_adf=True`（全域）→ 函式第 2 行就返回 `True` → **所有 group 都走 slow，包含 L3 rolling groups（它們本來不需要 ADF）**。

> ⚠️ **潛在優化機會**：`do_adf` 目前是全域判斷，但 ADF 實際上只對 L1/L2 layers（需要 fracdiff 的 layer）有意義。若像 `do_fracdiff` 一樣加入 per-layer 過濾，L3 rolling groups 即使在 Legacy 模式下也能走 fast path，省去無謂的 slow path 路由開銷。

#### IC-First 模式

```
[L6.5] Registry transform config:
  groups=124, workers=2, mode=replace
  use_fast=False, can_use_numba_fast=True
  winsor=True, rank=False, zscore=False
  fracdiff=True, adf=False, gaussian=False   ← IC-First 停用 adf/rank/zscore/gaussian

任務分配: 122 full groups (fast=99, slow=23) + 2 slow_chunked
```

| 子階段 | 耗時 | 佔比 | 說明 |
|--------|------|------|------|
| Fast path (99 個 L3 rolling group) | ~41s | 11% | 419 cols/group，只做 winsorize |
| L1 slow groups (ADF/FracDiff) | ~35s | 9% | 23 個 L1 group |
| **L2 slow-chunked (WorldQuant + Momentum)** | **~305s** | **80%** | **瓶頸所在** |
| **IC-First L6.5 合計** | **381s** | 100% | SPEC 目標 ≤250s，**超標 52%** |

#### L2 Slow-Chunked 詳細拆解

| Group | 欄位數 | 佔用時間 | 原因 |
|-------|--------|---------|------|
| `12h_L2_WorldQuant` | 6,704 cols | ~210s | ADF/FracDiff 逐欄計算，split_threshold=2000 → 4 chunk |
| `12h_L2_Momentum` | ~2,585 cols | ~95s | ADF/FracDiff，2 chunk |

**結論：L6.5 時間 80% 被 L2 的兩個大 group (WorldQuant + Momentum) 的 ADF 計算消耗。**

## 五、最重要的異常：d_star Cache 永遠 0 命中

### 5.1 現象

兩次執行中，每個 group 的 d_star cache hit 均為 **0**：

```
[L6.5] symbol=ETHUSDT tf=12h d_star_cache_hit=0/122 path=.../d_star_ETHUSDT_12h_b1774b7788aa.json
[L6.5] symbol=ETHUSDT tf=12h d_star_cache_hit=0/695 path=.../d_star_ETHUSDT_12h_b1774b7788aa.json
[L6.5] symbol=ETHUSDT tf=12h d_star_cache_hit=0/1335 path=.../d_star_ETHUSDT_12h_b1774b7788aa.json
...
```

Legacy 執行完畢後，`d_star_ETHUSDT_12h_b1774b7788aa.json` 已存在（470 KB）。
IC-First 在 Legacy 之後執行，但仍全為 0 命中。

### 5.2 技術根因分析

**Cache 路徑構成**:
```python
# _d_star_cache.py
path = cache_dir / f"d_star_{symbol}_{timeframe}_{fracdiff_hash[:12]}.json"
```

兩次執行路徑相同（`b1774b7788aa`），代表 `fracdiff_hash` 相同。  
所以 cache **確實有被載入嘗試**，但 `_payload_matches()` 驗證失敗。

**`_payload_matches()` 驗證邏輯**（以下任一不符即清空 cache）：

| 驗證項目 | Legacy 值 | IC-First 值 | 是否匹配 |
|---------|----------|------------|---------|
| `cache_version` | `"v3"` | `"v3"` | ✅ |
| `fracdiff_hash` | `b1774b7788aa...` | 同上 | ✅ |
| `adf_engine_version` | 依 `get_fast_adf_enabled()` | 同上 | ⚠️ **需確認** |
| `symbol` | `ETHUSDT` | `ETHUSDT` | ✅ |
| `timeframe` | `12h` | `12h` | ✅ |
| `source_data_version` | `""` (attrs 為空) | `""` | ✅ |
| `row_count` | 1,696 | 1,696 | ✅ |
| `time_range` | `[start_ts, end_ts]` | `[start_ts, end_ts]` | ⚠️ **需確認** |
| `adf_threshold` | from config | from config | ✅ (假設) |
| `sample_size` | from config | from config | ✅ (假設) |

**最可能的失敗點（3 個候選）**：

1. **`adf_engine_version` 不一致**：`_adf_engine_version()` 回傳取決於 `get_fast_adf_enabled()`。如果兩次執行此值不同（例如 Legacy 是 `"statsmodels-v1"` 而 IC-First 是 `"fast_adf-v1"`），則 `_payload_matches()` 會在 `exact_fields` 檢查時失敗。

2. **`time_range` 格式不一致**：`_preprocessing_time_range()` 依賴 DataFrame index。如果 Legacy 傳入 `raw_data`（kline 時間戳 index）而 IC-First 傳入 `all_features`（int index），`time_range` 的數值型別可能不同導致比對失敗。

3. **同次執行內 cache 不跨 group 共用**：在 `_transform_parallel_registry()` 中，`_d_star_cache_shared=True` 只在「同一 call stack 的 group 間」共用。但 cache **flush_atomic() 寫入 JSON 是在整個 L6.5 結束時**，若下一個 group 是在不同 worker 執行，則讀到的仍是舊的（無此次計算值的）JSON。

### 5.3 d_star Cache 失效的影響

d_star cache 的目的是**跨 run 避免 ADF 重新計算**。ADF 是 L6.5 最耗時的操作：

| 情境 | L2_WorldQuant ADF 時間 | L2_Momentum ADF 時間 |
|------|----------------------|---------------------|
| **Cache Miss（現狀）** | ~210s | ~95s |
| **Cache Hit（理想）** | <1s | <1s |

**如果 d_star cache 正常命中，IC-First L6.5 時間理論上可從 381s → ~76s**（僅剩快速的 winsorize 和 FracDiff 計算，不需要 ADF 搜尋最佳 d）。

## 附錄 A：Legacy fast=0 根因分析——設計缺失確認

> **針對用戶問題**：「Legacy 模式下，能走 fast path 的 group 是否應該走 fast？答案是應該，但目前沒有。」

### A.1 `_group_requires_slow_transform()` 完整判斷邏輯

```python
def _group_requires_slow_transform(self, group, transform_context) -> bool:
    if self.mode != "replace":
        return True                                          # (1) mode 非 replace → slow
    if bool(transform_context.get("do_adf", False)):
        return True                                          # (2) ADF 啟用 → ALL groups slow（全域，設計缺失所在）
    if bool(transform_context.get("do_gaussian", False)):
        if transform_context.get("gaussian_apply_to", "all") != "all":
            return True                                      # (3) 非全域 gaussian → slow
    if not bool(transform_context.get("do_fracdiff", False)):
        return False                                         # (4) 不做 fracdiff → fast
    if "ALL" in self._fracdiff_apply_to_layers:
        return True                                          # (5) fracdiff 全 layer → slow
    source_layer = self._group_layer_name(group)            # (6) per-layer fracdiff 判斷
    if source_layer:
        return source_layer in self._fracdiff_apply_to_layers
    # ...
```

### A.2 Legacy vs IC-First 的關鍵差異

| 情境 | `do_adf` | 觸發規則 | 結果 |
|------|----------|---------|------|
| **Legacy** | `True`（全域啟用） | 規則 (2)：全域判斷，立刻 `return True` | 所有 122 groups → slow (**fast=0**) |
| **IC-First pre-IC** | `False`（`_layer6_5_pre_ic()` 明確停用） | 跳過規則 (2)，進入規則 (4/6) per-layer 判斷 | L3 groups（不做 fracdiff）→ fast (**fast=99**) |

> **IC-First 為何要 pre-IC 停用 ADF？**
> `_layer6_5_pre_ic()` 第 1622 行：
> ```python
> self._set_preprocessing_step_enabled(preprocessing_config, "adf_differencing", False)
> ```
> Pre-IC 只做 winsorize + fracdiff（用已 cache 的 d_star），不跑新的 ADF 測試。因此 `do_adf=False`，L3 groups 繞過規則 (2)，走 per-layer fracdiff 判斷，因 L3 不在 `fracdiff_apply_to_layers` 中，最終走 fast path。

### A.3 為何 Legacy fast=0 是設計缺失而非正確行為

**V1 SPEC 原始設計意圖**（`docs/L65_OPTIMIZATION_SPEC.md` line 248）：
> FracDiff 預設僅套用 L1/L2（level-like）；L3+ 多數為已轉換特徵，預期 d≈0 或低 ROI

ADF 是 FracDiff 的前置步驟（決定最優 d_star），兩者在概念上綁定在相同的 layer set。若 fracdiff 只套用 L1/L2，則 ADF 也只對 L1/L2 有意義，L3+ groups 不需要 ADF → 應走 fast path。

但目前 `_group_requires_slow_transform()` 規則 (2) 是**全域判斷**（先於 per-layer fracdiff 過濾），只要 `do_adf=True` 就讓所有 groups 走 slow，破壞了 V1 SPEC 設計。這個全域判斷可能是實作時的簡化，但其效果是 Legacy L3+ groups（不需 ADF）也被迫走 slow path。

**結論：Legacy fast=0 是設計缺失，不是正確行為。** IC-First 透過「pre-IC 停用 ADF」間接繞過這個問題，Legacy 則沒有對應的修復。

### A.4 修復方案（P1 等級，ADF per-layer 過濾）

```python
# 目前（全域，設計缺失）：
if bool(transform_context.get("do_adf", False)):
    return True

# 修復（per-layer，與 fracdiff 相同邏輯）：
if bool(transform_context.get("do_adf", False)):
    if "ALL" in self._fracdiff_apply_to_layers:
        return True
    source_layer = self._group_layer_name(group)
    if source_layer and source_layer in self._fracdiff_apply_to_layers:
        return True
    # 若此 group 的 layer 不需要 ADF → 繼續往下判斷（可走 fast path）
```

**工程影響**：
- 不需新增設定（直接復用 `_fracdiff_apply_to_layers`，ADF 套用範圍=fracdiff 套用範圍）
- L3 的 99 個 groups 在 Legacy 也能走 fast path
- **預估節省**：Legacy L6.5 從 1,193s → ~700-800s
- **優先順序**：P1（低於 fast_adf/ADF 並行化，但是恢復原始設計意圖的正確修復）

### 11.4 意外發現：Legacy New 整體比 IC-First 快 35s

**觀察**：Legacy New（更多 transforms：rank+zscore+gaussian+adf）L6.5 合計 344.5s，比 IC-First（更少 transforms：僅 fracdiff+winsorize）380.35s **快 35.8s**。

**各 phase 分解**：

| Phase | IC-First | Legacy New | 差異 | 原因 |
|-------|----------|------------|------|------|
| L3 fast groups（99個） | ~40s | ~73s | **+33s（慢）** | Numba 執行更多 ops（rank+zscore+gaussian） |
| L1/L2 slow full groups（23個） | ~35s | ~40s | **+5s（慢）** | ADF+rank+zscore+gaussian |
| **L2_WorldQuant slow-chunked** | **~208s** | **~155s** | **-53s（快！）** | 系統負載 / 記憶體狀態差異 |
| **L2_Momentum slow-chunked** | **~96s** | **~74s** | **-22s（快！）** | 同上 |
| **合計** | **380s** | **344.5s** | **-35.8s** | L2 節省 75s > L3+L1 額外 38s |

**分析**：
1. L3 fast groups：Legacy New 多了 rank+zscore+gaussian（Numba），預期比 IC-First 慢 → **實測 +33s，符合預期**。
2. L2 large groups（WorldQuant + Momentum）：Legacy New 比 IC-First **快 75s**，但 Legacy New 有 ADF+fracdiff+rank+zscore+gaussian，比 IC-First（只有 fracdiff）更多工作。
3. **最可能原因**：run-to-run 系統負載變異（兩次執行相差 2.5 小時，d_star_cache 全未命中在兩次 run 中都成立），以及每 chunk 的 d_star 計算量相同，但 CPU 調度和記憶體 page fault 在 legacy new 執行時較優。
4. **結論**：Legacy New 比 IC-First 快的現象屬於正常統計雜訊（35.8s 差距在 5-10% 範圍內），**不代表「多做 rank+zscore+gaussian 反而更快」**；兩者在相同硬體條件下應視為等效（±50s）。
