### 9.2 真實原因：browse_data_quality 端點與 warmup 共用 process

| 23:23:58 | warmup 開始（API task `e60ff01e...`）|
| 23:23:43 | **`browse_data_quality` 第 1 次掃描啟動**（早於 warmup 15s）|
| 23:24:55 | browse_data_quality 第 2 次掃描啟動 |
| 23:25:17 | browse_data_quality 第 3 次掃描啟動 |
| 23:27:22 | browse_data_quality 第 4、5 次掃描幾乎同時啟動 |
| 23:27:34 | browse_data_quality 第 6、7 次掃描幾乎同時啟動 |
| 23:29:25 | 第 1 次掃描完成（**342.1s**）|
| 23:33:53 | 第 2 次掃描完成（**538.0s**）|
| 23:35:16 | 第 3 次掃描完成（**599.4s**）|
| 23:38:42 | 第 4 次完成（**680.1s**）|
| 23:38:53 | 第 5、6 次完成（678.4s、691.0s）|
| 23:38:54 | 第 7 次完成（679.5s）|
| 23:41:28 | warmup 完成 |

**期間 7 次 browse_data_quality 平行掃描，每次掃描 442,079 features × 1,061 parquet（≈3,000s 累積 CPU 時間）**，與 CGSA warmup 共用單一 FastAPI process。Python GIL + parquet I/O 嚴重競爭，warmup 被拖慢約 +677s。

> **這 +677s 不是 warmup 本身的迴歸**——20260514 baseline run 是「手動觸發、不開 UI」的純後端跑批；20260521 是「手動觸發 + 同步開啟 Feature Explorer」的真實使用情境。**baseline 隱藏了 UI 流量成本**。
>
> **如果排除 UI 流量影響，warmup 純值可估算為**：總 1,050s 減去 browse_data_quality 7 次掃描在 warmup 期間消耗的 estimated CPU 時間（保守估 ~600s 真實競爭）→ warmup 純值 ≈ 450–500s，僅比 baseline +80–130s。這個增幅與 §4「features −2.6%、L6.5 sub-tasks −0.2%」的 group 索引重建成本（baseline → new 也曾 +90s）一致。

### 9.3 修復建議（已記錄在 RUN_COMPARISON_20260521.md §6 行動 #3）

`browse_data_quality` 加入 task-level cache，首次掃描完成後寫入 `data_cache/features/{task_id}/quality_dashboard.parquet`，後續 6 次呼叫直接命中（O(1)）。預期：
- warmup 期間 UI 流量歸零 → warmup 純值降至 450s 附近
- 前端 quality tab 從 562–724s → <100ms

### 12.2 問題 A：`large_trade_ratio` 全 NaN（117,052 筆 ≈ 95% 的問題特徵）

**根因鏈**：

```
資料源 trades 缺失（22:42:37 microstructure_indicators WARNING: trades missing）
   ↓
L1: ms_12h_large_trade_ratio_13 / _21 / _55 三欄全 NaN
   ↓
L2 Momentum: 每欄 × N lag → ~30 NaN cols
L2 Cross:    每對 × cross ops → ~40 NaN cols
L2 Ratio:    pattern guard 已擋（不再產生）
L2 Distance / SignedStrength: ~50 NaN cols
   ↓
L3 rolling: 對上面所有 NaN col × 10 window × 10 aggregator → ~120,000 NaN cols
   ↓
L4 lag: 對 L1+L2+L3 全部 lag → 117,052 個 100% NaN 欄位
```

**性質**：**100% bug**——根源是 trades 資料源沒抓到（不是真實的「市場上沒有大單交易」），下游所有衍生欄位的 NaN 都是 propagation 造成。

### 12.3 問題 B：MIDPOINT_89/144 + 小窗 Skew/Kurt + HT-TRENDMODE rolling 統計（5,240 筆）

Top 5 mid-hole 範例：
| Rank | 特徵名 | 比例 |
|---|---|---|
| 1 | `taker-ratio_1h_trend_MIDPOINT_89_Skew_W3` | 89.23% |
| 2 | `taker-ratio_1h_trend_MIDPOINT_144_Kurt_W5` | 87.53% |
| 3 | `taker-ratio_1h_trend_MIDPOINT_144_Skew_W5` | 87.53% |
| 4 | `volume_1h_cycle_HT-TRENDMODE_Kurt_W8` | 85.85% |
| 5 | `volume_1h_cycle_HT-TRENDMODE_Skew_W8` | 85.85% |

**根因（三個獨立小問題）**：
1. **MIDPOINT_89/144 warmup = 89 / 144 bars** → 前段全 NaN 是**設計上必然**，但前端把這段「head warmup」誤分類成「mid-hole」（這是 UI 顯示 bug，不是計算 bug）。
2. **Skew_W3 / Kurt_W5 視窗過小** → 3–5 點算 skew/kurt 統計上意義不大；當視窗內 std=0 或樣本過少時 → NaN/inf 邊界值（這是**配置 bug**：不應該對所有指標都跑全部 window×aggregator 笛卡爾積）。
3. **HT-TRENDMODE 是離散指標（0/1 輸出）** → 對其做 rolling Skew/Kurt 數學上沒意義（值域只有兩種，std 經常 = 0 → 除零產生 NaN）（這是**語義 mismatch**：cycle 類別內混入了不該做統計算子的離散指標）。

**性質**：**3 種小 bug 混合**，與 trades-missing 問題互相獨立。

### 12.4 問題 C：尾端缺失 724 筆（< 0.6% of 問題總數）

未做 Top 20 級分析，量小、影響有限。**性質推測**：rolling lookback 在資料尾端 N bars 內不足 → 末尾 NaN。這是**設計上必然**，但前端應與 head warmup 一視同仁標示，而不是算成獨立問題。

### 12.5 總結：123,016 筆問題特徵的真實組成

| 類別 | 數量 | 占比 | bug 性質 |
|---|---|---|---|
| 高 NaN（large_trade_ratio 家族） | **117,052** | **95.2%** | **資料源 bug** + 應在 L1 fail-fast skip |
| 中間孔洞（MIDPOINT/HT-TRENDMODE）| 5,240 | 4.3% | UI 顯示 bug + 配置 bug + 語義 mismatch |

## 14. 回答 Q2：「修復前 Feature Explorer 反而比較快」的可能原因

> 用戶觀察：「在做 NaN 優化前，feature explorer 的每一項都快很多，就算是第一次跑也是快很多，而且也都是開 UI 手動跑。」

這個觀察與本次 log 的 562–724s/scan 形成強對比，需要嚴格區分**至少 4 個可能根因**：

### H1：修復前 pipeline fail-closed，L7_raw 根本沒寫完（最可能）

修復前的「NaN poisoning」常導致 L2 ratio 算子在某些 group 觸發 `inf>0` 或 `coverage<threshold` → fail-closed，整個 batch 半途中止。
- L7_raw 只持久化部分 group（可能僅幾百個 parquet，而不是 1,061）
- 總欄位可能只有 ~150k 而非 442k
- Feature Explorer 掃描成本 = O(features × parquet_count) **同時下降兩個維度** → 自然快很多

**驗證方法**：
```bash
# 找一個修復前的 task_id
ls -la data_cache/features/<old_task_id>/L7_raw/ | wc -l
# 預期：明顯少於 1,061
```

### H2：修復前 large_trade_ratio 整欄被 feature_validator 自動丟掉

修復前 `feature_validator` 可能對 100% NaN 欄位有自動 drop（之前的 raw fail-closed gate 或 dead-column filter）。
- 117,052 個 large_trade_ratio 家族欄位在持久化前就被刪
- L7_raw 實際只有 ~325k 欄位
- data-quality 端點掃 325k × 1,061 ≈ 比 442k × 1,061 快 26%（但這只能解釋部分加速，不足以解釋「快很多」）

**驗證方法**：
```bash
# 對修復前 task 直接讀 L7_raw 列出欄位
ls data_cache/features/<old_task_id>/L7_raw/*.parquet | head -5
# 用 pyarrow 讀 schema，看是否含 ms_*_large_trade_ratio_*
```

### H3：Feature Explorer 端點程式碼變更（中度可能）

`browse_data_quality` 端點的實作可能在某個 PR 內從「parquet metadata-only」改成「partial DataFrame load」，例如為了支援「中間孔洞偵測」必須讀實際 row 才能知道 NaN 是 head warmup 還是中段，metadata-only 不夠。
- 這會讓掃描成本從 O(metadata) → O(rows × cols) 跳一個量級

**驗證方法**：
```bash
git log --since="2026-04-25" --oneline -- api/services/feature_factory_service.py api/routes/feature_browser.py
# 找跟 browse_data_quality / mid-hole / null_count 有關的 commit
```

### H4：修復前看的是不同（較小）的 task（次要可能）

如果你修復前 UI 上停留的是某個 BTC-only 或 1h-only 的 task，feature count 自然小很多。

**驗證方法**：看修復前的 task list 紀錄、比較欄位數。

### 推薦驗證順序

1. **先做 H1 驗證**（最快，1 行 ls 即可）→ 如果舊 task L7_raw 確實只有幾百個 parquet，H1 直接確認
2. **再做 H3**（git log 抓 commit 差異）
3. **最後 H2/H4**（需要實際讀資料對比）

### 與「pattern guard 變更」的真實關係

Pattern guard 本身**不會**讓 Feature Explorer 變慢——它降欄位數（−2.6%）、降磁碟（−2.6%）、降 disk I/O。所以「修復後變慢」**不可能是 pattern guard 直接造成**。最可能是 **H1（pipeline 第一次真正跑完）** 或 **H3（顯示邏輯升級為需要讀 row）**。

## 15. 回答 Q3：如何分辨「真實 NaN」vs「計算 bug 造成的 NaN」

123,016 筆問題特徵裡，**計算 bug** vs **真實 NaN** 的判定流程：

### 15.1 判定決策樹

```
某欄位 X 的 NaN 比例異常高
  │
  ├── Step 1：往上游追到 L1 atomic（看根來源）
  │     │
  │     ├── L1 原始欄位本身就 ≥ 95% NaN
  │     │     │
  │     │     ├── 對應 atomic engine 有 WARNING (e.g. "trades missing")
  │     │     │   → 【BUG: 資料源缺失】(e.g. large_trade_ratio 117k 全部歸此類)
  │     │     │
  │     │     └── atomic engine 無 WARNING，但市場本身就稀疏
  │     │         → 【真實 NaN: 該標的低流動性】(罕見)
  │     │
  │     └── L1 原始欄位 NaN < 5%，但下游欄位 NaN 高
  │           │
  │           ├── Step 2：檢查 NaN 在時間軸上的分布
  │           │     │
  │           │     ├── 連續前綴 NaN（前 N bars，後段乾淨）
  │           │     │     │
  │           │     │     ├── N == 指標 warmup（e.g. MIDPOINT_144 → N=144）
  │           │     │     │   → 【設計必然: warmup】(不該算 mid-hole)
  │           │     │     │
  │           │     │     └── N >> 預期 warmup
  │           │     │         → 【BUG: 算子實作問題】
  │           │     │
  │           │     ├── 連續後綴 NaN（前段乾淨，後 M bars NaN）
  │           │     │     → 【設計必然: rolling 末端 lookback 不足】(尾缺)
  │           │     │
  │           │     ├── 中段塊狀 NaN（前後乾淨，中間連續 NaN）
  │           │     │   → 通常是【BUG: 上游某段資料缺失，沒做 forward-fill】
  │           │     │
  │           │     ├── 隨機散布 NaN
  │           │     │   → 通常是【BUG: 除零 / log(負數) / inf-NaN 轉換】
  │           │     │
  │           │     └── 100% NaN（整欄沒一個有效值）
  │           │         → 【嚴重 BUG: 整條 pipeline 路徑炸了】
  │           │
  │           └── Step 3：跨 symbol 驗證
  │                 │
  │                 ├── 所有 symbol 都同樣高 NaN
  │                 │   → 【系統性 BUG（算子/配置問題）】
  │                 │
  │                 └── 只有部分 symbol 高 NaN
  │                     → 【資料源 BUG（該 symbol 抓取失敗）】或
  │                       【真實 NaN（該 symbol 該時段確實沒交易）】
```

### 15.2 對 20260521 123,016 筆的判定結果套用

| 子類 | 數量 | 判定路徑 | 結論 |
|---|---|---|---|
| `ms_*_large_trade_ratio_*` 家族 | 117,052 | Step 1 → L1 有 WARNING `trades missing` | **BUG（資料源）** |
| `*_MIDPOINT_89/144_Skew/Kurt_W3/W5` | ~2,000 | Step 1 → L1 乾淨 → Step 2 → 前綴 NaN = warmup | **設計必然 + UI 顯示 bug** |
| `volume_*_HT-TRENDMODE_Skew/Kurt_W*` | ~3,000 | Step 1 → L1 乾淨 → Step 2 → 散布 NaN（除零）| **BUG（語義 mismatch）** |
| 「尾端缺失」724 筆 | 724 | Step 2 → 後綴 NaN | **設計必然** |

**最終結論**：123,016 筆裡，估計 **117,052 + 3,000 ≈ 120,052（97.6%）是真正的 bug**，**剩 ~2,964（2.4%）是設計必然 + UI 顯示分類錯誤**。

### 15.3 實務操作步驟（可直接照做）

對任何「可疑高 NaN」欄位，**3 行命令確認真偽**：

```python
# Step 1: 看 L1 原始欄位
import pyarrow.parquet as pq
pq.read_table(f"data_cache/features/{task_id}/L1/{symbol}_{tf}_L1.parquet",
              columns=[suspect_col]).to_pandas().isna().mean()
# 結果 = 1.0 → 資料源 bug
# 結果 < 0.1 → 往下游追

# Step 2: 看 NaN 時間分布
df = pq.read_table(f"data_cache/features/{task_id}/L7_raw/{group}.parquet",
                   columns=[suspect_col]).to_pandas()
first_valid = df[suspect_col].first_valid_index()
last_valid  = df[suspect_col].last_valid_index()
print(f"first_valid={first_valid}, last_valid={last_valid}, len={len(df)}")
# first_valid 接近 0 + last_valid 接近 len → 中段散布 NaN（bug）
# first_valid 較大 + last_valid 接近 len → head warmup（設計）
# first_valid 接近 0 + last_valid 較小 → tail（設計）

# Step 3: 跨 symbol 比對
for sym in ["BTCUSDT", "ETHUSDT", "SOLUSDT"]:
    df = pq.read_table(f".../L1/{sym}_1h_L1.parquet",
                       columns=[suspect_col_L1]).to_pandas()
    print(f"{sym}: NaN ratio = {df[suspect_col_L1].isna().mean():.2%}")
# 全部 100% → 系統性 bug
# 只有部分 100% → 資料源 bug 或真實 NaN
```

```json
  "category": "BUG",

  "suggested_action": "Skip at L1 (fail-fast)"

```
