## 核心設計原則

### First Principles分析

**根本需求**：使用者需要視覺化查看案例的K線圖，以判斷案例質量，並使用統一格式的數據訓練機器學習模型。

**核心矛盾**：
- 視覺化需求：靈活性（任意timeframe、任意範圍）
- ML訓練需求：一致性（固定timeframe、固定範圍）

**設計決策**：採用**雙模式架構**，分離兩種需求但共享底層數據。

## 系統架構層次

### 三層架構設計

```
┌─────────────────────────────────────────┐
│          應用層（Application）           │
│  ┌──────────────┐    ┌──────────────┐  │
│  │  視覺化模式  │    │  ML訓練模式  │  │
│  │  (靈活查看)  │    │  (標準特徵)  │  │
│  └──────────────┘    └──────────────┘  │
├─────────────────────────────────────────┤
│         服務層（Service）                │
│  ┌──────────────┐    ┌──────────────┐  │
│  │  圖表服務    │    │  特徵工程    │  │
│  │  動態裁切    │    │  統一提取    │  │
│  └──────────────┘    └──────────────┘  │
├─────────────────────────────────────────┤
│         數據層（Data）                   │
│  ┌─────────────────────────────────┐   │
│  │  HDF5多timeframe存儲           │   │
│  │  統一的K線數據格式              │   │
│  └─────────────────────────────────┘   │
└─────────────────────────────────────────┘
```

**設計理由**：
1. **分層解耦**：視覺化和ML使用不同服務，互不影響
2. **數據復用**：同一份HDF5數據支持兩種模式
3. **易於擴展**：新增功能只需添加新服務層

## 雙模式架構詳解

### 模式1：探索模式（Exploration Mode）

**目的**：使用者視覺化分析案例

**特點**：
- 使用者可自由選擇timeframe（1h/4h/1d等）
- 使用者可調整顯示範圍（往前X根、往後Y根）
- 圖表以案例時間點T為中心
- 支援拖曳、縮放等互動操作

**數據流**：
```
使用者選擇案例
  ↓
指定顯示參數（timeframe、範圍）
  ↓
圖表服務從HDF5動態讀取
  ↓
渲染圖表（以T為中心）
```

**關鍵設計**：
- 最大顯示根數限制：避免性能問題
- 按需加載：虛擬滾動技術
- 數據缺失處理：即時下載或提示

### 模式2：訓練模式（Training Mode）

**目的**：為機器學習提供標準化特徵

**特點**：
- 固定特徵timeframe（如1h）
- 固定時間窗口（如T-72根到T+24根）
- 統一的特徵維度
- 可處理多種原始timeframe的案例

**數據流**：
```
讀取案例列表（可能多種timeframe）
  ↓
全部轉換到統一的特徵timeframe
  ↓
按固定窗口提取數據
  ↓
計算特徵向量
  ↓
生成標準化Feature Matrix
```

**關鍵設計**：
- Timeframe轉換邏輯：確保時間對齊
- 固定窗口保證：所有案例相同維度
- 批量處理優化：提升效率

## 數據存儲架構

### HDF5多層級結構

**設計原則**：
- 按symbol分組
- 按timeframe分層
- 元數據獨立存儲

**結構示意**：
```
kline_cache.h5
├── ETHUSDT/
│   ├── 1h/
│   │   ├── data (實際K線數據)
│   │   └── metadata (時間範圍、更新時間)
│   ├── 4h/
│   ├── 12h/
│   └── 1d/
├── BTCUSDT/
│   └── (同上結構)
└── cache_metadata/
    └── index (快速查詢索引)
```

**資料欄位**（每根K線）：
- timestamp (Unix時間戳)
- open, high, low, close (價格)
- volume (成交量)
- taker_buy_volume (主動買入量)
- taker_ratio (主動買入比例，計算得出)
- quote_volume (計價貨幣成交量)

**設計理由**：
1. **多timeframe支援**：視覺化和ML可選用不同粒度
2. **增量更新**：只下載缺失的時間段
3. **快速讀取**：HDF5原生支援切片操作
4. **數據完整性**：元數據記錄確保可追溯

## 關鍵功能設計

### 1. 案例時間點標記

**需求**：圖表上明確標示案例發生的時間點T

**實現方式**：
- 垂直虛線穿過所有圖表
- 紅色箭頭或標籤標示
- 懸停顯示"案例時間點"

**技術考量**：
- Lightweight Charts的Marker API
- 或使用VerticalLine Series
- 跨圖表同步標記位置

### 2. 策略信號標記

**需求**：在ML窗口範圍內標示符合策略的K線

**核心邏輯**：
```
使用者選擇策略（如EMA5 > EMA20）
  ↓
系統計算T-72到T範圍內的指標
  ↓
判斷每根K線是否符合策略
  ↓
符合的K線顯示箭頭標記
```

**計算範圍限制**：
- 只在ML窗口內計算（如T-72到T）
- 不計算T之後的數據（避免未來函數）
- 提升性能且符合邏輯

**視覺化設計**：
- Price圖：綠色向上箭頭（買入信號）
- Volume圖：同步顯示對應位置箭頭
- Taker_Ratio圖：同步標記

**技術考量**：
- 策略定義格式標準化
- 指標計算引擎可擴展
- 批量計算優化性能

### 3. 動態圖表互動

**需求**：使用者可拖曳、縮放圖表，以T為中心查看

**實現方式**：
- 初始載入：以T為中心，顯示預設範圍
- 拖曳：左右移動時間軸，按需加載數據
- 縮放：調整時間粒度或範圍
- 重置：雙擊回到T點居中

**性能優化**：
- 虛擬滾動：只渲染可見範圍
- 分批加載：接近邊界時動態加載
- 最大限制：避免一次載入過多數據

### 4. ML參數可配置

**需求**：使用者可調整ML訓練的數據範圍

**配置項**：
- 特徵timeframe（如1h）
- 往前根數（如72根）
- 往後根數（如24根）

**預設值設計**：
- 1h timeframe + 72根前 + 24根後
- 基於統計學和ML最佳實踐
- 使用者可根據需求調整

**驗證邏輯**：
- 最小值限制（如往前至少20根）
- 最大值限制（避免內存問題）
- 合理性檢查（往前應大於往後）

## API架構設計

### 端點分類

**圖表相關（視覺化模式）**：
- `GET /api/v1/chart/data` - 獲取圖表數據
- `POST /api/v1/chart/signals` - 計算策略信號
- `GET /api/v1/chart/timeframes` - 查詢可用timeframe

**ML相關（訓練模式）**：
- `POST /api/v1/ml/extract-features` - 批量特徵提取
- `GET /api/v1/ml/config` - 查詢ML配置
- `POST /api/v1/ml/config` - 更新ML配置

**數據管理**：
- `POST /api/v1/data/download` - 批量下載K線
- `GET /api/v1/data/status` - 查詢下載進度
- `POST /api/v1/data/import` - 導入案例CSV

### 統一響應格式

**成功響應**：
```
{
  "success": true,
  "data": {...},
  "metadata": {
    "request_id": "...",
    "timestamp": "..."
  }
}
```

**錯誤響應**：
```
{
  "success": false,
  "error": {
    "code": "DATA_NOT_FOUND",
    "message": "K線數據不存在",
    "details": {...}
  }
}
```

## 跨市場擴展設計

### 抽象數據提供者

**設計原則**：
- 定義統一的數據介面
- 不同市場實作各自的Provider
- 上層服務無感知市場差異

**市場差異處理**：
- 交易時間：加密貨幣24/7，股票有開盤時間
- Timeframe支援：不同市場支援不同粒度
- 數據欄位：統一映射到標準格式

**已規劃市場**：
- 加密貨幣（幣安、OKX）
- 台灣股市（證交所API）
- 美國股市（IBKR、yfinance）
- 期貨市場（待規劃）

**關鍵設計**：
- 配置檔定義市場參數
- Provider工廠模式選擇實作
- 統一的數據Schema保證互通

## 性能與可擴展性

### 性能考量

**預期規模**：
- 案例數量：100-10,000個
- 每案例K線：96根（1h, 72+24）
- 總數據量：< 100MB（可接受）

**優化策略**：
- HDF5壓縮存儲
- 分批讀取和處理
- 前端虛擬滾動
- 圖表渲染優化（60fps目標）

### 可擴展性設計

**水平擴展**：
- 數據下載可並行（多worker）
- 特徵計算可分散（按symbol分組）
- API無狀態設計（可多實例）

**垂直擴展**：
- MacBook M1充分利用8核心
- HDF5支援大文件（GB級別）
- 內存管理得當（分批加載）

## 系統限制與邊界

### 已知限制

1. **數據量限制**：單次圖表顯示最多500根K線
2. **並行限制**：最多8個worker（M1核心數）
3. **API限制**：幣安有速率限制，需控制請求頻率
4. **內存限制**：16GB/32GB，大批量需分批處理

### 錯誤處理策略

**數據缺失**：
- 提示使用者數據不存在
- 提供下載或重試選項
- 不影響其他案例處理

**API失敗**：
- 智能重試機制（3次）
- 錯誤分類和記錄
- 失敗案例單獨追蹤

**計算錯誤**：
- 指標計算異常跳過該案例
- 記錄錯誤原因
- 不中斷整體流程

## 總結

本架構設計基於First Principles思考，核心解決了**視覺化靈活性**與**ML訓練一致性**的矛盾，通過**雙模式架構**實現兩者兼顧。

**關鍵優勢**：
1. 清晰的分層設計，易於理解和維護
2. 數據層復用，避免重複存儲
3. 模組化設計，功能獨立可擴展
4. 跨市場支援，未來可輕鬆擴展
5. 性能與可擴展性平衡良好

**設計原則總結**：
- ✅ 分離關注點（視覺化 vs ML）
- ✅ 數據驅動（真實API數據）
- ✅ 可配置性（使用者可調整）
- ✅ 可擴展性（新市場、新功能）
- ✅ 可維護性（清晰的架構層次）
