## 設計目標

### First Principles分析

**根本問題**：機器學習模型需要什麼樣的輸入數據？

**核心需求**：
1. **一致性**：所有案例必須具有相同的特徵維度
2. **時間對齊**：不同timeframe的案例需要統一標準
3. **無未來資訊**：只使用案例時間點T之前的數據
4. **足夠資訊**：包含預測所需的所有關鍵特徵

**設計挑戰**：
- 使用者上傳的案例可能來自不同timeframe（1h、4h、12h、1d）
- 如何將不同timeframe的案例轉換為統一格式？
- 如何確保特徵提取不洩漏未來資訊？

**解決方案**：
- 定義統一的特徵timeframe（如1h）
- 固定的時間窗口（如T-72根到T+24根）
- 標準化的特徵提取流程

## 核心設計原則

### 1. 統一特徵Timeframe

**設計決策**：所有案例統一轉換到1h timeframe提取特徵

**理由**：
- 1h解析度足夠細緻，捕捉短期波動
- 覆蓋3天歷史（72根），包含高價值特徵窗口
- 訓練樣本量最大化（同樣時間，1h樣本是4h的4倍）
- 適合預測12小時漲跌（短期預測）

**可配置性**：
- 使用者可調整為4h或其他timeframe
- 但一次訓練必須使用統一timeframe
- 預設值：1h（基於統計學分析）

### 2. 固定時間窗口

**標準配置**：
- 往前：72根（T-72到T-1）
- 往後：24根（T到T+23）
- 總共：96根K線數據

**時間覆蓋**（1h timeframe）：
- 往前：72小時 = 3天
- 往後：24小時 = 1天
- 總計：4天

**設計理由**：
- 3天歷史：統計學上的有效信息窗口
- 1天未來：足夠觀察12小時預測結果
- 72根：足夠計算MA50等中期指標
- 24根：足夠計算未來漲跌幅和回撤

### 3. 無未來函數保證

**嚴格規則**：
- 特徵計算只使用 TO-1 之前的數據
- TO 點（Time Open，開單時間）及之後的數據仅用於計算標籤（Label）
- 訓練時模型看不到未來資訊

**時間分界點**：
```
T-72  ........  T-1  |  TO  ........  TO+23
[   特徵數據範圍   ] | [   標籤計算範圍   ]
     (Features)      |      (Labels)
                     ^
                  開單時間（TO）
                  在此決策是否進場
                  只能看到 TO-1 之前
```

**TO (Time Open) 定義**：
- TO = K 線的開盤時間
- 12h TO 和 1h TO 的 OPEN 時間相同
- 在 TO 開盤時決策是否進場
- TO 當根 K 線的 OHLCV 都看不到（屬於未來數據）

## Feature Matrix結構

### 整體結構

**維度**：`[N_cases, N_features]`

- N_cases：案例數量（如1000個）
- N_features：特徵數量（如200-500個）

### 特徵分類

**1. 原始K線特徵（每根K線5個）**：
- open, high, low, close, volume
- 時間序列：T-72到T-1共72根
- 特徵數：72 × 5 = 360個

**2. 衍生特徵**：
- 價格變化率（returns）
- 成交量變化
- 波動率
- 趨勢指標
- 預估：50-100個

**3. 技術指標特徵**：
- EMA（5, 20, 50）
- RSI（14）
- MACD相關
- 預估：30-50個

**4. 籌碼特徵**：
- taker_ratio（每根K線）
- taker_ratio移動平均
- 預估：20-30個

**5. 時序特徵**：
- 時間（hour, day_of_week）
- 市場階段（bull/bear/sideways）
- 預估：5-10個

**總特徵數預估**：200-500個

### 特徵命名規範

**格式**：`{feature_name}_{time_offset}`

**範例**：
- `close_t-1`：TO-1時刻的收盤價（最新可見）
- `close_t-2`：TO-2時刻的收盤價
- `volume_t-10`：TO-10時刻的成交量
- `rsi14_t-1`：TO-1時刻的RSI(14)
- `ema20_t-5`：TO-5時刻的EMA(20)

**設計理由**：
- 清楚標示時間位置
- 避免混淆當前值與歷史值
- 方便追蹤特徵來源
- **TO 當根 K 線看不到，所以沒有 t0，最新是 t-1**

## Timeframe轉換邏輯

### 問題場景

**情境**：
- 案例A：ETHUSDT, 2025-06-02 12:00, 4h timeframe
- 案例B：BTCUSDT, 2025-06-03 08:00, 1h timeframe
- 需要：轉換為統一的1h timeframe特徵

### 轉換策略

**案例A（4h → 1h）**：

```
原始案例時間點：2025-06-02 12:00 (4h)
  ↓
找到最接近的1h時間點：2025-06-02 12:00 (1h)
  ↓
提取1h數據：T-72根到T+23根
  ↓
計算特徵
```

**案例B（1h → 1h）**：

```
原始案例時間點：2025-06-03 08:00 (1h)
  ↓
直接使用：2025-06-03 08:00 (1h)
  ↓
提取1h數據：T-72根到T+23根
  ↓
計算特徵
```

### 時間對齊規則

**對齊邏輯**：
- 4h時間戳（如12:00）可直接對應1h（12:00）
- 如果無法精確對應，取最接近的1h時間戳
- 確保對齊後的時間點有實際K線數據

**範例**：
- 4h: 00:00, 04:00, 08:00, 12:00, 16:00, 20:00
- 1h: 00:00, 01:00, 02:00, ..., 23:00
- 對齊：4h的12:00 → 1h的12:00 ✅

### 數據完整性檢查

**必須驗證**：
1. 對齊後的時間點是否有K線數據
2. T-72到T+23範圍內數據是否完整
3. 是否有缺失值或異常值

**處理策略**：
- 數據完整：正常提取特徵
- 數據缺失：跳過該案例並記錄
- 數據異常：標記但保留（可能是真實事件）

## 標籤（Label）計算

### 標籤定義

**預測目標**：案例時間點T後12小時是否上漲

**標籤值**：
- 1：Positive（會漲）
- 0：Negative（不會漲）

### 計算邏輯

**方法1：固定時間窗口**：
```
計算T到T+12小時內的最高價
漲幅 = (最高價 - T點收盤價) / T點收盤價
如果漲幅 >= 閾值（如3%）→ Label = 1
否則 → Label = 0
```

**方法2：使用CSV標籤**：
```
直接使用CSV中的Positive_case欄位
1 → Label = 1
0 → Label = 0
```

**推薦**：使用CSV標籤（使用者已標記）

### 標籤驗證

**檢查項**：
- 標籤值只能是0或1
- 正負樣本比例是否合理（不要過度失衡）
- 標籤與實際價格變化是否一致（抽樣驗證）

**平衡策略**（如果需要）：
- 過採樣少數類
- 欠採樣多數類
- 使用類別權重

## 配置系統設計

### ML配置檔結構

**檔案位置**：`config/ml_config.yaml`

**配置項**：

```yaml
ml_training:
  # 特徵提取配置
  feature_extraction:
    timeframe: "1h"           # 統一特徵timeframe
    bars_before: 72           # 往前根數
    bars_after: 24            # 往後根數
    
  # 特徵選擇
  features:
    use_raw_kline: true       # 是否使用原始OHLCV
    use_indicators: true      # 是否計算技術指標
    use_taker_ratio: true     # 是否使用籌碼特徵
    
    indicators:               # 要計算的指標
      - "EMA5"
      - "EMA20"
      - "EMA50"
      - "RSI14"
      - "MACD"
      - "ATR14"
  
  # 標籤配置
  label:
    source: "csv"             # csv或calculated
    threshold: 0.03           # 漲幅閾值（3%）
    time_window: 12           # 觀察窗口（小時）
  
  # 數據預處理
  preprocessing:
    normalize: true           # 是否標準化
    handle_missing: "drop"    # 缺失值處理：drop或fill
    remove_outliers: false    # 是否移除異常值
  
  # 訓練配置
  training:
    test_size: 0.2            # 測試集比例
    validation_size: 0.1      # 驗證集比例
    random_state: 42          # 隨機種子
    stratify: true            # 是否分層抽樣
```

### 使用者可調參數

**前端UI提供的配置**：
- Timeframe選擇（1h/4h/12h/1d）
- 往前根數（20-500）
- 往後根數（10-100）
- 指標選擇（勾選框）

**預設值設定**：
- Timeframe: 1h
- 往前: 72根
- 往後: 24根
- 指標: EMA5, EMA20, RSI14

**驗證規則**：
- 往前根數 >= 20（最少需要）
- 往前根數 >= 最長指標週期（如MA50需要>=50根）
- 往後根數 >= 預測時間窗口（如12小時需要>=12根）

## 特徵工程流程

### 整體流程

```
1. 讀取案例CSV
   ↓
2. 批量下載K線數據（如缺失）
   ↓
3. Timeframe轉換與時間對齊
   ↓
4. 提取固定窗口數據（T-72到T+23）
   ↓
5. 計算技術指標
   ↓
6. 生成特徵向量
   ↓
7. 計算標籤
   ↓
8. 標準化處理
   ↓
9. 組裝Feature Matrix
   ↓
10. 分割訓練/驗證/測試集
```

### 批量處理策略

**分批原因**：
- 記憶體限制（MacBook M1: 16GB/32GB）
- 避免一次處理過多案例

**分批大小**：
- 建議：100-500個案例一批
- 視可用記憶體動態調整

**並行處理**：
- 特徵計算可並行（按symbol分組）
- 充分利用M1的8核心
- 每個worker處理不同symbol

## 數據品質控制

### 特徵有效性檢查

**檢查項**：
1. 是否有NaN（缺失值）
2. 是否有Inf（無窮大）
3. 特徵方差是否過小（常數特徵）
4. 特徵分佈是否合理

**處理策略**：
- NaN：填補（前向填充）或刪除該案例
- Inf：標記並檢查計算邏輯錯誤
- 常數特徵：移除（對模型無用）
- 異常分佈：記錄但保留

### 標籤一致性檢查

**檢查項**：
1. 標籤是否只有0和1
2. 正負樣本比例（建議30%-70%範圍）
3. 標籤與價格變化是否對應

**不平衡處理**：
- 如果正負比例嚴重失衡（如90:10）
- 使用SMOTE過採樣或類別權重
- 或調整採樣策略

## Feature Matrix輸出格式

### 檔案格式

**格式選擇**：HDF5或Parquet

**推薦**：HDF5
- 與K線數據存儲一致
- 支援大數據快速讀取
- 可壓縮節省空間

### 輸出結構

**HDF5結構**：
```
ml_features.h5
├── features/
│   └── data              # Feature Matrix (N x M)
├── labels/
│   └── data              # Labels (N x 1)
├── metadata/
│   ├── feature_names     # 特徵名稱列表
│   ├── case_ids          # 案例ID列表
│   └── config            # 提取配置
└── splits/
    ├── train_indices     # 訓練集索引
    ├── val_indices       # 驗證集索引
    └── test_indices      # 測試集索引
```

### Metadata內容

**必須記錄**：
- 特徵提取時間
- 使用的配置參數
- 案例來源（CSV路徑）
- 數據版本號
- 特徵數量和案例數量

**用途**：
- 可重現性：確保可以重複生成相同特徵
- 可追溯性：了解特徵來源
- 版本管理：追蹤數據迭代

## 特徵標準化

### 標準化方法

**StandardScaler（推薦）**：
```
標準化公式：
z = (x - μ) / σ

其中：
- x：原始特徵值
- μ：訓練集均值
- σ：訓練集標準差
```

**使用訓練集統計量**：
- 計算訓練集的μ和σ
- 訓練集、驗證集、測試集都使用相同的μ和σ
- 避免數據洩漏

**不標準化的特徵**：
- 類別特徵（如hour, day_of_week）
- 已是比例的特徵（如taker_ratio: 0-1）

### 標準化流程

```
1. 分割數據集（train/val/test）
   ↓
2. 在訓練集上計算μ和σ
   ↓
3. 使用訓練集的μ和σ標準化訓練集
   ↓
4. 使用相同的μ和σ標準化驗證集和測試集
   ↓
5. 保存μ和σ供預測時使用
```

## 數據分割策略

### 分割比例

**標準配置**：
- 訓練集：70%
- 驗證集：10%
- 測試集：20%

**分層抽樣**：
- 根據標籤分層（保持正負比例）
- 確保各集合標籤分佈一致

### 時間序列注意事項

**隨機分割 vs 時間分割**：

**隨機分割**（推薦）：
- 案例來自不同時間和symbol
- 隨機分割合理
- 測試泛化能力

**時間分割**（可選）：
- 如果要測試時間外推能力
- 按時間排序後分割
- 訓練集：早期數據
- 測試集：近期數據

**本系統採用**：隨機分層抽樣

**端點**：`POST /api/v1/ml/extract-features`

**請求參數**：
```
{
  "case_file": "path/to/cases.csv",

    "timeframe": "1h",

```

**響應**：
```
{
  "success": true,
  "data": {
    "feature_file": "path/to/ml_features.h5",

  }
}
```

**端點**：`GET /api/v1/ml/features/{feature_id}`

**用途**：載入已生成的Feature Matrix供訓練使用

## 錯誤處理

### 常見錯誤

**數據不足**：
- 案例時間範圍內K線數據不完整
- 處理：跳過該案例，記錄警告

**指標計算失敗**：
- 數據不足以計算指標（如MA50需要50根）
- 處理：該案例該指標設為NaN或跳過案例

**時間對齊失敗**：
- 無法將案例時間點對齊到1h timeframe
- 處理：記錄錯誤，跳過該案例

### 日誌記錄

**記錄內容**：
- 處理的案例總數
- 成功提取特徵的案例數
- 跳過的案例數及原因
- 數據品質統計

## 性能優化

### 計算優化

**向量化操作**：
- 使用pandas/numpy向量化計算
- 避免Python循環
- 利用M1的SIMD指令集

**並行計算**：
- 按symbol分組並行處理
- 每個worker獨立計算特徵
- 最後合併結果

**快取機制**：
- 已計算的指標快取
- 避免重複計算

### 記憶體優化

**分批處理**：
- 不一次載入所有案例
- 批次大小動態調整

**資料型態**：
- 使用float32而非float64（節省50%空間）
- 整數用int32

**即時釋放**：
- 處理完一批立即釋放記憶體
- 避免記憶體洩漏
