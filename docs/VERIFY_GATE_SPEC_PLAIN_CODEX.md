# 驗收防偽閘 v2.1 白話版

## 1. 一句話總結

這個閘的目的，是讓任何「已驗證、測試通過、真的跑過、沒有資料洩漏」之類的驗收宣稱，都必須能對上真實執行留下的收據；沒有收據、收據範圍不對、或用快測冒充慢測，就不能被寫進交接、commit 或正式驗收流程。

它不是用來防駭客或防惡意偽造的人，而是用來防「人太忙、太相信前一段紀錄、把沒跑過的東西寫成已跑過」這類流程事故。更精準地說，它做到的是：careless-proof 加 tamper-evident，也就是防粗心、留痕跡；不是密碼學等級的防偽。

幾個後面會出現的流程詞先用白話對照：

- commit：把本機改動正式記進版本歷史。
- hook：在 commit 前或寫文件時自動觸發的小檢查。
- CI：推到遠端後，由雲端或自動化環境再跑一次的正式檢查。
- PreToolUse：agent 動手改交接文件前的攔截點。
- receipt：驗證收據，記錄實際跑了什麼和結果。
- hash：檔案或內容的指紋，用來核對「有沒有被換過或改過」。

先把「硬擋」和「放行」講清楚：交接文件、commit 訊息、RESULT 區塊裡新增的驗收宣稱走 fail-closed，證據不齊就擋；討論、引用、事故回顧、SPEC 範例、或已明確標成 SUPERSEDED 的舊結論走 fail-open，不能因為提到「已驗、通過」這些字就誤擋。

## 2. 要防什麼：避免事故重演

這次事故的本質很單純：文件寫了「某個慢測已驗證、已真紅」，但事實上真正的慢測沒有跑過。當時只跑了快速檢查，卻被寫成完整驗收結果。後來第一次真的跑慢測，才發現它是紅的。

這個閘要防的就是這種「驗收宣稱和實際證據對不起來」：

- 沒有跑測試，卻寫「已驗」。
- 只跑了很快的檢查，卻寫成慢測、mutation、requires_kline 這種重驗證已通過。
- 自己手寫一個看起來像收據的檔案，拿來支撐宣稱。
- commit 訊息或交接文件裡夾帶「通過、全綠、無 look-ahead」等驗收結論，但沒有對應證據。
- 一個收據只涵蓋 A 測試，卻拿來支撐同段文字裡 A+B 兩個驗收宣稱。
- 舊文件曾經說綠，後來證明紅，但舊綠燈沒有被標成已取代，導致後人又採信過期結論。

它不試圖解決所有品質問題。它專注在一件事：只要是會影響信任的驗收宣稱，就要能追到「誰、何時、在什麼 commit、跑了什麼、結果如何、log 是哪份」。

## 3. 怎麼防：5 個 Phase 白話版

在進入 5 個 Phase 前，先說明這份 SPEC 的風險分級：它被列為 high，不是因為它會改交易數值、模型或回測結果，而是因為它會碰到交接文件、提交前檢查、CI 和所有驗收流程這些共用路徑。一旦設計錯，可能不是單一測試壞掉，而是整個協作流程卡住或失去保護。

因此它不能直接開工。SPEC 要求的流程是：雙家族 adversarial review、TODO、Composer 實作、Codex review。這些不是形式，而是因為這個閘會影響所有後續工作。

這份 SPEC 也建立在幾個已確認現況上：現有 gate 只攔部分工具呼叫，沒有掃 HANDOFF 內容，也沒有管 commit message；目前 `.git/hooks/` 沒有自訂 hook；GitHub workflow 已存在，可以作為雲端後盾；既有 reconcile stamp 主要靠文字戳記，不驗證來源；既有 mutation 檢查目前沒有自動 receipt；既有 gate 在缺少 `jq` 時偏 fail-open。這些事實決定了為什麼要補三層防線，而不是只改一個腳本；新 CI 的設計則相反，缺工具或環境不完整就 FAIL，不能默默放行。

### Phase 1：跑任何驗證，都自動留下收據

以後重要驗證不是單純跑命令，而是透過一個包裝工具執行。這個工具會同時做兩件事：

- 保留完整 log。
- 產生一張機器可檢查的收據。

收據會記下命令、工作目錄、當時的 git 版本、是否有未提交變更、開始與結束時間、花多久、退出碼、測試摘要、實際選到哪些測試、哪些 marker、stdout/stderr/log 的指紋。

重點是：驗證類型不是人說了算。人可以說「我希望這是 mutation 測試」，但最終分類要由命令內容、測試節點、marker、執行結果推導。這是為了避免「我把快速檢查標成慢測」。

同時，工具還會把收據事件寫進審計紀錄。檢查器不只看收據本身，還要看到審計紀錄中有對應事件，並重新核對收據和 log 的指紋。手寫收據、事後改收據擴大範圍，都不能直接通過。

收據和審計 log 也必須能被 git 追蹤。這裡要特別處理既有 `*.log` ignore 規則，避免真正的 receipt、audit log 或它們的索引被 `.gitignore` 誤傷；否則 CI 和其他 agent 仍然看不到證據，等同「本機有收據、共享歷史沒收據」。

取捨是：這仍然不是防惡意偽造。因為產生收據和寫審計紀錄的是同一個可寫環境。惡意的人仍可能偽造整套痕跡。這個設計承認這點，只承諾能擋粗心與讓竄改留下可查痕跡。

### Phase 2：看文件裡的「驗收宣稱」有沒有證據

檢查器會掃交接、handoff、commit 訊息等信任邊界，找出像「已驗、通過、全綠、真跑、真紅、無 look-ahead、signoff」這類宣稱。

但它不能粗暴地看到關鍵字就擋。因為我們也會在事故檢討、引用舊錯誤、SPEC 說明中提到「已驗」這些字。為了避免誤傷，它會先把文字分成一個個 claim-object，也就是一個小宣稱物件，判斷：

- 這是在宣稱成功、失敗、取代舊結論、待驗，還是純討論？
- 宣稱的範圍是某個命令、某個測試檔、某個 node、某個 task，還是整個區域？
- 它期待的是靜態檢查、快速 smoke、requires_kline 慢測、mutation 測試，還是純讀碼簽核？
- 這段文字是正式操作結果、根 HANDOFF 狀態、commit 訊息、SPEC 討論、引用區塊，還是 fenced evidence？
- 它背後有沒有 receipt、task、stamp、supersede 這類背書？

只有「正式操作結果中的新驗收宣稱」會被硬擋。討論、引用、否定舊 claim、標明 supersede 的段落要放行。這是整個設計最重要的平衡點：機器只當分流器，不當最終法官。

幾個必須放行的白話例子：pytest 原文輸出 `` `42 passed` `` 放在 evidence 區塊時不是新的驗收宣稱；英文片語 `passed through` 不是「測試通過」；架構描述「資料通過層 6.5」也不是驗收結果。這些 V7 排除例會進誤報測試，確保 fail-closed 只打在正式 claim 上。

如果一段正式結果寫了「已驗 VERIFY:某收據」，檢查器會核對：

- 收據真的存在。
- 收據有對應審計事件。
- 收據和 log 指紋吻合。
- 收據已被 git 追蹤或和本次 claim 一起 staged，不能只是本機臨時檔。
- 收據結果的成功或失敗，和文字宣稱一致。
- 收據涵蓋的測試範圍，足以支撐這個 claim。
- 快速檢查不能支撐慢測或 mutation claim。

對讀碼結論，設計允許用 SIGNOFF 類型背書，因為讀碼不一定有測試 receipt。但這種背書不能拿來支撐「慢測跑過」。

還有一個 pending ledger。當某件事被標為待驗，它會留下待驗紀錄。只要同一 task 還有未關閉的待驗項，就不能再宣稱 DONE、ready 或已驗完成。

同一個 claim 也會被算出固定 fingerprint。這不是用來證明它是真的，而是用來發現「後來已經紅了，但舊文件還留著同一個 claim 的綠燈」這類衝突。

### Phase 3：三層 enforcement，把洞補在不同位置

第一層是寫交接文件時擋。當工具要改 `HANDOFF.md` 或 `handoffs/*`，如果新增或修改了正式結果區塊，就先跑 claim checker。這層只看本次新增或修改的文字，不重掃整份歷史文件，避免舊債讓工作無法前進。

但這一層有硬性前提：必須先證明 claim-object 偵測測試的誤報等於 0，才能接到 PreToolUse。若誤報不能降到 0，第一版就不能上這層全攔，只能先用 commit hook、CI 和 receipt。這是 SPEC 的硬性順序條件，不可跳過。

第二層是本地 git hook。pre-commit 會掃 staged 的 HANDOFF、handoffs、docs；commit-msg 會掃 commit subject 和 body。它能擋多數本地提交流程，也會讓使用者在提交前立刻看到問題。

第三層是 CI。這是正式後盾，因為本地 hook 可以被 `--no-verify` 繞過。CI 會在 PR 或 push 上掃 changed files 和 commit range；如果檢查器、環境或依賴缺失，CI 不能假裝沒事放行。

另外會有 health check，檢查 hook 是否安裝、檢查器是否可執行、必要工具是否存在。這是為了防「閘本身壞了但大家以為還在保護」。

### Phase 4：把既有 mutation 驗證和委員流程也接上來源證據

既有 `mutation_probe_check.sh` 會改成經由收據工具執行。它原本的 PASS/FAIL 判定和輸出訊息不應改變，只是多留下收據和審計事件。

這個 Phase 也補兩個同型漏洞：

- adversarial review 不能只查「有沒有某個檔案」，還要能對上 task-id、模型家族、輸出檔 hash 和審計事件。
- reconcile stamp 不能只靠文字搜尋找到一行戳記，還要能對上 task 審計事件和輸出檔 hash。

白話說：不只測試要有收據，委員會審查與 reconciliation 的來源也要能追。

另外會提供一個 `verify_audit_chain.py`，讓使用者或 reviewer 可以低成本抽查整條審計鏈。它是輔助人工稽核，不是承諾把所有判斷都機器化。

### Phase 5：RESULT 欄位結構化，並處理舊綠燈和新紅燈衝突

以後 RESULT handoff 不能只用自然語言寫「看起來過了」。它要有固定欄位：

- 靜態檢查是 NOT_RUN、PASS、FAIL，還是 N/A 並附理由。
- runtime 檢查是 NOT_RUN、PASS、FAIL，還是 N/A 並附理由。
- mutation 檢查是 NOT_RUN、PASS、FAIL，還是 N/A 並附理由。
- 對應 receipts 是哪些。
- 還有哪些 pending 未關閉。

這讓機器不用猜段落語意，也讓人快速看出到底哪些真跑、哪些沒跑。

Phase 5 也會做輕量衝突檢查：如果某個 claim 後來出現 RED/FAIL，舊文件裡相同 claim 的綠燈沒有標成 SUPERSEDED，就擋。完整的 HANDOFF 自動 render 索引暫不在 v1 做，因為改動習慣和文件流太大，先用衝突檢查降低風險。

Phase 5 還補一條針對 SPEC 自身的防線：任何規格文件在 §A 或「已確認」段落裡寫到資料結構、型別、欄位、單位、命令輸出等事實時，必須附 `FACT-RECEIPT:`，說明實際跑了什麼、印出什麼。純設計假設不能寫成「已確認」；規格文件本身也不能空口宣稱「已實測」。

## 4. 為什麼要三層防線

只靠一層會有明顯漏洞。

只靠寫文件時擋，可能漏掉 commit 訊息，也可能因為工具路徑不同沒有觸發。

只靠本地 git hook，開發者可以用 `--no-verify` 跳過，或本機 hook 沒裝好。

只靠 CI，問題會到 PR 或 push 才爆，回饋太晚，而且本地交接文件仍可能短時間污染後續 agent。

所以三層各守不同位置：

- PreToolUse 守「寫進交接的當下」。
- git hook 守「本地提交前」。
- CI 守「正式進入共享歷史前」。

這三層不是為了追求完美，而是避免單點失效。設計上也保留降級路徑：如果 claim-object 偵測還沒做到誤報 0，就不能急著接 PreToolUse，以免合法討論或引用被擋到大家繞過整套制度。

## 5. 已知會失效的地方，以及怎麼補

### 5.1 它不能防惡意偽造

收據和審計紀錄都在同一個 repo / 工作環境內產生。惡意的人若有寫入權，理論上可以偽造完整鏈條。

接受原因：目前威脅模型是「編排者疏忽、過度宣稱、文件污染」，不是惡意內鬼或外部攻擊。

補法：如果未來要防惡意偽造，需要 repo 外密鑰、簽章、不可變審計系統，這不在 v1。

### 5.2 它不能保證人類解讀正確

如果測試真的跑了，但人把紅看成綠，或把「不代表資料正確」的結果解讀成「資料正確」，這個閘不能完全判斷。

接受原因：機器能核對「有沒有跑、跑了什麼、範圍對不對」，但不能可靠判斷所有工程語意。

補法：靠 adversarial review、三方委員會、code review、結構化 RESULT 欄位降低錯讀機率。

### 5.3 語意分類器不能當法官

中文、英文、引用、反諷、事故檢討、SPEC 範例都可能包含「已驗、通過、真紅」這些詞。若用關鍵字硬擋，會造成大量誤報，最後大家會用豁免或跳過把制度掏空。

接受原因：SPEC 明確要求分類器只當 router。它負責找出可疑 claim 並分流；真正判斷靠 receipt、task、stamp、ledger 是否對得上。

補法：先做誤報=0 的測試套件；討論、引用、fenced evidence、supersede 要能放行；未知近似詞先 WARN，收集後再決定是否升級為 FAIL。

### 5.4 豁免可能被濫用

如果豁免太寬，大家可能用 `VERIFY-EXEMPT` 洗掉所有不方便的檢查。

接受原因：有些文字確實不該要求收據，例如 typo、doc-example、migration-note、template-drift、tooling-blocked、spec-ambiguity。

補法：豁免類別很窄；每檔每 issue-id 最多一次；HANDOFF operational status、commit message、RESULT 段零豁免；CI 統計 exempt 率並警告。

### 5.5 本地未追蹤收據不能支撐已提交 claim

如果 claim 進了 commit，但 receipt/log/audit 只存在本機未追蹤檔，其他人和 CI 看不到，會形成「我本機有證據」但共享歷史沒有證據。

補法：VERIFY、REF、SIGNOFF 的 backing artifact 必須和 claim 同 commit staged，或已存在於被引用的 git object；worktree-only backing 不滿足已 commit claim。

### 5.6 pending ledger 可能有競態或卡住

pending ledger 是 append-only JSONL。v1 沒有完整 file lock，單機場景風險低，但理論上仍有同時寫入導致順序或一致性問題。

補法：v1 提供 reducer 和 `list-open`，讓人能看未結 pending；phase 2 再加鎖與更完整索引。

### 5.7 舊文件的歷史債不會一次清完

v1 不做完整 HANDOFF render 索引，不會把所有過期 claim 一次重寫。這避免大規模 churn，但也表示舊污染可能只在衝突檢查或人工檢視時逐步浮出。

補法：v1 做相同 claim 的 RED/FAIL 與舊綠燈衝突檢查；完整自動索引延後到 phase 2。

### 5.8 未知同義詞一開始可能只警告

如果有人用新的說法描述「已驗」，例如不是詞表中的近似語，v1 可能先 WARN 而不是直接 FAIL。

接受原因：一開始就把所有近似語硬擋，容易造成誤報和繞過。

補法：收集 WARN，週期性補詞表，再把高信心詞升為 FAIL。

## 6. 還沒做完的部分

v1 明確不做或延後的部分包括：

- 數值 golden baseline：本 epic 不改交易策略、ML 模型、回測結果或輸出 schema，所以沒有數值 golden；驗收靠治理行為測試，例如假 claim 會擋、真 receipt 會放、引用與討論誤報為 0。
- 完整 HANDOFF render 索引：先只做衝突檢查，完整索引列為後續 phase。
- 惡意偽造防護：v1 不做 repo 外簽章、不可變外部審計或密碼學保證。
- pending ledger file lock：v1 接受單機低風險，後續再加。
- run_receipts 完整索引與自動 render：後續 phase 補。
- 未知同義詞直接 fail：v1 先 WARN，避免誤報撞牆。
- PreToolUse 全攔：只有 claim-object 測試達成誤報=0 才能接；否則 v1 降級為 commit hook + CI + receipt。

總結取捨：這套閘把最危險、最低成本可機械化的部分先機器化，也就是「驗收宣稱必須有可追溯證據」。它刻意不把所有人類判斷都交給機器，因為那會產生誤報、繞過和假安全感。它的成功標準不是保證世界上不會再有錯，而是讓「沒跑卻寫已跑、快測冒充慢測、來源戳記無證據」這些事故在進入共享歷史前被擋下，或至少留下足夠清楚的稽核痕跡。
